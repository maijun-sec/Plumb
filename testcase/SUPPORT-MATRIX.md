### 03-pointer-multilevel

**Field-, array- and container-sensitive aliasing is sound, and its guard transfer is sound with it.** Allocation-site identity, field sensitivity, per-key container cells, cross-method returns and call-site context all resolve; every alias precision gate (12 TN) holds. R1113 found the one way guard transfer was still unsound: the rule suppressed a finding whenever *some* alias was guarded, but the alias map is a may-relation, so a guard on `first` silenced a dereference of a `List.get` result that could equally be an unguarded `second`. It now requires the guard to cover the receiver's whole points-to set. R1114 added the null direction to the heap facts -- as a separate channel rather than a null sentinel, because one shared sentinel would make every null in the program compare equal and leak into the guard test -- which closes the `x.f = null` gap the fact domain previously could not express. One limit remains recorded: the AST rule cannot follow an alias at all.

### 05-real-cve-derived

**`CVE-918-ssrf` is now scored as an UNSUPPORTED capability, and the count reads TP 14/14.** The case was a TP, pinned to `dfa-taint-leak` at line 140 -- and the finding it matched was a FALSE POSITIVE. The old resource-leak checker treated every `new X(...)` as an allocation, so `new URL(userSuppliedUrl)` was reported as an unclosed resource, but `java.net.URL` has no `close()` and is not a resource at all. The case therefore passed for the wrong reason: the finding was there, but it was not evidence of SSRF, and the manifest said so itself ("there is no CWE-918 finding, which is the remaining gap"). The checker now decides by TYPE -- an allocation is a resource only when the type can be closed, and the closeable list is the single source of truth for both the `new X(...)` form and the `X.factory(...)` form -- so the false positive is gone and the case correctly reports that the SSRF capability is ABSENT. It is marked `unsupported` rather than `false-negative`: the engine cannot detect CWE-918 at all, so scoring it as a miss would say the rule is broken rather than incomplete, and the gap is the real, named one.

**CWE-502 fires on all four unmitigated shapes and CWE-117 on all five Log4Shell shapes, including the three-frame cross-method case.** The CWE-117 support needed two fixes: the `log.sinks` family had no checker bound to it at all, and a logger held in a static field lowered to the callee signature `LOG.info/1` with no type, so no FQN-anchored sink pattern could match. R1115 closed the third: an identifier allowlist is the only correct fix for ORDER BY / table / column, because bind variables cannot bind identifiers, and the engine modelled sanitizers purely by callee signature -- an allowlist is not a call, it is a value being narrowed. It is now recognised, and only in the reject-and-assign form: `if (!"a".equals(x)) { x = "a"; }` closes every path that could carry an unlisted value, while `if ("a".equals(x)) { x = "a"; }` does not, because its fall-through keeps the user's value. R1120 tightened that further: polarity alone was not enough, because a negation inside a disjunction (`if (!"a".equals(x) || !"b".equals(y))`) can be satisfied by the unrelated disjunct, so the substitution never runs. The proof is now deferred to the branch, where the boolean combine is visible. R1116 closed the last true negative by fixing the FIXTURE rather than the engine -- `runCommand` had been a `println` stand-in, so no `command.sinks` pattern could ever match and the case asserted a finding on a shape the engine has no sink for. Behind an `if (false)` guard it is inert at runtime and present in the IR, which is what a fixture is for.

**R1122 closed the two CWE-502 limitations, and the count now reads TN 5/5.** `CVE-502-filtered-tn` and `CVE-502-allowlist-tn` are no longer known limitations: the engine now represents the JEP-290 filter as a fact, and the sink check honours it. `DeserializationFilterTracker` records that a stream carries a filter which can REJECT, and it distinguishes the two shapes that matter. A PATTERN filter restricts when its pattern ends in `!*` -- the JEP-290 idiom for "refuse everything else" -- and a pattern without it allows every class it does not mention, so it restricts nothing. A LAMBDA filter restricts when its body can return `REJECTED`; a body that only ever returns `ALLOWED` or `UNDECIDED` is the partial mitigation and must still be reported. The filter is a property of the STREAM, so the check is on the receiver, and it is SCOPED to the deserialization family: a filter says nothing about a log entry, a command line, or a SQL statement.

**Three engine defects had to be fixed before that fact could be represented at all, and each one had been hiding a real finding.**

- **Try-with-resources were never translated.** The resource declarations were dropped, so the resource variable was never a local: every reference to it inside the body fell through the name resolver's `this.<name>` fallback and became a FIELDLOAD off `this` with an `UNKNOWN` type, and the initializer was never translated so no taint could reach it. The consequence was that `try (ObjectInputStream ois = new ObjectInputStream(untrusted)) { ois.readObject(); }` was STRUCTURALLY INCAPABLE of producing a CWE-502 finding, while the same code outside a try-with-resources did produce one. A mitigation and a vulnerability that differ only in their braces were indistinguishable.
- **Lambda names were not program-unique.** The counter lived on the per-method builder, so every method's first lambda was called `lambda$0` and the program's function table held several functions with the same name. Anything that resolves a lambda BY NAME then got an arbitrary answer -- and the filter tracker asks "does this lambda's body ever return REJECTED?", so with one rejecting and one permissive lambda both read as rejecting, and the permissive one's finding was silently dropped.
- **The lambda bodies were indexed too late.** They were indexed in `finish()`, which runs AFTER the whole instruction walk, so a lambda filter never had its body read before the sink asked about it. They are now indexed in `initEngine()`, before any function is visited.

**The manifest's own pins were wrong, and that only became visible once the rule could fire.** `CVE-502-camel-pqc-file` was pinned to line 98 and `CVE-502-partial-mitigation` to line 142 -- the `readObject()` calls of the two MITIGATED methods, which are supposed to be silent. The CWE-502 rule never fired anywhere in this category before, so the pins were never exercised and nobody noticed they pointed at the wrong methods. They are re-pinned to 69 and 120.

**R1122 also recovered three findings in category 01 that the TAC had been hiding.** `NonSqlSink.writeByName` and `NonSqlSink.copyByPath` both open a `FileOutputStream` in a try-with-resources, so before the fix the `new FileOutputStream(out)` never entered the IR and the CWE-22 path-traversal finding on the tainted path was never reported. Category 01 now measures 903 findings instead of 900: +2 CWE-22 (genuine path-traversal true positives) and +1 CWE-404 (a conditional close, which leaks on the other path). Making the resource visible exposed two pre-existing gaps in the resource-leak checker, both now fixed: a close on a local did not close the allocation it was assigned from (the allocation is on a temporary, the close on the local), and a close on only SOME path was treated as a close on every path.

### 06-framework-orms

**Two framework shapes are covered, and they need two different engines.**

The Spring JDBC shape is a *taint-flow* problem: the request value is bound to a method parameter by the framework, flows through a field, and reaches a `JdbcTemplate` call whose SQL text is built by concatenation. Nothing about the framework is unusual except that the receiver's type cannot be resolved. The third-party jar is not on the analysis classpath -- the normal situation for a source-only scan -- so the TAC writes the callee signature with a SIMPLE receiver name (`JdbcTemplate.query/2`) instead of a fully qualified one. Every one of the 416 sink patterns in the registry is anchored to a fully qualified name, so before the sink matcher learned to accept the prefix-optional form, none of these sinks was reachable, and nothing was reported: no error, no warning, just a scanner that could not see Spring at all. The relaxed form is consulted only for a bare simple-name receiver; a fully qualified callee still matches the strict pattern first, the class name and the method name both stay mandatory, and a word boundary after the method name keeps `JdbcTemplate.query` from matching `queryForList`.

The MyBatis shape is *not* a taint-flow problem, and treating it as one is the mistake that hides it. The TAC does not carry annotations, and a mapper method lowers to a bare `RETURN`, so by the time the taint engine runs, the string `"SELECT * FROM users WHERE name = '${name}'"` is gone -- there is nothing left to propagate. The detection therefore belongs in the AST, where the annotation is still attached to the method. The rule reports a raw `${...}` substitution and not a bound `#{...}` placeholder, because the two have opposite safety properties: `#{}` becomes a PreparedStatement placeholder and the value is bound as data, while `${}` is a raw string substitution and the value becomes part of the SQL text. A `${}` that names something the method does not receive is not reported either -- a dynamic table name or column is a legitimate use of raw substitution, because a prepared-statement placeholder cannot stand in for SQL structure.

The third shape is the FRAMEWORK ENTRY POINT, and it is the one a servlet-aware scanner cannot see at all. A Spring controller has no `getParameter()` call anywhere: the framework binds the request value to the method parameter BY ANNOTATION, and the controller body never touches a request object. So the source is not a call, it is a parameter annotation. The taint engine therefore treats a parameter carrying `@RequestParam` / `@PathVariable` / `@QueryParam` as a source whose origin is the HTTP request, and the finding names that origin (`param:customer@spring-mvc:RequestParam`) rather than an opaque parameter name. The annotation list is the same one the AST checkers use for input validation, so the two layers agree on what "user input" means in this codebase. A framework entry point outranks the caller's origin: the value was bound by the framework from the request, so no caller can supply a more specific origin for it, and the caller's label would name an unrelated parameter in an unrelated class.

### 07-unchecked-return

**The question is whether a return value is observed, and the answer needs three facts: the call's name, its return type, and whether anything reads the result.**

CWE-252 is about a method whose return value says "did this work?" being thrown away. The value can be discarded in three shapes, and all three are real defects:

```java
target.delete();                // the statement drops the value
boolean ok = target.delete();   // stored, and 'ok' is never read
log(target.delete());           // the logger drops the value
```

The first shape is the one a name-based rule finds, and it is the *rarest* of the three in real code. The second needs a use analysis of the method's locals: a local that is written but never read is not observed. The third needs to know which callees ignore their arguments (`println`, `log`, `trace`, ...) and which use them (`valueOf`, `compare`, `requireNonNull`, ...).

## The void question

A void method has no return value, so there is nothing to discard. The JDK signatures are the authority: `InputStream.close()`, `Connection.commit()`, `Writer.flush()` and `Files.delete(Path)` are all void, and they report failure by **throwing**. A name-only rule reports every one of them.

Failing to handle the exception a void method throws is **CWE-703** (improper check of exceptional conditions) — a different rule, with a different mechanism. This category says nothing about it, and the rule does not pretend to.

The rule resolves the call's return type, and **an unresolvable call is reported**: an unresolved type is a missing fact, never a proof of safety. This matters because a source-only scan has no third-party jar on the classpath, so a library call usually cannot be resolved at all.

## What the fix underneath turned out to be

The void check needs symbol resolution, and the scan pipeline **translates to TAC first** and only then runs the AST checkers on the same tree. The translation was re-parenting the AST: the translator built a synthetic `VariableDeclarationExpr` around a field's original `VariableDeclarator` with `NodeList.nodeList(v)`, and that *moves* the declarator — it is detached from its `FieldDeclaration` and attached to a node that hangs off no `CompilationUnit`. JavaParser's `getSymbolResolver()` walks the parent chain to find the unit, so every `resolve()` on that declarator and everything under it threw.

The visible symptom was narrow — one rule reporting void methods as unchecked returns — but the cause was shared: **the translation silently disabled type resolution for every AST checker that ran after it**, and a checker that cannot resolve a type has no way to say "I do not know". The translator now *copies* the declarator instead of moving it, and `TranslationKeepsSymbolResolutionTest` holds that in place.
