## Verdicts

### 01-taint-crossfile

**Cross-process and cross-file taint propagation works, and findings are attributed to the caller's parameter.** Values traverse ~9 methods across 6 files and reach the sink. Every case passes, including the sink-side shapes the DFA engine has no pattern for -- those are caught by `ast-style-info-exposure-querystring` (CWE-89), which is why the harness must match on an explicit rule list rather than a rule-prefix blacklist (R1102).

### 02-domain-sensitive

**Range and guard narrowing is sound, including across call boundaries.** Local guards, `Math.min`/`Math.max` clamps, and the early-return idiom (`if (d == 0) return 0;`) are all honoured. The early-return case needed a false-edge fact the guard tracker could not express: the guard is popped by the JUMP that skips the else block, so the else body looked unguarded (R1101).

### 03-pointer-multilevel

**Field-, array- and container-sensitive aliasing is sound, and its guard transfer is sound with it.** Allocation-site identity, field sensitivity, per-key container cells, cross-method returns and call-site context all resolve; every alias precision gate (12 TN) holds. R1113 found the one way guard transfer was still unsound: the rule suppressed a finding whenever *some* alias was guarded, but the alias map is a may-relation, so a guard on `first` silenced a dereference of a `List.get` result that could equally be an unguarded `second`. It now requires the guard to cover the receiver's whole points-to set. R1114 added the null direction to the heap facts -- as a separate channel rather than a null sentinel, because one shared sentinel would make every null in the program compare equal and leak into the guard test -- which closes the `x.f = null` gap the fact domain previously could not express. One limit remains recorded: the AST rule cannot follow an alias at all.

Outstanding: 
- none

Known limitations: 
- `L6-AST-cannot-follow-the-alias`

### 05-real-cve-derived

**CWE-502 fires on all four unmitigated shapes and CWE-117 on all five Log4Shell shapes, including the three-frame cross-method case.** The CWE-117 support needed two fixes: the `log.sinks` family had no checker bound to it at all, and a logger held in a static field lowered to the callee signature `LOG.info/1` with no type, so no FQN-anchored sink pattern could match. R1115 closed the third: an identifier allowlist is the only correct fix for ORDER BY / table / column, because bind variables cannot bind identifiers, and the engine modelled sanitizers purely by callee signature -- an allowlist is not a call, it is a value being narrowed. It is now recognised, and only in the reject-and-assign form: `if (!"a".equals(x)) { x = "a"; }` closes every path that could carry an unlisted value, while `if ("a".equals(x)) { x = "a"; }` does not, because its fall-through keeps the user's value. R1120 tightened that further: polarity alone was not enough, because a negation inside a disjunction (`if (!"a".equals(x) || !"b".equals(y))`) can be satisfied by the unrelated disjunct, so the substitution never runs. The proof is now deferred to the branch, where the boolean combine is visible. R1116 closed the last true negative by fixing the FIXTURE rather than the engine -- `runCommand` had been a `println` stand-in, so no `command.sinks` pattern could ever match and the case asserted a finding on a shape the engine has no sink for. Behind an `if (false)` guard it is inert at runtime and present in the IR, which is what a fixture is for.

**Three cases are recorded as known limitations rather than counted as passing precision gates**, and R1121 is why the count reads TN 3/3 instead of 5/5. Two of them -- `CVE-502-filtered-tn` and `CVE-502-allowlist-tn` -- were previously scored as precision wins, and both were unfailable: each was anchored on an enclosing method name, which the engine reports only as a substring of other findings' `sink_function`, so the anchor check was answered by an unrelated finding and the gate passed without ever asking about CWE-502. Re-pinned to the real sink, the engine turns out to report BOTH JEP-290-mitigated `readObject()` calls, even though `UnsafeDeserializationChecker`'s own spec text names `ObjectInputFilter` / `resolveClass` as sanitizers it must recognise. Nothing implements that, so the limitation is an absence of capability in the fact domain rather than an unsound result, and both are scored outside the tallies with the finding left visible. The third, `LOG4SHELL-sanitized-tn`, is unrelated: a `replace("${", "")` chain is not provably a sanitizer, and the real fix is a runtime configuration cutoff.

### 06-framework-orms

**Two framework shapes are covered, and they need two different engines.**

The Spring JDBC shape is a *taint-flow* problem: the request value is bound to a method parameter by the framework, flows through a field, and reaches a `JdbcTemplate` call whose SQL text is built by concatenation. Nothing about the framework is unusual except that the receiver's type cannot be resolved. The third-party jar is not on the analysis classpath -- the normal situation for a source-only scan -- so the TAC writes the callee signature with a SIMPLE receiver name (`JdbcTemplate.query/2`) instead of a fully qualified one. Every one of the 416 sink patterns in the registry is anchored to a fully qualified name, so before the sink matcher learned to accept the prefix-optional form, none of these sinks was reachable, and nothing was reported: no error, no warning, just a scanner that could not see Spring at all. The relaxed form is consulted only for a bare simple-name receiver; a fully qualified callee still matches the strict pattern first, the class name and the method name both stay mandatory, and a word boundary after the method name keeps `JdbcTemplate.query` from matching `queryForList`.

The MyBatis shape is *not* a taint-flow problem, and treating it as one is the mistake that hides it. The TAC does not carry annotations, and a mapper method lowers to a bare `RETURN`, so by the time the taint engine runs, the string `"SELECT * FROM users WHERE name = '${name}'"` is gone -- there is nothing left to propagate. The detection therefore belongs in the AST, where the annotation is still attached to the method. The rule reports a raw `${...}` substitution and not a bound `#{...}` placeholder, because the two have opposite safety properties: `#{}` becomes a PreparedStatement placeholder and the value is bound as data, while `${}` is a raw string substitution and the value becomes part of the SQL text. A `${}` that names something the method does not receive is not reported either -- a dynamic table name or column is a legitimate use of raw substitution, because a prepared-statement placeholder cannot stand in for SQL structure.

The third shape is the FRAMEWORK ENTRY POINT, and it is the one a servlet-aware scanner cannot see at all. A Spring controller has no `getParameter()` call anywhere: the framework binds the request value to the method parameter BY ANNOTATION, and the controller body never touches a request object. So the source is not a call, it is a parameter annotation. The taint engine therefore treats a parameter carrying `@RequestParam` / `@PathVariable` / `@QueryParam` as a source whose origin is the HTTP request, and the finding names that origin (`param:customer@spring-mvc:RequestParam`) rather than an opaque parameter name. The annotation list is the same one the AST checkers use for input validation, so the two layers agree on what "user input" means in this codebase. A framework entry point outranks the caller's origin: the value was bound by the framework from the request, so no caller can supply a more specific origin for it, and the caller's label would name an unrelated parameter in an unrelated class.

Outstanding: 
- none

Known limitations: 
- none
