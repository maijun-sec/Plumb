# Three-Address Code (TAC) Format Specification

[English](../README.md) | [中文](../zh/tech/TAC.md)

This document defines the TAC format of Plumb's intermediate representation (IR). All Java source code / bytecode is eventually translated into TAC, which is then handed to the DFA engine for analysis.

## 1. Design goals

| Goal | Explanation |
| --- | --- |
| Dataflow-friendly | Single-definition / single-use (SSA-lite), convenient for forward/backward flow analysis |
| Serializable | All IR classes (`TacProgram` / `TacFunction` / `TacInstruction` / `TacCfg` / `TacBasicBlock` / `TacType` / `TacOperand` / `MergedProgram` / `SourceMap`, 9 in total) implement `Serializable` and can be written to disk through `IrSerializer` (see §6) |
| Language-agnostic | A naming convention of name + type, with no Java 17 syntax sugar embedded |
| Compact | For a repository of ~5000 files, the serialized IR is on the order of 150 MB on disk |

## 2. Top-level containers

### 2.1 `TacProgram`

```java
public final class TacProgram implements Serializable {
    private transient Path sourcePath;       // from .java / .class / .jar (transient, not serialized)
    private final String typeName;          // primary class name
    private final Map<String, TacFunction> functions;   // signature -> fn
    // additionally: classToParent, classToChildren, lambdaBindings
    // additionally: sourceMap, programProblems, classFieldAnnotations
}
```

`typeName` is the short class name (without the package name). For a file with multiple top-level classes, only the first one is kept as `typeName`, while the methods of the other classes are also translated into `functions`.

### 2.2 `MergedProgram`

```java
public final class MergedProgram implements Serializable {
    private final List<TacProgram> sources;
    public TacProgram asProgram();          // merge into one virtual program
}
```

`MergedProgram.asProgram()` returns a `TacProgram` view whose function set is `sources.flatMap(p -> p.functions().values())`. It is used for cross-TU scanning.

## 3. Functions

### 3.1 `TacFunction`

```java
public final class TacFunction implements Serializable {
    private final String name;               // "main"
    private final String signature;         // "Demo#main"
    private final String enclosingClass;    // "Demo"
    private final TacType returnType;
    private final List<TacOperand.TacVar> params;
    private final List<TacOperand.TacVar> locals;
    private final List<TacInstruction> instructions;  // linear flow
    // additionally: origin, classAnnotations, methodAnnotations, fieldAnnotations,
    //        paramAnnotations, tryRegions
    // the try/catch/finally regions (public final, for the CFG builder):
    //        tryStart/tryEnd, catchStart/catchEnd, catchLabels,
    //        finallyLabel, finallyStart/finallyEnd
}
```

`signature` has the format `<enclosingClass>#<name>` (constructors and `<clinit>` follow the same rule). It is the key of the call graph.

### 3.2 `TacVar` and `TacOperand`

```java
public sealed interface TacOperand extends Serializable
        permits TacOperand.TacVar, TacOperand.Const { }

public static final class TacVar implements TacOperand {
    private final String name;        // "x" / "t0" / "this"
    private final TacType type;
    private final boolean isTemp;     // temporary variable generated by the translator
}

public static final class Const implements TacOperand {
    public enum Kind { INT, LONG, FLOAT, DOUBLE, BOOL, CHAR, STRING, NULL }
    private final Kind kind;
    private final Object value;
    private final TacType type;
}
```

TAC is 3-address: every `TacInstruction` has at most 1 `dest` (destination) + 2 lhs (operands). An lhs can be a `TacVar` (named storage) or a `Const` (literal).

### 3.3 `TacType`

```java
public final class TacType implements Serializable {
    public enum Kind {
        BOOLEAN, BYTE, SHORT, CHAR, INT, LONG, FLOAT, DOUBLE, STRING,
        CLASS, ARRAY, NULL, VOID, UNKNOWN
    }
    private final Kind kind;
    private final Object payload;   // the short class name when kind == CLASS;
                                   // the element type (TacType) when kind == ARRAY
}
```

`className()` returns `(String) payload` when `kind == CLASS`; `arrayComponent()`
returns the element type when `kind == ARRAY`.

`STRING` takes a fast path; `CLASS` keeps only the short name (without the package). Generics are erased.

## 4. Instruction set

`TacInstruction.Kind` has 19 kinds in total:

| Kind | Fields | Meaning |
| --- | --- | --- |
| `MOVE` | `dest = lhs1` | Simple assignment / phi / one side of a cast |
| `BINOP` | `dest = lhs1 <op> lhs2` | Binary operation (+, -, ==, &&, \|\|) |
| `UNARYOP` | `dest = <op> lhs1` | Unary operation (-, !, ~, ++, --, cast) |
| `CALL` | `dest = calleeSig(args...)` | Method call; dest may be null (a `void` call) |
| `NEW` | `dest = new <type>(args...)` | Object construction |
| `NEWARRAY` | `dest = new <type>[lhs1]` | Array allocation |
| `ARRAYLOAD` | `dest = lhs1[lhs2]` | Array read |
| `ARRAYSTORE` | `lhs1[lhs2] = dest` | Array write |
| `FIELDLOAD` | `dest = lhs1.<fieldName>` | Field read (lhs1 is null for a static field) |
| `FIELDSTORE` | `lhs1.<fieldName> = dest` | Field write |
| `INSTANCEOF` | `dest = lhs1 instanceof <type>` | Type check |
| `BRANCH` | `if (lhs1) goto trueLabel else falseLabel` | Conditional branch |
| `JUMP` | `goto label` | Unconditional jump |
| `LABEL` | `label:` | Basic block label |
| `RETURN` | `return [lhs1]` | Method return |
| `THROW` | `throw lhs1` | Throw an exception |
| `CATCH_HANDLER` | `catch (<type>) -> dest` | Entry of a catch block (dest is the catch parameter) |
| `FINALLY_ENTER` | `finally:` | Entry of a finally block |
| `NOP` | — | no-op |

`CATCH_HANDLER` and `FINALLY_ENTER` make try/catch/finally explicit in the IR (and add `exceptionSuccessors` edges to the CFG). The exact semantics:

- **`CATCH_HANDLER` (`catch (<type>) -> dest`)** — the entry of a catch block. `dest` is the catch parameter binding (always non-null at runtime, with the type derived from the throws clause). When `TaintedCheckerBase` sees a `CATCH_HANDLER` it marks `dest` as NNE (Non-Null Evidence) and propagates the taint label of the associated `THROW` instruction to `dest`. This is why `NullDerefChecker` does not report "catch (NullPointerException e) { e.x ... }" — `e` is bound to be non-null.
- **`FINALLY_ENTER` (`finally:`)** — the entry of a finally block. The CFG builder adds an exception edge to the FINALLY block from every basic block inside the try and every catch block (the ones ending in `THROW`), modelling the semantics of "the finally block always runs, no matter how try/catch goes".
- The old `L_CATCH_<Type>` / `L_FINALLY` label name patterns are kept — label-based tooling (UnusedLabelChecker / SARIF / cache-key normaliser) is not broken.

### 4.1 Binary / unary operators

```java
public enum BinaryOperator {
    ADD, SUB, MUL, DIV, MOD,
    AND, OR, XOR, SHL, SHR, USHR,
    EQ, NE, LT, LE, GT, GE,
    LAND, LOR
}

public enum UnaryOperator {
    NEG, NOT, BITNOT,
    PRE_INC, PRE_DEC, POST_INC, POST_DEC,
    CAST
}
```

The target type of `CAST` is on `TacInstruction.castType`. `LAND`/`LOR` are the short-circuiting and/or operators (the rhs is not forced to be evaluated).

### 4.2 CALL signature

`calleeSig` uses the format `<FQN>#<method>(<param-types>)`, for example `java.lang.Runtime#exec(String)`. Overloads are distinguished by the full signature.

For a lambda call, the calleeSig is a synthesised `lambda$N`, corresponding to a binding registered by `TacProgram.bindLambda`.

## 5. CFG

```java
public final class TacCfg implements Serializable {
    private final String functionSig;
    private final List<TacBasicBlock> blocks;      // in order
    private final Map<Integer, List<Integer>> successors;          // block id -> successor ids
    private final Map<Integer, List<Integer>> exceptionSuccessors;  // block id -> exception-flow successor ids
    private final int entryId;
}

public final class TacBasicBlock implements Serializable {
    private final int id;                 // block number
    private final List<Integer> indices;  // indices of the owned instructions in TacFunction.instructions
}
```

A basic block **does not hold the instruction list**; it only holds indices, while the instructions themselves stay in `TacFunction.instructions`.
The edges are **not object references** either, but a mapping from `block id` to a list of successor `block id`s.
The dataflow engine uses `succs(blockId)` to get the normal successors and `exceptionSuccs(blockId)` to get the exception-flow successors
(a block inside a try region that throws leads to the corresponding catch block; when the try has a finally, it also leads to the finally block).

`TacCfgBuilder.build(fn)` splits `TacFunction.instructions` into basic blocks, correctly handling:

- Straight-line flow (MOVE/BINOP/CALL/...) staying in the same block
- `BRANCH` / `JUMP` ending the current block
- `LABEL` starting a new block
- `RETURN` / `THROW` terminating the current block
- `CATCH_HANDLER` / `FINALLY_ENTER` starting a new block, with the CFG builder wiring up the try/catch edges

## 6. Serialization (IrSerializer)

All IR classes implement `java.io.Serializable` + `serialVersionUID = 1L`. `org.plumb.tac.io.IrSerializer` provides `writeProgram / readProgram / writeMerged / readMerged / writeObject / readObject`, backed by `ObjectOutputStream` + `BufferedOutputStream`, with an optional `.gz` suffix triggering GZIP wrapping.

File format:

```
┌──────────┬──────────────┬─────────────────┐
│ MAGIC    │ VERSION      │ <Object>        │
│ 0x504C554D (4B)        │ (Java serialization) │
│ 0x00000001 (4B)        │                │
└──────────┴──────────────┴─────────────────┘
```

See `docs/usage/CLI.md` §5.3 and `plumb-main/.../OutputLayout.java` for the file naming.

## 7. TAC generation pipeline

```
.java  →  JavaParser  →  CompilationUnit  →  ParsedSource
                                                  │
                                                  ▼
                                          TacTranslator
                                                  │
                                                  ▼
                                              TacProgram
                                                  │
                                                  ▼
                                          TacCfgBuilder  →  TacCfg
                                                  │
                                                  ▼
                                          DfaEngine（plumb-dfa）
```

The implementation of `TacTranslator` lives in `plumb-tac/src/main/java/org/plumb/tac/translate/TacTranslator.java`. It recursively visits every node of the CompilationUnit and translates statements into a linear `TacInstruction` stream. The CFG is built offline by `TacCfgBuilder` (`plumb-tac/.../TacCfgBuilder.java`).

The bytecode path (`.jar` / `.class`) goes through `BytecodeAnalyzer` (inside plumb-tac), which lowers SootUp's Jimple further down to TAC, with the same structure as the source code path.

## 8. The gap to SSA

Plumb's TAC is **not full SSA**:

- There is no `φ` function; the same variable is not automatically joined at a branch merge point
- Branch conditions appear repeatedly (for example, in `if (a > 0) { a = 1; } use(a);` the use does not see that `a` was defined)

This means:

- Forward dataflow needs to copy the last-def at every BRANCH
- Cross-function reasoning relies on `summaryCache` (reuse of callee summaries), not on the SSA form

Constraint solving (Z3) lives in the `solver` package of `plumb-dfa`, but that is **constraint solving over facts**,
not rewriting TAC into the SSA form: the TAC itself keeps the non-SSA shape described above.
