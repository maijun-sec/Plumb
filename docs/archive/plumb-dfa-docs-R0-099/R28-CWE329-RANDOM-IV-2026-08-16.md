## Goal

Add detection for CWE-329 (Not Using a Random IV with CBC Mode). Juliet's
CWE-329 corpus has 17 files, all using the same template.

## Background

CWE-329 covers AES (or any block cipher) in CBC mode that uses a
non-random or non-unique Initialization Vector. The IV is XORed with
the first plaintext block before encryption, so:

- A **hardcoded IV** (e.g. all zeros) means identical plaintexts
  always produce identical first blocks. Two encryptions of the
  same plaintext look identical.
- A **reused IV** with the same key allows an attacker to detect
  when two messages share a common first block, and with enough
  ciphertexts to recover the XOR of any two plaintexts.

Juliet's `CWE329_Not_Using_Random_IV_with_CBC_Mode/` corpus (17 files)
uses the same template:

- **Bad (`bad()`)**: builds an IV as a hardcoded byte array
  (`byte[] iv = {0x00, 0x00, ..., 0x00};`) and passes it to
  `new IvParameterSpec(iv)`.
- **Good (`good1()` / `good2()`)**: builds the IV as
  `new byte[blockSize]`, fills it with `SecureRandom.nextBytes(iv)`,
  then passes it to `new IvParameterSpec(iv)`.

## R28 ships

### New file: `Cwe329RandomIvChecker.java`

A source-reading DFA-style checker in the main `checkers/` package.
Uses `SourceReader` (R19's shared utility) to read the source file,
then walks each `new IvParameterSpec(...)` call.

Detection logic:

1. **Inline literal** (e.g. `new IvParameterSpec({0x00, ...})`) — fire
   immediately. The brace at the start of the arg is the
   "definitely hardcoded" signal.
2. **Variable form** (e.g. `new IvParameterSpec(initializationVector)`):
   - Walk back to find the variable's declaration.
   - If the declaration is a literal array initializer
     (`byte[] iv = {0x00, ...};`) — fire.
   - If the declaration is `new byte[N]` (zeroed) AND there's NO
     `.nextBytes(iv)` call between the declaration and the
     `IvParameterSpec` — fire (likely zeroed, not random).
   - If the declaration is `new byte[N]` AND there's a
     `secureRandom.nextBytes(iv)` call — don't fire (FIX).
3. The `joinDecl` helper concatenates multi-line declarations
   (Juliet uses `byte[] iv = { 0x00, 0x00, ..., 0x00 };` across
   multiple lines).

## Known limitations

1. **Linear source walk, not function-scoped**: R28 walks the
   whole file from start to the call site looking for the
   declaration. In a real codebase with helper methods
   (e.g. `byte[] generateIV() { return new byte[16]; }`), the
   declaration wouldn't be visible at the call site. R28
   would conservatively skip these (no declaration found).
2. **No control-flow analysis**: If a function has two paths —
   one filling the IV, one not — R28 doesn't reason about
   which path is taken.
3. **BouncyCastle not supported**: Only matches
   `javax.crypto.spec.IvParameterSpec`. BouncyCastle's
   `ParametersWithIV` would be missed.
4. **Doesn't verify CBC mode**: R28 fires on any
   `IvParameterSpec` with a non-random IV, even if the cipher
   is in ECB or CTR mode. Most callers use CBC, so the FP
   rate is low in practice.

## Cross-cutting lessons

1. **Multi-line source patterns need multi-line regex or
   string-joining**: Juliet's literal array initializers span
   3-4 lines:
   ```
   byte[] iv = {
       0x00, 0x00, 0x00, 0x00,
       0x00, 0x00, 0x00, 0x00
   };
   ```
   A single-line regex `byte[] iv = {...};` doesn't match.
   R28's `joinDecl` helper concatenates from the
   declaration line until the terminating `;` so the
   pattern can match multi-line initializers.
2. **Java FQN vs short form**: Some files use
   `new javax.crypto.spec.IvParameterSpec(...)` (FQN),
   others use `new IvParameterSpec(...)` (after
   `import javax.crypto.spec.IvParameterSpec;`). The regex
   needs to accept both via `(?:javax\.crypto\.spec\.)?`.
3. **Same Juliet-template → same fix pattern**: All 17 files
   in CWE-329 use the exact same `bad()` / `good1()` /
   `good2()` template. A single-pass detector that handles
   this template is sufficient for 100% recall.
