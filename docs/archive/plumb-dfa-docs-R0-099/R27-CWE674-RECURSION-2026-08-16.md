# R27 — CWE-674 (Uncontrolled Recursion) DFA Checker

**Date**: 2026-08-16
**Round**: R27
**Status**: SHIPPED
**Effort**: ~30 min (as planned)

## Goal

Add detection for CWE-674 (Uncontrolled Recursion). Juliet's CWE-674 corpus
is small (2 files), so this is a quick win that fills a long-standing gap.

## Background

CWE-674 covers a function that calls itself without a proper base case or
depth limit, leading to stack overflow on adversarial input. Juliet's
`CWE674_Uncontrolled_Recursion/` corpus has just two files:

1. `CWE674_Uncontrolled_Recursion__long_01.java` — `helperBad(level)`
   recurses with `level - 1` until `level == 0`, but is called with
   `Long.MAX_VALUE`. The "FLAW" comment says "Although this cannot cause
   infinite recursion, it is essentially limited to Long.MAX_VALUE which
   is rather large".
2. `CWE674_Uncontrolled_Recursion__missing_base_01.java` — `helperBad(level)`
   recurses with NO base case at all.

The good variants in each file add an `if (level > RECURSION_LONG_MAX) return;`
guard (long_01) or an `if (level < 0) return 0;` base case (missing_base_01).

## Pre-R27 state

A taint-style `UncontrolledRecursionChecker` already existed in
`plumb-dfa/src/main/java/org/plumb/dfa/unified/checkers/taint/`.
But it was a CFR decompilation with a broken callee-sig comparison — it
only accepted the Jimple `#shortName` and `#shortName()` suffixes, not the
`{shortName}/{arity}` format that the Java-source TAC translator actually
emits. The R557 sweep on the Juliet CWE-674 corpus showed **0 fires**
with this checker (see `r557-recursion-loop.txt`).

## R27 ships

### New file: `Cwe674RecursionChecker.java`

A clean DfaChecker implementation in the main `checkers/` package (so
it always runs, not just when taint is enabled). Detects self-recursive
`CALL` instructions in the TAC IR by matching the callee's bare method
name + arity against the enclosing function's name + arity.

```java
public final class Cwe674RecursionChecker implements DfaChecker {
    // ...
    public void checkInstruction(TacInstruction ins, TacFunction fn, AnalysisContext ctx) {
        if (ins.kind != TacInstruction.Kind.CALL) return;
        if (ins.calleeSig == null) return;
        // ... extract short name, arity from fn ...
        // ... extract callee method name, arity from ins.calleeSig ...
        // ... compare and fire CWE-674 if self-recursion ...
    }
}
```

The check handles three callee-sig formats:

| Format | Example | Source |
|--------|---------|--------|
| Bare same-class call | `helperBad/1` | Java source static call, no scope |
| Typed scope | `IO.writeLine/1` | Java source, with scope |
| Jimple FQN | `pkg.Cls#method/1` | Jimple bytecode |

For each, we split on the last `.` or `#` to get the bare method name,
then strip the `/arity` suffix and compare against the function's short
name. Arity must also match (when known) so `foo(1)` doesn't match `foo(2)`.

For nested fns (where `fn.name()` is `Outer.helperBad`), the callee
class must end with the fn's enclosing class. For top-level fns, no
class-prefix check is applied (we don't have the enclosing class info
from the IR alone).

### Updated file: `taint/UncontrolledRecursionChecker.java`

The existing taint-style checker is fixed to use the same
`{shortName}/{arity}` matching logic. Now both the always-on DFA version
and the taint-only version fire on the Juliet CWE-674 corpus.

- `Cwe674RecursionCheckerTest.java` — 9 unit tests:

  - `doesNotFireOnNonRecursiveFunction` — only non-recursive calls

## Known limitations

1. **No base-case analysis**: R27 fires on any self-recursive call, even
   when the recursion is bounded. The good variants in Juliet's CWE-674
   corpus (`helperGood1`) are FPs by R27's structural definition.
2. **No mutual recursion**: `a() calls b() calls a()` cycles are not
   detected. A future R-round could compute call-graph SCCs.
3. **No convergence analysis**: We don't check whether the recursive
   call's arguments actually progress toward the base case
   (e.g. `foo(n-1)` vs `foo(n)`).
4. **Cross-class FPs for top-level fns**: When the calling function is
   top-level and the callee has a class prefix, we don't verify the
   class matches. This is rare in practice (most self-recursive methods
   have unique names within their package) but does happen.

## Cross-cutting lessons

1. **TAC callee sig format discovery**: The TAC IR emits three callee
   formats depending on the call site's scope (same-class static,
   typed scope, Jimple FQN). All three reduce to "method name + arity"
   comparison after stripping the right prefix. The pre-R27 taint
   checker only knew the Jimple form.
2. **`fn.name()` is just the method name (or "Outer.methodName" for
   nested classes), NOT the class + method**. The class info is
   separate (the `enclosingClass` field, not always populated for
   top-level classes).
3. **For nested fns we have class info; for top-level fns we don't**.
   So class-prefix checks are strict for nested fns and lenient
   (skip) for top-level fns.
4. **CFR-decompiled checkers can carry latent bugs from the original
   bytecode**. The pre-R27 taint checker was a CFR decompilation with
   a string-format bug that the existing test suite didn't catch (no
   unit tests for it). R27's new DFA-style checker is human-written.
