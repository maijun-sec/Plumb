## R7 vs R6 (HardCodedPasswordSinkChecker)

| Checker | Type | CWE-256 fires | CWE-259 fires | Use case |
|---------|------|--------------:|--------------:|----------|
| `HardCodedPasswordSinkChecker` (R6) | DFA (literal) | 0 | 18 | password = "7e5tc4s3" pattern |
| `DBCredentialSinkChecker` (R7) | Taint | 38 | 0 | password = `properties.getProperty("password")` |

The two are **complementary** — R6 catches literal hard-coded
passwords (CWE-259), R7 catches file/network-sourced passwords
(CWE-256). Juliet CWE-256 deliberately uses `.properties` (no
literal), so R6 is silent on CWE-256; R7 picks it up.

## R7 FP analysis (1 fire on `_81_goodG2B`)

The Juliet CWE-256 `_81_goodG2B` variant passes a *constant* password
into a helper function via:

```java
public void goodG2B() throws Throwable {
    String password;
    password = "fixed-secret-from-vault";
    ...
    passwordGoodB2G(password);
}
public void passwordGoodB2G(String password) throws Throwable {
    Connection dBConnection = DriverManager.getConnection(
        "jdbc:hsqldb:mem:test", "sa", password);  // <-- FP
}
```

The R215 framework's `initFunction` marks every parameter as
`param:<name>` (potentially tainted). The constant password is
un-tainted at the call site, but the helper sees it as `param:password`
= tainted. The R5+ cross-function summary fold is needed to
un-taint: the caller passes a constant, so the summary should
mark the parameter as not-tainted in the callee. R5+ is a known
TODO (5-day effort).

**Mitigation**: 1 FP / 37 TP = 97% precision is acceptable for
the first ship. R5+ un-taint will eliminate it. Until then, the
AI dedup agent (which already reads the dataflow trace) will
likely classify this as FP using the `param:password` source
label.
