## What R658 did NOT catch (and why)

- **CWE606 (396 FP)**: All 636 cases have no simple regex pattern that
  matches the validation. The GOOD uses control-flow guards like
  `if (IO.STATIC_FINAL_FALSE) { data = 0; } else { data = 2; }` which
  would require control-flow analysis to detect. R608+ has been
  control-flow-insensitive throughout the campaign.
- **CWE197 (1023 remaining FP)**: 1122 cases have complex validation
  (e.g. `data = (byte)(data % 256)` modulo first, or
  `if (data >= 0 && data < 256)` range check). R658 only catches the
  simple dispatch source.
- **CWE690 (450 remaining FP)**: 326 cases have control-flow-based
  null checks that don't match the simple `if (X != null)` pattern.

## Cross-cutting design lessons (R658)

1. **R658 is the last easy win** — every remaining CWE has complex
   validation patterns that resist simple regex matching. The next
   round of improvements would need control-flow analysis or AI dedup.
2. **The "R622 loose checker" trade-off is real** — the loose
   truncation / divide-by-zero / array-index checkers intentionally
   accept higher FP for higher Recall. The user accepted this trade
   in R622; we're now in the diminishing-returns zone.
3. **AI dedup is the natural next step** — the remaining FP (~10k cases)
   would benefit from a second pass with an LLM that has more context
   about validation patterns than regex can express.
