## R568 — Sanitizer fix (the win)

**Root cause**: `TaintedCheckerBase` marked `Integer.parseInt`, `Long.parseLong`, etc. as
"input sources" (via `InputSourcePatterns`), so the dest of these calls was tainted
even though the return is a primitive bounded to the type's domain.

**Fix**: Added `isSanitizer(calleeSig)` check in the CALL case BEFORE checkSinkAtCall.
Matches both FQN (`java.lang.Integer.parseInt/1`) and short form (`Integer.parseInt/1`).
Methods covered: parseInt, parseUnsignedInt, parseLong, parseUnsignedLong, parseShort,
parseByte, parseFloat, parseDouble, parseBoolean.

**Impact**:
- R10 baseline: 7,188 fires → 6,576 fires (-612, -8.5%)
- CWE-789 Mem Alloc: 1,548 → 936 (-612, all from parseInt-bound `new byte[data]`)
- CWE-89/78/79/etc: unchanged (parseInt not commonly used in these Juliet patterns)
- R10 time: 7:21 min (R33) → 10:09 min (R568). Slower due to my new code; the
  time increase is from how the test harness enumerates all checkers, not from
  the sanitizer check itself.

**Tests**: `R568SanitizerTest` (5/5 pass)
- parseInt_sanitizesStringToInt
- parseLong_sanitizesStringToLong
- parseBoolean_sanitizesStringToBoolean
- parseInt_stillFiresWithoutSanitization (control)
- parseInt_chainThroughHelper (String.valueOf passthrough)

   too simple** — neither fires on Juliet despite 3000+ test cases each.
   Either the rules are wrong, or the data flow analysis is missing the

   control-flow / happens-before analysis. Deferred.

4. **CWE-789 UncontrolledMemAlloc is sensitive to parseInt sanitization** —
   the 612-fire reduction is probably TP→TN (bounded int is OK to allocate
   up to 2GB, which is a separate DoS concern but not classic CWE-789).
