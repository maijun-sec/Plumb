## What's missing

For CWE-113 _66a, the structure is:

```java
public class CWE113_*_66a extends AbstractTestCaseServlet {
    public void bad(HttpServletRequest request, HttpServletResponse response) {
        String data = ... source ...;
        CWE113_*_66b b = new CWE113_*_66b();
        b.badSink(data, request, response);   // <-- taint should flow through here
    }
}
```

The `b.badSink(data, ...)` call should:
1. Resolve `b`'s type to `CWE113_*_66b`
2. Find `badSink` method in `_66b`
3. Trace into `_66b.badSink(String, HttpServletRequest, HttpServletResponse)` with the tainted `data`
4. Inside `_66b`, the call `response.addHeader("X-Custom", data)` should fire `bu-0112-taint-sink-header`

The sink helper `_66b` fires 20 times (across 10 sources × 2 patterns), so the trace INTO _66b works. The trace INTO _66a from a CALLER's perspective (so _66a.bad()'s body is analyzed with the caller's taint) doesn't trigger the sink finding at _66a's line.

This is the opposite direction of the CWE-78 _51b case (where _51b correctly fires when _51a's bad() calls it with tainted data). The CWE-113 case is failing because of the merged program analysis: when the merged program is built, the call to `_66a.bad()` is from the test framework's `mainFromParent(args)`, which doesn't have taint, so the taint propagation through `_66a.bad()` doesn't trigger.

Actually wait — the merged program analysis should still see the taint in the SOURCE assignment in `_66a.bad()`, then propagate through the `_66b.badSink(data, ...)` call. The finding should fire at the sink site (in _66b), not at the source. The index marks _66a as isBad=true (because it has bad()), so the firing inside _66b from _66a's call should count as a TP for _66a... but it doesn't.

This suggests the merged program correctly traces the taint, but the finding is attributed to `_66b` (the file with the sink line), not `_66a` (the entry point). The 20 `_66b` findings ARE the ones from `_66a`'s call — they're just attributed to the helper file, not the entry point.

## Cross-CWE pattern

The same pattern is observed in:
- **CWE-78** (R181): 22a fires, 53a/66a/67a/68a/71a/72a/81a don't fire
- **CWE-89** (R184): similar — many _a.java entries don't fire
- **CWE-81** (R183): 81a doesn't fire (see R183 doc)

This is a systemic issue with how the merged-program analysis attributes findings to the file containing the source line, not the file containing the entry-point method that started the call chain.

## Fix strategy

The fix would attribute findings to the ENTRY-POINT file (the file with the `bad()` method) rather than the HELPER file (the file with the sink line). This is a scoring-side change, not an analysis-side change:

1. After finding is reported at `_66b.java:42` (sink), trace the call stack to find the nearest entry-point `_66a.bad()` and attribute the finding to `_66a`.
2. If no entry-point is found (e.g. the helper is called from outside the CWE), fall back to the sink file.

This change is small (~30 lines) but requires the analysis to track the call chain through the worklist. The R183 / R188 / R189 / R190 plan is to land this fix in R190 as part of the cross-class dispatch master fix.
