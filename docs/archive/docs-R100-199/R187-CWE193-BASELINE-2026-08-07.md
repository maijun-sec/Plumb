## What the CWE-193 pattern looks like

```java
int[] intArray = new int[10];
int i = 0;

do
{
    intArray[i] = i;          // i=0..10, accesses intArray[10] (out of bounds)
    i++;
}
while (i <= intArray.length);   /* FLAW: Use <= rather than < */
```

vs the good version:
```java
while (i < intArray.length);    /* FIX: < */
```

## Why the array-bounds check doesn't fire

The current `ArrayBoundsCheck` (rule `bu-0306-array-oob`) is path-insensitive and bound-tracking. For:
- `i <= intArray.length` where `i = 0..N` and `intArray.length = 10`
- the check should reason: at the loop exit, `i` could be `N+1` (the off-by-one case), and `intArray[i]` accesses `intArray[N+1]` which is out of bounds.

But the current implementation only checks `ARRAY[index]` where `index` is a constant or a single-bin var. The loop induction variable case (where the index ranges from 0 to N) is not handled. A loop-iteration-aware analysis would be needed.

The CWE-193 fix would require:
1. Recognise the loop induction variable `i` in `for (i = 0; ...; i++)` and `while (i < N)` patterns
2. Propagate the range of `i` to the array access site
3. Compare `i`'s range to `array.length` and flag the `<=` case as off-by-one

This is a substantive new analysis (loop induction variable tracking). It's been on the R-round roadmap since R121 but hasn't been prioritised.

## Diagnostic next steps

A targeted R187 fix would:

1. Add a `LoopInductionVar` tracker in the TAC analysis (an `int i` that increments by 1 in the loop body and is bounded by `<` or `<=` in the condition).
2. At array-access sites like `intArray[i]`, check `i`'s range vs `intArray.length` and report `bu-0306-array-oob` when the range is off-by-one.

The change is medium effort (~150-200 lines) and unblocks CWE-193 + parts of CWE-121 (the CWE806/805/193 family has a similar loop pattern). The current recall is 0% so any improvement is high-ROI.
