## Why printf never fires

The TaintCatalog has the right patterns:
- `**.PrintStream.printf/*`
- `**.PrintWriter.printf/*`

But the `System.out.printf(...)` call site TAC is probably emitted differently than expected. The Plumb TAC for a static field call like `System.out.printf(...)` would be:
- `out` is a static field of `System` (TacOperand.FieldLoad with the type `PrintStream`)
- `out.printf(fmt, args)` is a CALL on the FieldLoad result

The `transferInvokeImpl` may not correctly match `**.PrintStream.printf/*` against this pattern because the receiver is a FieldLoad (not a plain TacVar), or the call sig doesn't include the receiver type prefix.

## Why format string findings miss the entry points

Same pattern as R183 / R188: for cross-class 22/53/66/67/68/71/72/81 patterns, the entry points (`_a.java`) don't fire. The helpers (`_b.java`) fire instead. The 141 TP from R182 is biased toward the helper files.

## Two-part fix

1. **printf receiver type fix**: the FieldLoad receiver for `System.out` should resolve to `PrintStream`. This is a TAC type-inference fix (~10 lines).
2. **Cross-class entry-point attribution** (R188's fix): move the finding from the helper file to the entry-point file (~30 lines).

Combined, the expected R189 + R188 fix could push CWE-134 from 20.6% to ~50% (300+ TP from 141).
