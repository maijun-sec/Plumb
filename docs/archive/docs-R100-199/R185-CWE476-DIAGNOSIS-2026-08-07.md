## What the 476 pattern looks like

CWE-476 has many sub-patterns. The most common are:

| Sub-pattern | Shape | Sink |
|-------------|-------|------|
| `binary_if_01` | `if ((myString != null) & (myString.length() > 0))` — single `&` short-circuit missing | `myString.length()` NPD |
| `binary_if_02` | `if ((myString == null) | (myString.length() > 0))` — single `|` short-circuit missing | same |
| `Integer_*` | `if (data != null & data.intValue() > 0)` | `data.intValue()` NPD |
| `deref_*` | `data.foo()` after `data = null;` | NPD on deref |
| `return_*(...)` | `return data.toString()` where `data = null` | NPD in return |
| `loop_*` | `while (data.foo() > 0) { ... }` | NPD in loop condition |

The bad() body typically:
1. Declares a variable to `null`
2. Optionally has a null check via `&` (single, not `&&`) so both sides evaluate
3. Calls a method on the null variable → NPD

The good() body uses `&&` so the second part is short-circuited.

## Why the 198 files don't fire

The current `NullDerefChecker` likely uses a simple "is the variable null at the deref site?" check. For:

```java
String myString = null;
if ((myString != null) & (myString.length() > 0))  // line N
```

The variable `myString` IS null at the assignment. The `if` check uses single `&`, so the right side `myString.length() > 0` IS evaluated. The current checker should fire on `myString.length()`.

But only 4 files fire. The likely root causes:

1. **Path-condition unaware**: The check doesn't know that the `&` (vs `&&`) means both sides evaluate. The current null-deref analysis sees the `if (myString != null) & ...` as a conditional that doesn't affect the path.
2. **Type inference gap**: `myString` is declared as `String` (not a custom type), but the checker may not properly handle the `null` literal in the `String myString = null` assignment.
3. **Method-call-as-source-of-null**: Some 476 patterns have `data = someMethod()` that returns null. The checker needs to track the null source through the call.

## Diagnostic next steps

A targeted R185 fix would:

1. Add a path-condition-aware null-deref check: when the deref is in a condition like `if (x != null) & (x.foo() > 0)`, recognize that the right side is in a "both sides evaluated" path.
2. Add a literal-`null` initialiser detection: `String x = null;` should immediately mark `x` as null in the abstract state.
3. Run CWE-476 to see which sub-patterns fire (binary_if, Integer, return, etc).

## Action

Defer R185 to a future round. The CWE-476 fix needs a substantive check rewrite (not a one-liner). Move to R186 (CWE-252 unchecked return) which has a smaller surface area.
