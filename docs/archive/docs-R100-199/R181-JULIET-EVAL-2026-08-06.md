## R181 — Engine changes

Two narrow fixes in `plumb-dfa/.../TaintAnalysis.java`:

### Fix #1 — Worklist bug in `doWorklist`

The pre-R181 loop was:

```java
outFact.put(bid, out);
for (final int s : cfg.succs(bid)) {
    final TaintFact newIn = (s == cfg.entryId()) ? out : inFact.getOrDefault(s, TaintFact.bottom()).union(out);
    if (worklist.contains(s)) continue;        // <-- BUG
    if (!newIn.equals(inFact.get(s))) {
        inFact.put(s, newIn);
        worklist.add(s);
    }
}
```

When the successor was already in the worklist, the early `continue` **also skipped** the
`inFact.put(s, newIn)` line. That meant the join-point BB never received the union of all
incoming paths; only the first one to be enqueued won. The fix is to always update
`inFact` first, and skip the redundant push:

```java
if (!newIn.equals(inFact.get(s))) {
    inFact.put(s, newIn);
    if (!worklist.contains(s)) {
        worklist.add(s);
    }
}
```

### Fix #2 — `MOVE dest = null` was erasing pre-existing taint

Juliet's switch-case flow variants (`_15`, `_21`, `_66a`, `_67a`, etc.) include a
default-branch `data = null;` that the Juliet test framework inserts as CWE-561
incidental dead code. After the worklist fix correctly unions the case-6 path's
tainted `data` into the join-point BB, the in-BB `data = null` on the second pass
re-erased it: `in.with(dest, in.taintOf(null))` returned an empty set, and
`with(emptySet)` is implemented as `remove(dest)`. The fix special-cases a null
literal write:

```java
if (ins.lhs1 instanceof TacOperand.Const && ((TacOperand.Const) ins.lhs1).value() == null) {
    next = in;            // keep the pre-existing dest taint
} else {
    next = in.with(ins.dest, lhsTaint);
}
```

The over-approx (keeping taint on a real `dest = null` write) is sound: real code rarely
writes a `null` literal as a deliberate taint eraser (the only common idiom is
`if (x != null) { use(x) }` which doesn't need MOVE tainting to work). The dead-code
case in Juliet is exactly the situation where the over-approx is correct.

## What R181 unblocked

The root cause was a classic flow-sensitive but path-insensitive worklist bug. After
the fix, any Juliet flow variant where the `bad()` body has:

1. A `switch(n)` / `if-else if` chain with a data-flow-relevant case
2. Plus a default branch that does `data = null;` (CWE-561 dead code Juliet inserts)

now correctly produces a finding. The 2 remaining `_*_15.java` FNs per CWE are the
ones where the `switch` value comes from a method that returns a constant not visible
to the taint analysis (e.g. `return CONST_RETURN;` not propagated). Those need
R91-style constant propagation through method returns, which is on the R184 roadmap.

## Lessons

1. **The pre-R181 worklist bug was masked by the CWE-78 _01 flow**: the most-tested
   single-variant always fires the case 1 path first, so the early `continue` was
   always hit on a different path than the one that mattered. The bug only surfaces on
   flow variants where the *default* branch dominates first (e.g. `_15`).
2. **Over-approx is correct for incidental null writes**: real code rarely writes
   `data = null;` to deliberately erase taint. When it does (defensive `data = null;`
   after a sink to prevent double-reporting), the over-approx costs us a single FP per
   case. Juliet has zero such cases, so the over-approx is a clean win.
3. **Strict per-CWE scoring is essential**: the previous eval (r180c) scored a wider
   rule set and conflated cross-rule OGNL FPs with the CWE-specific TPs. The new
   scorer (`score_r181.cjs`) filters to exactly one `rule_id` per CWE and is
   reproducible across rounds. Re-scoring r180c with the new strict scorer showed the
   baseline was actually 36.8% (vs the 67.4% reported in R180c which was method-range
   based, not isBad-index based).
