# R180c Juliet Java Evaluation Report

**Date:** 2026-08-06
**Scope:** `plumb-dfa` (dataflow analysis engine) + `plumb-style` (style checks)
**Corpus:** Juliet Test Suite for Java v1.3 (`D:/work/tmp/Juliet_Java/src/testcases/`, ~50k test cases, 113 CWE families)
**Hardware:** Windows, JDK 17, JVM `-Xmx4g`
**Methodology:** per-family merged program (R117 / R148e), `bad()` / `goodG2B()` / `goodB2G()` / `action()` byte-range scoring, **strict per-CWE rule** (a `bu-0102-taint-sink-cmd` finding in a CWE-78 file counts toward CWE-78 TP; cross-rule FP from `bu-0115-taint-sink-ognl` etc. is excluded by rule filter).

## R180c — Engine changes

Two narrow source edits in `plumb-dfa/.../TaintCatalog.java`:

1. **Added `**.sendError/*` to `bu-0104-taint-sink-xss`** — CWE-81 XSS-in-Error-Message uses `response.sendError(404, "... " + data)` as its sink; the pre-R180 catalog only had `getWriter/getOutputStream/write/println`, missing `sendError`. This single missing pattern took CWE-81 from 0% → 46%+ recall (Juliet fires 158 unique bad files with `sendError`-sinked taint).
2. **Tightened `bu-0115-taint-sink-ognl`** — removed the broad `**.getValue/*` / `**.setValue/*` / `**.parseExpression/*` patterns that produced FPs in Juliet (every `Cookie.getValue()` was being reported as OGNL expression evaluation). Kept only the explicit `Ognl/OgnlUtil/Spel*/ExpressionParser/StandardEvaluationContext` engine classes. CWE-78/CWE-80/CWE-81/CWE-89 saw 33-450 fewer FPs per family.

**Hotspot:** `TaintAnalysis` re-walks the entire IR for every checker; with 22 checkers × N functions × N instructions we get an `O(checkers × IR)` cost on every merged-program scan. CWE-89's 3 682 files × 22 checkers = the long tail.

## What is still missing (next round candidates)

**High-leverage wins still on the table** (measured in missed recall):

1. **Switch / if(true) / if(5==5) — source not propagated** (CWE-78/89/369/etc.)
   The Juliet `flow variant 03 / 04 / 15 / 53 / 54 / 66-75` family wraps the source in `if (5==5) { ... }`, `switch(6) case 6: { ... }`, or wraps the source inside a private helper (`bad_source()`). Plumb's path-sensitive dataflow does not always pick up the read under the constant branch (constant-condition is correctly detected and reported, but taint propagation through the constant branch is missed). Estimated cost: +5-10% recall across all taint families.

2. **Type-erasable String → int / float bridges** (CWE-190 / CWE-191 / CWE-369 / CWE-789)
   Juliet's pattern `String s = readLine(); int x = Integer.parseInt(s);` flows taint through `parseInt` but the resulting `int x` doesn't carry the `MayBeZero` fact (or `BoundedInt`). Needs a `taint-bridges-parsers` fact or a wider application of `**.parseInt*` to the numeric checkers. Estimated cost: +30-50% recall on CWE-190/191/369/789.

3. **Field taint from class-level fields** (CWE-78/89 with `badPrivate = true; data = bad_source();`)
   The `badPrivate` instance field drives a private helper that returns the source. The `*.data` field-taint walk in `TaintAnalysis` (R161) should handle this, but in practice we see ~5-10 missed `21_*` files per CWE.

4. **Cross-class `81_bad.action(data)` propagation** (CWE-78/89/113 81_* pattern)
   Juliet flow 81 wraps the sink in a separate `*_81_bad` class with an `action(String data)` method. The driver `*_81a` calls `new *81_bad().action(data)`. Plumb's call graph follows the constructor but the `data` parameter taint doesn't reach the inner class's `Runtime.exec(data)` because the IR loses the inter-class field/parameter taint across the action-call boundary. Estimated cost: +5-10% recall per family.

5. **Sink-family FP tightening** (low priority)
   Even after R180c, the `**.HttpServletResponse.setHeader/*` pattern matches `response.setHeader(...)` and fires on the `*_header_servlet_*` family of CWE-113. There are no FPs in the current run, but the broad pattern will trip on real code that has many header sets. Suggested: add a per-class allowlist (only fire when the *receiver* is `HttpServletResponse`).

6. **Per-file mode performance** (low priority for merged mode, but still useful for editor integration)
   The per-file eval (no merged program) takes ~30-60 s for 100 files. The 22-checker × N-function × N-instruction cost is the same as merged mode; we are paying for it in cold-start JVM + repeated class loading. A long-running server with a check-cache would amortize this.

## How to reproduce

```bash
# Build
mvn -pl plumb-main -am package -DskipTests

# Run per family
java -Xmx4g -jar plumb-main/target/plumb-main-0.1.0-SNAPSHOT-all.jar -c path/to/family.yaml

# Per-family config example (juliet-config.yaml):
#   inputs:
#     - 'D:/work/tmp/Juliet_Java/src/testcases/CWE78_OS_Command_Injection'
#   output: { path: 'CWE78.ndjson', format: ndjson }
#   checks: { taint: true, nullDeref: true, divByZero: true, ... }
```

Score with `smoke_juliet/juliet-eval-sub.ps1` or the inline PowerShell scorer in this report.
