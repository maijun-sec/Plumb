# TAC 存储：三个可以分开运行的阶段

[English](../../tech/TAC-STORE.md) | [中文](../README.md)

本文描述 TAC 存储：中间表示在磁盘上的形式。它让一次扫描的三个阶段 —— 捕获命令、生成 TAC、分析 TAC ——
可以在不同的时间、不同的地点、不同的机器上分别运行。

## 1. 为什么把阶段拆开

一次扫描有三类工作，它们的代价不同、生命周期不同：

| 阶段 | 做什么 | 需要什么 | 产出什么 |
| --- | --- | --- | --- |
| 1. 捕获 | 记录编译器的调用 | 构建本身 | 每个编译单元一条捕获记录 |
| 2. 生成 | 把捕获记录变成 TAC | 源码与 classpath | 一个 TAC 存储 |
| 3. 分析 | 在 TAC 上跑数据流引擎 | TAC 存储 | 结论 |

拆开带来三样东西。

**构建不必重做。** 阶段 2 读的是捕获文件，不是构建日志，因此不需要重跑编译器。同一份捕获文件可以
针对不同的分析反复生成。

**分析不需要源码。** 阶段 3 读 TAC 存储，全程不打开源码文件。存储可以拷到另一台机器 —— 构建代理、
CI runner —— 上在那里分析。正是这个性质让拆分值得多出一个文件格式：分析的输入是**数据**，不是源码树。

**三个阶段各自独立地失败。** 一条无法重新生成的捕获记录是阶段 2 的问题，不会妨碍阶段 3 分析它已经
拥有的部分。

## 2. 捕获阶段

捕获阶段记录编译器被要求做什么。`plumb-build-capture` 为每个编译单元产出一条 `CaptureEntry`，
导出步骤把一组捕获记录转成编译数据库。

### 2.1 编译数据库格式

导出结果是 JSON **数组**。每个元素恰好三个键：

```json
[
  {
    "directory": "D:/work/project/src/main/java",
    "arguments": ["javac", "-cp", "lib/a.jar", "Main.java"],
    "file": "D:/work/project/src/main/java/Main.java"
  }
]
```

| 键 | 装什么 | 如何归一化 |
| --- | --- | --- |
| `directory` | 该次编译的工作目录 | 分隔符变 `/`；保留盘符；保留大小写 |
| `arguments` | 编译器的参数向量 | **原样保留** —— 反斜杠不动 |
| `file` | 该条目描述的源文件 | 分隔符变 `/`；保留盘符 |

`arguments` 与两个路径字段之间的不对称是刻意的。`arguments` 是编译器**实际收到**的东西：把一个
反斜杠改成正斜杠就改变了命令，而 Windows 上的编译器两者都接受，Linux 上的编译器只接受一个。
`directory` 与 `file` 是消费方要解析的东西，消费方要拿它们去对文件系统解析，因此归一化成一种写法。

### 2.2 路径归一化规则

| 规则 | 效果 |
| --- | --- |
| 分隔符 | 每个 `\` 变成 `/` |
| 盘符 | `D:\x` 变成 `D:/x` —— 字母与冒号保留 |
| 大小写 | 不变 —— 路径的大小写不是产出方该决定的事 |
| 绝对路径 | 越过根的 `..` 被丢弃：`D:/a/../../b` 变成 `D:/b` |
| 相对路径 | `..` 保留：`a/../b` 仍是 `a/../b` |

最后两条规则故意不同。绝对路径有根，所以要爬到根之上的 `..` 没有意义，直接丢弃。相对路径没有根可以
爬越，它的 `..` 是有意义的，保留。

### 2.3 格式是怎么验证的

格式是对照一份参考实现来验证的，而不是对照一份记录下来的输出。参考实现从源码编译成一个探针程序，
两个实现拿到相同的输入，输出逐字节比较。

这一点很重要：黄金文件记录的是**一个**答案，而比较提出的是**一个问题** —— 两个实现在每一个输入上
是否一致，包括那些别扭的输入？探针的输入包含控制字符、非 ASCII 字符、盘符和父目录引用 —— 正是这些
情况下归一化规则最容易出错，而一份黄金文件会欣然把那个错误记录成正确。

探针的输入以转义的 wire 形式给出（`\n`、`\t`、`\uXXXX`），因为「每行一个用例」无法表达含换行的字符串。

## 3. 生成阶段

生成阶段读捕获记录，产出 TAC 存储。

### 3.1 从捕获记录到模块

每条捕获记录变成一个编译模块。这个映射是机械的：

| 来自捕获记录 | 到模块 |
| --- | --- |
| 编译器的语言 | 解析它的前端 |
| 源文件 | 模块的源文件列表 |
| classpath | 模块的 classpath |
| 源根 | 源码位于其下时，作为模块的源根 |

Java、Kotlin、Scala、C# 各有自己的前端，捕获记录里的语言决定选哪个。各前端的形态统一：
`parse(source, path, context)`。

### 3.2 存储的形状

存储是一个 SQLite 数据库。这个选择与查询语言无关 —— IR 上并没有查询 —— 它关乎的是**文件格式**：

| 需求 | 一个 SQLite 文件 | 每个程序一个文件 | 一个目录若干文件 |
| --- | --- | --- | --- |
| 是一件可拷贝的产物 | 是 | 否 | 否 |
| 构建运行中可更新 | 是 | 别扭 | 别扭 |
| 经得住写到一半 | 是（事务） | 否 | 否 |
| 不启动引擎也能查看 | 是 | 部分 | 部分 |

IR 本身是一棵多态对象树，按列存意味着每种节点一种 schema，字段一变就要迁移。存储把 IR 作为
**blob** 保留，让既有的序列化器定义它的形状：

```
┌──────────────┬──────────────┬─────────────────┐
│   MAGIC      │   VERSION    │   <Object>      │
│ 0x504C554D   │ 0x00000001   │ Java serialized  │
│  (4 bytes)    │  (4 bytes)    │ (any IR object) │
└──────────────┴──────────────┴─────────────────┘
```

头部与基于文件的缓存用的是同一个，所以一个 blob 与一个 `.tac` 文件是同一串字节。存储里的内容可以
取出来交给文件读取器读，文件也可以装进存储。

### 3.3 表

| 表 | 键 | 装什么 |
| --- | --- | --- |
| `programs` | `cache_key` | 每个源文件一个 `TacProgram` |
| `merged` | -- | 分析消费的合并程序 |
| `manifest` | key | 生成该存储时的元信息 |

缓存键按程序**由什么生成**来标识它 —— 源路径与内容 —— 因此一次产出相同程序的重建会替换旧的那份，
而不是一份份堆积。

## 4. 分析阶段

分析阶段读存储并报出结论。它不打开源码文件。

### 4.1 路径重映射

存储记录的是构建时看到的路径。分析可能跑在一台文件系统布局不同的机器上：构建代理的工作区不是
审阅者的检出目录。

因此路径在**加载时**重映射，而 **IR 不被修改**。IR 里的路径是存储的身份 —— 它是缓存键的一部分，
若改写路径，两个仅仅构建位置不同的存储就无法区分。重映射发生在打开存储之后、分析开始之前。

一个映射是一对根：

```
<producerRoot>=<consumerRoot>
```

producer 根下的路径被重新表述为 consumer 根下的路径。不在任何 producer 根内的路径保持原样。

### 4.2 这个阶段刻意不做的事

分析阶段不读源码树。一个依赖源码的步骤 —— 比如打开声明文件来解析静态字段的值 —— 会让答案取决于
机器上恰好有什么，同一个存储就会在两台机器上给出不同结论。

引擎自身的跨函数机制已经带着跨函数边界所需的信息，所以这个限制没有损失什么。

## 5. 运行各阶段

这些阶段是子命令。既有的扁平命令行不变：第一个参数不是子命令时走扁平命令行的路径。

| 子命令 | 阶段 | 读 | 写 |
| --- | --- | --- | --- |
| `capture` | 1 | 捕获记录 | 编译数据库 |
| `build` | 2 | 捕获记录 | TAC 存储 |
| `analyze` | 3 | TAC 存储 | 结论 |

| 子命令 | 选项 |
| --- | --- |
| `capture` | `--capture-dir <dir>`、`--output <file>` |
| `build` | `--capture-dir <dir>`、`--output-dir <dir>` |
| `analyze` | `--store <file>`、`--output <file>`、`--source-path-map <producer>=<consumer>` |

不给 `--output` 时，`capture` 把编译数据库写到标准输出，`analyze` 把报告写到标准输出。

### 5.1 `analyze` 与路径重映射

```
plumb analyze --store <store> [--output <file>] [--source-path-map <producer>=<consumer>]
```

重映射选项接受一对 `producer=consumer`，而且可以给多次 —— 每次出现增加一对。

### 5.2 跨机器的一次往返

拆分的意义在于存储是可搬运的。顺序是：

1. 在构建机器上：`capture` 捕获这次编译，然后 `build` 生成 TAC。
2. 把存储拷到分析机器。
3. 在分析机器上：`analyze` 存储；两台机器路径布局不同时加上 `--source-path-map`。

第三步不需要源码树，也不需要编译器。

## 6. 保证的形状

三个阶段是分开的，但并不彼此独立：存储的内容正是生成阶段产出的东西，分析报出的正是存储里有的东西。

这正是路径重映射属于加载期事务的原因。若 IR 里带着 consumer 的路径，存储就不再是「构建出了什么」的
忠实记录，一条结论就会指向构建时从未存在过的位置。

`TacPipelineTest` 里的端到端测试走完整个序列 —— 捕获、生成、存储、删除源码、分析 —— 并断言结论
指向 consumer 的路径而非 producer 的。**删除源码**正是让这个测试有意义的地方：任何一步悄悄回头去读
源码树，测试都会失败。
