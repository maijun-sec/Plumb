# Plumb 中的 PHP：sidecar 路线、参考 PHP 解析器，以及 TAC 如何生成

[English](../../tech/PHP-FRONTEND-ANALYSIS.md) | [中文](../README.md)

## 0. 先说结论

Plumb 能读 PHP。路线是一个 PHP sidecar，它驱动参考 PHP 解析器的 JavaScript
移植版；它产出的 TAC 就是那个 TAC：同样的指令、同样的调用约定、同样的 keyed
命名空间——JavaScript、TypeScript 和 Python 前端用的就是这一套。

| 问题 | 答案 |
|---|---|
| 用哪个解析器 | 参考 PHP 解析器的 JavaScript 移植版，由 Node 运行时驱动 |
| 跑在哪里 | 一个 Node 进程，走 stdio，一个请求一帧 |
| 读哪些文件 | `.php` |
| 产出什么 | IR 里的 `TacFunction`，并带上这个文件的问题清单 |
| 还不产出什么 | findings：PHP 的 sink 目录和语义表是规则层的工作 |

最后一行是诚实的那一行。前端把 PHP 正确地降级成 TAC；能不能出 finding，取决于
那些匹配降级后调用的规则，而 PHP 的规则还不存在。

## 1. JVM 够不到 PHP 的解析器

### 1.1 解析器是一个程序，不是一个库

PHP 的文法由参考解析器决定：它决定 `match` 能不能解析、heredoc 的值到哪里
结束、一个名字是函数还是类。

在 JVM 里重写那份文法，就是第二份实现，而第二份会和第一份在"一个文件是什么
意思"上产生分歧。关于名字的分歧会产生不同的 callee 签名，而 callee 签名正是
sink 目录所匹配的东西。

### 1.2 路线：一个 PHP sidecar

所以分析跑在一个 sidecar 里，由它驱动那个解析器，走长度前缀的 JSON 分帧，
每个响应都带一次版本握手。Java 侧把线上格式映射进 IR；IR 就是那个 IR，引擎并
不知道它是哪种语言产出的。

### 1.3 为什么这个解析器是 JavaScript 移植版

参考解析器是一个 PHP 程序，而 Plumb 跑的那些机器上并没有装 PHP。这个 sidecar
用的解析器是它**到 JavaScript 的移植版**，而它的 AST 就是参考 AST——所以规则所
对着写的节点形状，正是 PHP 社区写规则时对着写的那些形状。

所以这个 sidecar 是一个 Node 程序，和 TypeScript、ArkTS 那两个一样。它需要
Node 和它那一个 npm 依赖，别的不需要：没有 PHP 运行时要装，也没有 Composer 要
跑。

### 1.4 为什么解析器自己读文件

解析器从磁盘读源码。它必须这样：调用方递进来的文本未必是磁盘上的文本，而一
个文本被换掉的文件是**另一个程序**。所以调用方递进来的文本会跟磁盘上的文本
比对，而差异是**报出来的**：分析用的是磁盘上的那个文件，而把这件事说出来，
正是"已知的下界"和"意外的沉默"之间的区别。

## 2. PHP 会把 TAC 的什么打破

### 2.1 对象是命名空间，不是记录

在 PHP 里 `$o->name` 和 `$o['name']` 是同一个位置，`$items[0]` 就是
`$items["0"]`。所以属性访问被降级成带字符串键的容器访问——一个 `ARRAYLOAD`
或一个 `ARRAYSTORE`，它的下标操作数就是那个键——而不是字段访问。字段指的是字
段，而属性不是字段。

**赋值是一次写，而这次写必须到达 store。** 属性赋值是一个 `ARRAYSTORE`，键就
是属性名，这样后面再读同一个属性时才能读到刚写进去的值。

### 2.2 接收者槽位是保留的

TAC 的调用约定把 `args[0]` 留给接收者，真正的参数从 `args[1]` 开始。这个槽位
是有调用就保留、没有调用也保留：自由函数没有接收者，于是槽位里放的是**命名
空间**名的常量。

### 2.3 callee 签名就是 PHP 写出来的那个名字

PHP 的 callee 是按 PHP 的方式命名的，签名带着那个名字加上 arity：

| 源码 | 签名 |
|---|---|
| 全局命名空间里的 `system($cmd)` | `\system/1` |
| `namespace App\Services;` 里的 `system($cmd)` | `\system/1` |
| `namespace App\Services;` 里、且在那里声明的 `helper($x)` | `App\Services\helper/1` |
| `Mailer::send($to)` | `App\Services\Mailer::send/2` |
| `$mailer->send($to)` | `App\Services\Mailer::send/2` |

**为什么用 PHP 的名字，而不是一个 Java 形状的名字。** sink 目录匹配的是 callee
签名，而一条关于 PHP 代码的规则就该用 PHP 的写法来写。一个写着 `\system` 的
pattern 匹配 `\system/1`；一个写着 `App\Services\Mailer::send` 的 pattern 匹
配那个方法。

**命名空间的规则就是 PHP 自己的规则。** 不带限定的**函数**调用先在当前命名
空间里找，只有当前命名空间没有声明它时才回退到全局命名空间——所以命名空间里
的 `system($cmd)` 就是全局那个 `system`，因为这个命名空间没有声明它。不带限
定的**类**名**没有**全局回退：`namespace App\Services;` 里的 `new Logger()`
就是 `App\Services\Logger`，没有别的可能。`use` 语句把一个别名绑到一个限定名
上，而 `use function` 绑的是函数、普通的 `use` 绑的是类；两者各自独立地解析。

**声明是在文件被降级之前读到的。** 当前命名空间有没有声明某个名字，是关于这个
文件的事实；而一个出现在它所调用的声明**之前**的调用，照样要带上那个声明的
arity。所以先读文件的声明，再降级文件。

文件声明过的函数的调用是 `CALL`；其余一切是 `UNINTERPRETED`：一个引擎看不
见内部的黑盒。两者都会被 sink 目录查到，所以像 `system` 这样的 PHP sink 怎么
样都匹配得上。

### 2.4 arity 数的是声明出来的参数

文件声明的函数贡献它声明的参数，接收者不在其中：一个带一个参数的方法是
`App\Services\Mailer::send/1`，接收者在 `args[0]`。可选参数也是参数：被调方
给它留了槽位，不管调用方填不填。

来自别处的函数贡献这次调用传了几个参数。PHP 没有静态类型，所以外部函数的声明
参数在这里看不见。

### 2.5 PHP 会去执行的那些命令

**反引号字符串**是一条命令：PHP 会把它交给 shell 跑。所以它被降级成一次对
shell 替身的调用，而不是一个普通字符串——这样这条命令才以调用的形式可见。

| 构造 | 签名 |
|---|---|
| `` `ls $x` `` | `<php>.shell/1` |
| `include 'f.php'` | `<php>.include/1` |
| `foreach` 里集合的长度 | `<php>.count/1` |

那个 owner 不是真的命名空间：一份写着 `system/1` 的 sink 目录不该碰巧匹配上
`<php>.shell/1`。

### 2.6 哪些没有被建模，以及怎么报

下面每一条都会作为问题报在那个函数上，受影响的值变成未知值。绝不静默省略。

| 构造 | 会发生什么 |
|---|---|
| 被当作值用的闭包或箭头函数 | 报为 `SOURCE_LOWERED`；值变成未知 |
| 生成器（`yield`） | 报为 `UNHANDLED_NODE`；值变成未知 |
| `switch` | 报为 `SOURCE_LOWERED`：PHP 比较它的 subject 是宽松比较，而 TAC 不是 |
| 对带字符串键的数组做 `foreach` | 报为 `SOURCE_LOWERED`：键变量里装的是位置 |
| 接收者类型推不出来的方法调用 | 报为 `SOURCE_LOWERED`：owner 退回代码所在的那个类 |
| callee 不是名字的调用 | 报为 `UNHANDLED_NODE`；这次调用是黑盒 |
| `goto` | 报为 `UNHANDLED_NODE` |
| 其他任何语句或表达式 | 报为 `UNHANDLED_NODE`；值变成未知 |

有一处差别**不**报，因为这个差别改变不了分析能看到的东西：PHP 的 `==` 会先
做类型转换再比较，而 TAC 的相等测试就按值的样子比较。这个差别不改变污点怎么
流动。

**同一个问题只报一次，带上次数。** 一个文件里有五十个 switch，那么是一条说
"发生了五十次"的问题，而不是五十条问题。

## 3. 是工程，不是文件

### 3.1 文件的模块名就是它的路径

文件的模块名是它在工程根目录下的路径，用 PHP 自己的命名空间分隔符连起来。模块
名是文件顶层代码的 owner，所以根目录决定了 callee 签名长什么样。

### 3.2 工程的边界在哪里

边界是编译上下文的模块根目录（当文件属于某个模块时），否则是最近的、带有工
程标记的祖先目录。

| 标记 | 含义 |
|---|---|
| `composer.json` | 工具链自己的清单：一个工程 |

刻意**不**当标记的是"一个装着 PHP 文件的目录"：PHP 没有哪个配置文件会说"这个
目录是一个工程"，而自己编一个会让边界变成猜测。

### 3.3 哪些被排除在外，以及为什么

`vendor` 目录里是 Composer 装下来的依赖，`node_modules` 里是前端构建的依赖，
构建输出里是生成的代码，而名字以点开头的目录是工具自己的状态。

## 4. PHP 的 TAC：五步

### 4.1 打开工程

Java 侧把工程的文件和它们所在的根目录发过去。sidecar 把两者记下来，之后每
个文件都带着那个根目录去翻译。

### 4.2 翻译

Java 侧点名要一个文件。sidecar 从磁盘读它的文本，然后降级。

### 4.3 降级

文件顶层的代码变成一个合成函数；函数变成函数；类的类体变成一个合成函数，它的
方法各自变成函数；属性读和属性写变成带字符串键的容器访问；二元运算符变成一个
`BINOP`。

### 4.4 讲线格式

函数以长度前缀的 JSON 传递。每个响应都带协议版本和 IR 版本，失败的那些也一
样。

### 4.5 报出每一处降级

降不下来的构造会成为那个函数上的一个问题，函数的精度降到 `SOURCE_LOWERED`。
一个没解析成功的文件会变成一次失败响应，Java 侧把它变成一个问题：一个不是
PHP 的文件不是"不完整的 PHP 文件"，它是另一个程序。

## 5. 让两半互相校验的交叉检查

Java 侧对着一个说同样协议的替身 sidecar 做测试，所以分帧、握手和线上到 IR 的
映射在任何能跑测试的机器上都被钉住了。PHP 侧由一个烟雾测试来测：它把真正的
sidecar 当进程启动，检查从线上回来的 TAC。端到端测试则用真正的前端去驱动真正
的解析器。

两半都被有意改坏过，用来检查另一半会不会发现：

- 属性读被改成字段读——测试会变红，**但只有在测试源码里本身就有一次属性访问
  之后才会**。只用下标形式的源码在属性读被改坏时依然会通过，因为下标自己那次
  容器访问把断言满足了；
- 接收者槽位被挪到参数列表末尾——测试会变红；
- 命名空间限定被丢掉——测试会变红，因为签名不再是 PHP 给出的那个名字；
- 短条件式的真值分支被换成占位值——测试会变红，因为随测试进来的污点被扔掉了；
- `match` 的"没有 arm 匹配"那条路径被排到 arm 之后——测试会变红，因为那条
  路径会跑去执行第一个 arm 的体，而 PHP 在那里是抛异常的。

## 6. 本文不主张什么

| 主张 | 状态 |
|---|---|
| PHP 源码被降级进 TAC | 成立，并且是对着真正的解析器测过的 |
| 降级能找出每一条污点流 | 不主张：分析是过程内的，一个方法里写的属性，另一个方法看不到 |
| PHP 会产出 finding | 还不会：PHP 的 sink 目录和语义表都不存在 |
| callee 的 owner 一定对 | 不主张：接收者类型推不出来时，owner 退回代码所在的那个类，并且这一点会被报出来 |
| 会检查 PHP 的版本 | 不主张：解析器是一个固定的 npm 依赖，没有哪个运行时的版本会漂移 |
