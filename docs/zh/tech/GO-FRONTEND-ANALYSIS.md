# Plumb 中的 Go：sidecar 路线、捕获契约，以及 TAC 如何生成

[English](../../tech/GO-FRONTEND-ANALYSIS.md) | [中文](../README.md)

本文按顺序回答四个问题：

1. **一个跑在 JVM 上的引擎，到底能不能分析 Go？** 这个答案决定路线，而且它不是一个
   偏好问题。
2. **Go 会把 TAC 的什么打破？** 有四个构造在现有 IR 里没有归宿。其中三个由决策关闭，
   第四个靠接受一个更粗的类型系统关闭。
3. **构建捕获必须供出什么？** Go 的构建会产生两类不同的命令，而其中只有一类说明了
   二进制里到底有什么。
4. **一份 Go 的 TAC 是怎么端到端产生的？**

路线与 C# 已经用的那条相同：一个原生进程，讲一套带帧的 JSON 协议，由 JVM 读回来。
变化只在于 Go 侧的 sidecar 必须是**一个 Go 程序**——因为 Go 的类型解析器就是一个 Go
程序。

标注 **[MEASURED]** 的部分是从本仓库的代码里读出来的，或是对着本仓库实测的。描述 Go
工具链行为的部分标注 **[TOOLCHAIN]**，它们是关于工具链的已文档化行为的陈述，而不是关于
Plumb 的。

---

## 0. 先说结论

| 问题 | 答案 |
| --- | --- |
| JVM 能分析 Go 吗？ | **不能直接分析，而且这个缺口补不上。** 解析一个 Go 的类型意味着运行 `go/types`，而它是 Go 标准库里的 Go 源码。它没有 JVM 移植版。一个解析不出类型的 JVM 前端产不出被调用者签名，而被调用者签名正是 sink 目录匹配的东西。 |
| 路线是什么？ | **一个原生 Go sidecar**，用 C# sidecar 已经在讲的那套长度前缀 JSON 协议，把同样一份 Java 序列化的 IR 喂给同一个引擎。 |
| TAC 的 IR 契约要改吗？ | **不改。** IR 契约零改动：没有新 opcode，没有新类型种类，`RETURN` 不变，被调用者键契约不变。Go 是第一个**不用动 IR** 就接进引擎的语言，而这是决策的结果，不是运气。 |
| 捕获要交出什么？ | 每个包的编译命令**以及**链接命令。链接命令的 import 配置才是"二进制里到底有哪些包"的权威说法；编译命令说的是每个包是对着什么编译的。 |
| 真正的成本是什么？ | **sink 目录。** `sink-families.yaml` 有 82 个 family，其中 38 个按语言限定，而**没有一个**限定到 Go。Go 不共享 JVM 的标准库，所以 Go 的目录是一份新的工作量，不是一次移植。 |

最后一行决定了 Go 到底能不能出 finding，而它与 C# 目录是同一个形状的问题
（[CSHARP-FRONTEND-ANALYSIS.md](CSHARP-FRONTEND-ANALYSIS.md)）。

## 1. JVM 解析不了 Go 的类型

### 1.1 一个跑在 JVM 上的 Go 前端得做什么

前端的活是把源码变成 TAC，而一条 TAC 指令带着一个**被调用者签名**：owner、方法名和元数，
规范形态是 `owner.method/arity`（`CalleeKeyNormalizer.java:45`）。引擎拿这个签名去查
sink 目录，而目录就是一组签名的模式。

所以前端绕不开类型解析。它也伪造不了，因为目录里的模式是写在**已解析签名**上的：一个要
匹配 `net/http.Get` 的模式，必须对着一个写着 `net/http.Get/1` 的签名来匹配，而只有类型
解析器能产出后者。

解析 Go 的类型意味着：

- `go/parser`，产出语法树；
- `go/types`，做类型检查，并给每个表达式一个类型；
- `go/build` 与 `golang.org/x/tools/go/packages`，找到包与导出数据。

这四样**都是 Go 源码**。它们没有 JVM 实现，也不太可能有：`go/types` 是给一门类型系统
用 Go 代码写出来的语言做的类型检查器，而且它依赖 Go 标准库自己的数据结构。一个 JVM
前端等于要从零重写一遍 Go 的类型系统，而且必须**一模一样地**重写——因为一个解析得
不一样的类型会产出不一样的签名，进而不一样的目录匹配。

这不像"写一个 Go 解析器"那种难。它像"成为这门语言的第二个实现"那种难，而且换不来什么：
Go 工具链已经有了，而且它是对的。

### 1.2 路线：一个原生 Go sidecar

C# 前端已经定下了形状：一个拥有该语言自家编译器的原生进程，用一套带帧的 JSON 协议连
着，由 JVM 把结果归约成与其它前端产出的同一个 IR
（[CSHARP-FRONTEND-ANALYSIS.md 第 2.4 节](CSHARP-FRONTEND-ANALYSIS.md)）。

Go 取的是同一个形状，只是换了一处替换：sidecar 是一个链接了 `go/parser` 与 `go/types`
的 Go 程序，而不是一个链接 Roslyn 的 .NET 程序。下游一切不变：

| 层 | 它是什么 | 对 Go 有变化吗 |
| --- | --- | --- |
| sidecar | 运行该语言自家前端的原生进程 | 有：它是 Go 程序，不是 .NET 程序 |
| 线格式 | 长度前缀 JSON，形状映射 TAC | 无 |
| IR | `org.plumb.tac.ir.*`，由前端产出，由 `IrSerializer` 序列化 | 无 |
| 引擎 | CFG 构建器、DFA 引擎、sink 目录 | 目录会多出 Go 的 family；引擎不变 |
| 磁盘缓存 | 同一份 `.tac` 契约，同一个版本握手 | 无 |

两家独立的商业静态分析工具对 Go 用的就是这个形状，而这个形状是被逼出来的而不是选出来
的：一个跑在 JVM 上的分析器想要 Go 的类型，就得运行 Go 的类型检查器，而运行 Go 的类型
检查器的唯一办法就是运行 Go。

## 2. Go 会把 TAC 的什么打破

TAC 有 22 个 opcode（`TacInstruction.Kind`）、一个最多带一个值操作数的 `RETURN`
（`TacInstruction.java:362`）、一个 14 种类型的类型格（`TacType.Kind`），以及一个
`owner.method/arity` 的被调用者键契约。有四个 Go 构造放不进去，其中没有一个需要新
opcode。

### 2.1 四个缺口

| Go 构造 | TAC 现在有什么 | 怎么关闭 |
| --- | --- | --- |
| 多返回值 `(T, error)` | `RETURN` 最多带一个值；`ReturnShape` 是单值形态 | 一个决策：值结果是调用的目的变量，错误结果是异常出口 |
| `defer` | `CATCH_HANDLER` 与 `FINALLY_ENTER` 是函数内部控制流里的标记 | 挂在函数上的侧表，而不是控制流区域 |
| `go` 语句与 channel | 引擎没有程序级并发模型 | 显式异步，但不声称任何 happens-before |
| map、指针、slice、struct | 14 种类型种类，没有指针、map 或 struct | 映射到已有种类上的更粗的类型 |

### 2.2 多返回值：值结果与异常出口

Go 最常见的两结果形状是 `(T, error)`，而 Go 的约定是 `error` 是**最后一个**结果。正是
这个约定让下面的降级不需要动 IR 就能成立：

| Go 形状 | 降级成 | 分析因此说不出的 |
| --- | --- | --- |
| `v, _ := f()` | 目的变量没被用掉的 `CALL` | 什么也没丢；被丢掉的结果只是没被读 |
| `v, err := f()` | 目的变量为 `v` 的 `CALL`；错误是该调用的异常出口 | 错误不再是调用方能检查的值 |
| `return v, nil` | `RETURN v` | -- |
| `return v, err` | `THROW err` | 调用方看到的是异常出口，而不是返回的错误 |
| 返回两个都有意义的结果的函数 | 不建模 | 该函数被报为 `SOURCE_LOWERED` |

`THROW` 那一行是承重的。Go 自己的惯用法是

```go
v, err := f()
if err != nil {
    return err
}
```

这恰好就是"在错误路径上，异常地离开本函数"。把错误结果建模成异常出口，就把这条惯用法
变成了 TAC 自己的 `THROW`，而 TAC 已经有 `THROW` 与 `CATCH_HANDLER`。**IR 不变。**

它的代价值得明说，因为这是一个真实的损失而不是技术细节：

- 错误不再是值。一个"错误返回未被检查"的 checker 没法在调用方读到 `err`，因为那里已经
  没有 `err` 这个值了。这样的 checker 必须改成按异常出口模型为 Go 重新定义。
- 一个返回两个**都**对分析有意义的值的函数建模不了。这个情况很少见，在翻译期就能
  检出，而且会被报成一次降级，而不是被悄悄丢掉。

### 2.3 `defer`：defer 站点上的一条调用，加上「它到底是什么」的记录

`defer` 不是 `finally` 块，TAC 的 `FINALLY_ENTER` 也不是它的归宿，理由有两条：

- `defer` 在**函数**出口处运行，而不是在包含它的那块代码的出口处运行。
  `FINALLY_ENTER` 标记是控制流区域里的一个点。
- `defer` 的**实参在 `defer` 语句所在处求值**，不是在延迟调用实际运行时求值。
  控制流区域是在区域里求值的。

所以一个 `defer` 同时被建模在两个地方：

- **调用被写进指令流**，紧接在求值其实参的那些指令之后。实参就是 defer 站点产出的那些，
  所以从被污染的值到延迟调用的那条边是真实的：`defer` 之后被重新赋值的值不会被它看到，
  这与 Go 完全一致。
- **延迟调用记录**同时挂在函数上：被调用者签名、实参操作数，以及 defer 站点的位置。
  它说明指令流近似的是什么。

为什么两者都要？因为只有调用会把调用的**时机**放错，只有记录会把那条**边**丢掉。一条只存在于
侧表里的记录，对读指令流的 checker 是不可见的，于是 `defer os.WriteFile(name, tainted, 0644)`
根本不会有通向 `os.WriteFile` 的路径 —— 而缺一条路径是缺一个结论，不是缺一点精度。

损失是什么，并且说出声：调用实际上在函数出口处运行，而指令流把它放在 defer 站点。依赖 `defer`
周围语句顺序的 checker 会得出程序并不保证的结论。所以该函数的精度被降为 `SOURCE_LOWERED`，
并有一条 problem 说明原因。这个降级**不**抑制任何结论：它记录近似，而不是过滤结果。

### 2.4 `go` 与 channel：异步，但不声称任何顺序

引擎一次分析一个函数，没有程序级的并发模型。两家商业工具的 Go 分析实现取的是同一个
立场：goroutine 是**显式**的，但不声称任何 happens-before 关系。

于是：

- `go f(x)` 降级成一个普通的 `CALL`，外加挂在所在函数上的一个标记，说明这个函数起了
  一个 goroutine。
- channel 的发送与接收是 channel 类型上的普通调用。
- 分析**不声称**一个 goroutine 的写发生在启动者的读之前。

最后这一点必须说出声来，因为读者最容易在这里想多了。一个报"goroutine 写的值在没有
同步的情况下被读到"的 checker **不在范围内**，假装在范围内只会造出一台误报机器。

### 2.5 map、指针、slice 与 struct：一个更粗的类型系统

`TacType.Kind` 有 14 种种类——`BOOLEAN`、`BYTE`、`SHORT`、`CHAR`、`INT`、`LONG`、
`FLOAT`、`DOUBLE`、`DECIMAL`、`STRING`、`CLASS`、`ARRAY`、`NULL`、`VOID`——其中没有
指针、map、struct 或 slice。于是映射是：

| Go 类型 | TAC 类型 | 说明 |
| --- | --- | --- |
| `*T` | `CLASS` | 一个引用；污点引擎只问它有没有被污染 |
| `[]T` | `ARRAY` | |
| `map[K]V` | `CLASS` | 一个引用；读与写是 map 上的调用 |
| `struct{...}` | `CLASS` | |
| `error`（一个接口） | `CLASS` | |
| `string` | `STRING` | |
| `int`、`int64`、`float64`…… | 对应的数值种类 | |

这是可以接受的，因为污点引擎问的是"这个值有没有被污染"，而不是"它的确切类型是什么"。
一个需要知道某个值**恰好**是 `[]byte` 的 checker，需要 Go 专属的那一层，而且它会从 Go
前端自己的类型信息里拿到，而不是从 TAC 的类型格子里拿到。

### 2.6 IR 自己的词汇表要加什么

只有一样：一个 `SourceLanguage` 常量。这个枚举现在有六个常量（`JAVA`、`KOTLIN`、
`SCALA`、`GROOVY`、`CSHARP`、`UNKNOWN`），而在末尾加一个是向后兼容的，因为在磁盘缓存
契约里这个枚举是**按名字**序列化的（`SourceLanguage.java:24-25`）。

语言语义注册表也得学会 Go：`LanguageSemanticsRegistry.withDefaults` 今天注册了 Java、
Kotlin、Scala 与 C#，而一个没有注册语义的语言既没有 passthrough 规则，也没有 sanitizer
规则，也没有 source 规则。

## 3. 构建捕获：`go build` 必须交出什么

### 3.1 Go 构建的两个层次

`go build` 做两类不同的工作，捕获两层都要看到。编译器每个包被调用一次，然后链接器被
调用一次：

| 层次 | 命令 | 它带着什么 | 为什么重要 |
| --- | --- | --- | --- |
| 编译 | `compile -p <import path> -importcfg <file> -lang=go<version> ... -o $WORK/<n>/_pkg_.a <files>` | 该包自己的源文件、它的语言版本，以及它依赖的**导出数据** | 这是每个包是对着什么编译的 |
| 链接 | `link -importcfg <file> -o <binary> ...` | 真正被链接进二进制的**包列表** | 这是关于程序里有什么的权威说法 |

这个区别正是整节的重点。编译命令说的是每个包**看到了**什么；链接命令说的是程序**是**什么。
一个被编译但从未被链接的依赖——一个工具、一个测试、一个被 build tag 关掉的变体——不该
出现在分析里，而只有链接这一层知道这件事。

### 3.2 捕获必须抽出什么

| 从编译命令里 | 为什么分析需要它 |
| --- | --- |
| 包的 import path（`-p`） | 包的身份；调用图与模块图都以它为键 |
| 源文件 | 要翻译的文件 |
| 语言版本（`-lang=go1.23`） | 这个包是用哪个语言特性编译的；类型检查器必须被告知同一个 |
| import 配置里的导出数据 | 依赖的**类型**，而且不必读它们的源码 |
| build tag、`GOOS`、`GOARCH` | 到底哪些文件在那次编译里 |
| **工具链自己的路径** | **标准库源码在哪里。** 编译器位于 `<root>/pkg/tool/<goos>_<goarch>/compile`，所以 root 就是 `/pkg/tool/` 之前的那一段，而它正是**构建了这个工程**的那套工具链 |

| 从链接命令里 | 为什么分析需要它 |
| --- | --- |
| import 配置里的包列表 | 真正在程序里的包集合 |

导出数据是承重的那一项。一个靠读依赖**源码**来解析依赖的 Go 前端，只要碰上 build tag
不同、GOOS 不同，或者有 vendor / replace 的依赖，就会得到与构建不同的答案。**对着捕获
到的导出数据**解析，正是让分析与构建保持一致的做法。

**但到了分析真正跑的时候，导出数据通常已经没了。** 工具链把 import 配置写进构建的*临时*
目录，而构建结束时会删掉那个目录。所以一条从构建取来的捕获，点名的是一份已经不存在的 import
配置，它指向的导出数据也一起没了。

于是前端必须能挺过两种状态：导出数据还在，分析与构建完全一致；导出数据没了，依赖改从它的
**源码**解析——那是对类型的第二次意见，而不是构建自己的意见。第二种状态对一次 Go 构建来说是
常态，所以它不是错误——但它要**被报告**，因为这时分析推理的对象不是构建编译出来的东西，读者
必须知道。一条声称"这个项目没有依赖"的捕获才是谎言，而且是沉默的谎言。

### 3.3 捕获必须有一条降级路径

**一条只在构建成功时才存在的捕获不算捕获。** 构建会因为与分析无关的原因失败：一个
需要没装的工具的代码生成步骤、一次需要联网的模块拉取、一个源码树不完整的工具链。那种
时候，一条等着构建成功的捕获会**什么都没捕到**——而"什么都没捕到"与"没什么可分析的"
无法区分，而这正是一个扫描器最不该悄悄产出的结果。

所以捕获有两层：

| 层 | 它产出什么 | 它知道什么 |
| --- | --- | --- |
| 第 1 层：被拦截的构建 | 原样的 `compile` 与 `link` 命令 | 全部，包括每个包精确的语言版本与 build tag |
| 第 2 层：`go list -json -deps -export ./...` | 每个包一个 JSON 对象，带着 `ImportPath`、`Module`、`GoFiles`、`Imports` 与 `Deps`，以及每个依赖的导出数据 | 包图与源文件，而且不必编译任何东西 |

第 2 层不需要构建能跑通，模块缓存热的时候也不需要联网。它严格弱于第 1 层——特别是它
不告诉分析是哪些 build tag 选出了哪些文件——但它足以产出一份 TAC，而"一份带明确降级
说明的 TAC"胜过"没有 TAC"。

### 3.4 捕获放在哪里

捕获属于捕获仓，而不是本仓：在现有的 C、C++、MSVC、C# 与 JVM 适配器旁边加一个 Go 适配
器，在同一张选项映射表与注册表里注册。Go 构建的命令既不是 `csc` 形状也不是 `clang` 形状，
所以通用适配器认不出它们；Go 适配器必须认出 `compile` 与 `link` 调用，并读取它们的 import
配置。

共享模型要加两样东西，因为 Go 的构建在 C 的编译里没有对应物：

- **一份 import 配置。** 编译命令点名一个文件；那个文件点名若干包及其导出数据。这是每
  条命令的附属物，像 GCC 世界里的 `-importcfg`，但形状不同。
- **每条编译命令一个包身份。** C 的世界用源文件标识一个翻译单元；Go 的世界用 import
  path 标识它。

## 4. Go 的 TAC：五步

### 4.1 解析

对捕获到的源文件跑 `go/parser`，保留注释。解析器在这里正是文件集合起作用的地方：文件
集合必须是捕获到的那一个，因为那一个才是构建用的那一个。

### 4.2 类型检查

对解析出的文件跑 `go/types`，其 `Importer` 按这个顺序解析依赖：

1. **项目自己的包**从它自己的文件做类型检查。项目自己的包永远在这个集合里，所以项目内一个包对
   另一个包的调用，即使别的什么都解析不了，也能解析出来。
2. **带导出数据的依赖**从那份导出数据读取——那是构建编译出来的东西，所以类型是构建自己的类型。
3. **没有导出数据的依赖**从它的**源码**做类型检查，源码位置在两个地方之一：

   - **标准库**，在**Go 工具链的根目录**下。这个根目录首先来自捕获——编译器位于
     `<root>/pkg/tool/<goos>_<goarch>/compile`，所以 root 就是 `/pkg/tool/` 之前的那一段，而它正是
     **构建了这个工程**的那套工具链——因此也就是工程被编译时所对着的那个标准库。没有捕获的扫描没有
     命令可读，于是回退到环境里的 `GOROOT` 与 `PATH` 上的 `go` 命令。

     环境里的 `GOROOT` **不是**第一答案，而且只有当它指向一套**工具链**——一个放着标准库源码
     `<root>/src` 的目录——时才被采用。光有目录不够：一个被清空、只剩模块缓存的 `GOROOT`，在「目录
     存在」的检查下和一套工具链长得一模一样，于是后面的查找根本找不到源码。环境里的 `GOROOT` 是上一次
     安装的工具链留下的残留，它比它所指的那套工具链活得久；而一个指向「已经不在了的目录」的 `GOROOT`
     会让**每一次**标准库导入**静默**失败：导入解析不出来，对标准库的调用丢掉类型，依赖它们的
     finding 消失，而扫描仍然报告成功。一个不存在的目录和一个不存在的标准库长得一模一样。

   - **模块缓存**，给第三方依赖用：`$GOMODCACHE/<module>@<version>/<package>`，其中模块路径里的
     大写字母存成 `!` 加小写字母。`go/build` **不认识**这个布局——缓存是按模块路径与版本编址的，
     而 import path 说的是一个包，那个包还可能在某个模块**内部**——所以缓存是直接搜的，模块的
     最新版本被读走。

   这正是「构建结束后再读捕获」所处的常态——见 3.2 节——代价是要类型检查依赖的源码，而不是读它的
   导出数据。

顺序有意义：导出数据优先，因为它才是构建编译出来的东西。源码是回退路径，而回退路径是要**被报告**
的，不是被静默使用的。

两个地方都没找到依赖时，导入**响亮地**失败：失败信息说清搜了哪两个地方、为什么两边都没有。一个
类型缺失的依赖就是一个 finding 缺失的依赖，所以它不能被报成「没有 finding」。

类型检查器的配置要带上目标架构的尺寸（`types.SizesFor`），因为 Go 的 `int` 在某些目标上
是 32 位、在另一些上是 64 位，而 TAC 的数值种类取决于它。

### 4.3 降级

按函数：构建控制流图，把语句降级成 TAC。Go 专属的降级就是第 2 节的那四个——多结果模型、
`defer` 调用及其记录、异步的 `go` 调用、粗糙的类型映射——再加上常规控制流（`if`、`for`、`range`、
`switch`、`select`）。

一条 `select` 语句是它各个分支上的一个分支选择，默认分支作为落空路径。`range` 一个 slice
是一个带下标的循环；`range` 一个 map 是对 map 迭代器的调用；`range` 一个 channel 是一次
接收。

### 4.4 讲线格式

用 C# sidecar 已经在讲的那套长度前缀 JSON，同样的两个操作：`openProject` 建立工程，
`translate` 翻译一个文件。

**版本握手必须在出现第二个 sidecar 之前存在。** 线协议现在没有版本字段，而本构建不认识
的指令种类会静默变成 `HAVOC`——引擎只在 `CALL` 与 `UNINTERPRETED` 上查 sink，所以它永远
不会与目录匹配
（[CSHARP-FRONTEND-ANALYSIS.md 第 4.7 节](CSHARP-FRONTEND-ANALYSIS.md)）。只有一个
sidecar 时这是一个维护风险；有两个时它就是 finding 无影无踪消失的来源，因为两个
sidecar 会在不同时刻各自漂移。

### 4.5 把每一次降级都报出来

一个没有完全建模的 Go 构造必须产生一条 `FunctionProblem`。它不能只是缺席。

| 情况 | 必须报出什么 |
| --- | --- |
| 一个函数返回两个都有意义的结果 | 该函数上的一次降级，点名它 |
| 一个包的导出数据读不出来 | 用到它的那个包里的每个函数上的降级 |
| 捕获到的文件集合里有源文件没产出任何函数 | 该文件上的降级，而不是沉默 |
| build tag 或 GOOS 改变了文件集合 | 受影响的包上的降级 |
| 捕获降级到了第 2 层 | 工程级的一次降级，点名那些语言版本或 build tag 未知的包 |
| **找不到任何 Go 工具链根目录** | **工程级的一次降级，点名试过的那个根目录。** 没有它就够不到标准库源码，于是每一次标准库导入都解析不出来 |
| **一个依赖在工具链和模块缓存里都没找到** | **一次降级，点名 import path 与搜过的这两个地方** |

这与 C# 那条路已经学到的教训是同一条：不被报出来的降级就是一次无迹可寻的漏报。

## 5. 让捕获保持诚实的交叉校验

捕获与前端是对同一个构建的两次独立读取，它们可以不一致。校验的形状与 Maven 那条路
已有的形状相同（`CompileCrossCheck`、`CompileDiscrepancy`）：

| 校验 | 不一致意味着什么 |
| --- | --- |
| 链接 import 配置里的每个包都出现在 TAC 里 | 分析漏掉了一个在二进制里的包 |
| 每个被捕获编译单元的每个源文件都至少产出一个函数 | 前端丢掉了一个文件 |
| TAC 里的函数数与前端报出的函数数一致 | 从类型检查器到 TAC 之间丢了东西 |
| 捕获看到的包与前端看到的包是同一个集合 | 捕获与前端对程序的认知不一致 |

最后一条是唯一能抓到**过期捕获**的：来自上一次构建、或来自另一种配置的捕获，会为一份
不在磁盘上的程序产出 TAC。别的校验都不会发现这件事。

## 6. 本文不主张什么

- **不主张 Go 的规则覆盖度。** `sink-families.yaml` 有 82 个 family，其中 38 个按语言
  限定，没有一个限定到 Go。Go 的目录是这份计划里最大的一块工作量，而且还没开始。
- **不主张多结果模型是完备的。** 它覆盖 `(T, error)` 与被丢弃的结果。返回两个都有意义
  的结果的函数会被降级，并且被报出来。
- **不主张任何并发结论。** 没有 happens-before，没有 goroutine 顺序，没有 channel 缓冲
  推理。
- **不主张分析 cgo。** cgo 指令背后的 C 代码不在范围内，边界上的 Go 一侧当作普通调用
  处理。
- **不主张已经做过端到端测量。** 上面这份设计是照着 Go 工具链的已文档化行为、以及两家
  独立的 Go 分析实现写出来的。它没有在这里端到端跑过，而能证明它的那些数字——捕获到的
  命令形状、导出数据格式、降级与编译器的吻合度——都必须先测出来，才能被相信。
