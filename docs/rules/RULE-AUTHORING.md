# Rule Authoring: AI Prompt / CWE Labels / External Tool IDs / Adding a Rule

[English](../README.md) | [中文](../zh/rules/RULE-AUTHORING.md)

This document covers how to write a rule: the AI prompt it carries, where
its CWE labels come from, the equivalent IDs in the external tools, and
the steps to add a new one. The main rule catalogue is in `RULES.md`; the
style rule operations (enabling, disabling, changing parameters) are in
`RULE-STYLE-OP.md`.

## 1. AI augmentation and the per-rule prompt

Every `DfaChecker` / `AstChecker` carries its own `getAiPrompt(Finding) -> String`:

- returning `null` = the rule does **not** go through AI dedup
- returning a non-null value = the LLM receives this rule's prompt, the finding
  details, the dataflow trace and a source window, and outputs TP / FP / UNKNOWN

The prompt is provided by the checker by default. The hand-written overrides are:

- 20 `DfaChecker`s plus `TaintedCheckerBase` (auto-generated from `TaintRule` metadata)
- `plumb-style/src/main/java/org/plumb/style/security/HardcodedCredentialsCheck.java`
- `plumb-style/src/main/java/org/plumb/style/error/EmptyCatchBlockCheck.java`
- `plumb-style/src/main/java/org/plumb/style/style/BadShiftCheck.java`

The user's `--rule-prompts-dir` still overrides (a `<rule-name>.md` file
overrides the inline `getAiPrompt` return value of the matching checker).

**A three-level override chain**:

1. `TaintedCheckerBase` generates it automatically from the `TaintRule` metadata (`ruleId` / `sourceKindName` / `sinkFamilyKey` / `cwe` / `severityLabel` / `domain`)
2. A hand-written inline `getAiPrompt` in the DfaChecker / AstChecker (a few high-value rules)
3. The user's `.md` override in `--rule-prompts-dir` (highest priority)

See `docs/usage/CLI.md` §2.2 for details.

## 2. Where the CWE labels come from

CWE labels have two independent sources. When you add a rule, you need to know
which one your rule belongs to:

| Rule type | CWE source | How to add it |
| --- | --- | --- |
| AST rules (`plumb-style`) | The CWE list in the `RuleDef` constructor arguments | Pass `List.of("CWE-xxx")` in the `RuleDef` after `new RuleId(...)` |
| DFA rules (`plumb-dfa`) | `plumb-dfa/src/main/resources/cwe-mappings.yaml` | Add an entry under `mappings:` in that YAML |

The DFA mapping key is the **finding key**: `{CheckerName}`, or
`{CheckerName}_{SinkFamilyShortName}` when one checker emits several CWE families for
different sink families. So the YAML looks like:

```yaml
mappings:
  MyChecker: CWE-XXX
  MyChecker_sub: CWE-YYY
```

The CWE of an AST rule travels with the finding into the NDJSON `cwe` field;
the finding key of a DFA rule is looked up through `cwe-mappings.yaml`.
**Changing the emit-id string does not affect the CWE** -- they are not the same
mapping.

## 3. Equivalent IDs in external tools

There are **two** different things called "an external ID", and they are not the same
mapping.

**`RuleDef.aliases` carries Plumb's OWN aliases** -- the other spellings of the same
rule that Plumb itself accepts. A rule may have a canonical id and a compatibility alias:

```java
new RuleId("ast-error-empty-catch-block", "EMPTY_CATCH_BLOCK"),
// ...
List.of("ast-error-catch-block-strict", "empty-catch-block");
```

Those are the ids a user may write in `rules.enabled` or in an allowlist. They are **not**
PMD / SpotBugs / Checkstyle / SonarQube ids.

**The external-tool equivalents are a separate, documented mapping** in the per-rule
entries of `docs/plumb-style-rules.md`, under its external-equivalents label. That
mapping is **derived by `scripts/gen_rules_doc.py`**, not declared in the source: the
generator reads the checker's javadoc for explicit mentions ("Checkstyle's `Foo`",
"SonarQube S1234") and falls back to a small table of naming patterns. It covers **PMD,
SpotBugs, Checkstyle and SonarQube**, and nothing else. A rule with no
detected equivalent says so explicitly -- that is the normal case, not a gap.

The complete table is generated by `scripts/gen_rules_doc.py` into
`docs/plumb-style-rules.md`.

**The full comparison** (implementation mechanism / CWE coverage / false-positive
rate / performance / AI integration / where Plumb sits) is in
[`RULE-TOOL-COMPARISON.md`](./RULE-TOOL-COMPARISON.md).

## 4. Steps for adding a new rule

**Choose a path first.** There are two ways to add an AST rule:

| | Write a Java checker | Write a Kotlin DSL rule |
| --- | --- | --- |
| Suitable for | Rules that ship in the product's default rule set, complex logic, rules that need an AI dedup prompt | Project-local rules, quickly adding a shape check, tracking an upstream rule |
| Lands as | The `plumb-style` module plus a `CheckerCategories` registration | A single rule file (XML / YAML) |
| Distribution | Ships with the code | Travels with the project configuration |
| Documentation | §13.1 of this document | [`../tech/KOTLIN-DSL.md`](../tech/KOTLIN-DSL.md) |

Data-flow / taint rules have **only one path**: YAML plus a checker in
`plumb-dfa` (§13.2 / §13.3 of this document). The DSL engine only does AST
rules.

### 13.0 Choosing a Pattern (a prerequisite step for style rules)

**Choose a Pattern before you write a new style checker.** `AstDispatcher`
builds its dispatch table by reflecting over the `visit(NodeType, StyleContext)`
methods a checker declares, so a single checker that calls `findAll` / `walk`
several times makes every file get walked several times. The Pattern decision
table:

```
[Before writing a new AST checker]
   ↓
[1. What kind of node do I want to handle?]
   ↓
   ├── Several unrelated node types? (e.g. "the if/else branches of a BinaryExpr")
   │     ↓
   │   1.a One visit(X, ctx) overload per type → Pattern D
   │      (one AstDispatcher walk, no visit(CU))
   │      Example: ObjectHijackCheck.visit(ClassOrInterfaceDeclaration, ctx)
   │
   └── Only one node type (e.g. only MethodCallExpr)
         ↓
      2. Use a per-node visit(X, ctx) → Pattern D
         (fires only when the AstDispatcher walk hits that node type)
         Example: EnvVarCheck.visit(MethodCallExpr, ctx)
      │
      └── 2.b You need file-level context (Imports / Comments / cross-node relations)
            ↓
         2.b.1 Hand-roll one walk in visit(CU) with instanceof dispatch → Pattern A, improved
         2.b.2 If it is a small explicit set of types such as [Import + Class + AnnotationExpr]
               → use n.findAll several times, but **guarantee fA ≤ 2**
               → Pattern A (acceptable)
         2.b.3 Only if neither works is Pattern C (several n.walk calls) allowed
```

**The red lines** (hard constraints):

- ❌ **Pattern B is forbidden** (`visit(CU) + n.findAll(A) + n.findAll(B) + ...`, 3 or more)
- ❌ **A walk inside a loop is forbidden** (`for (X : n.findAll(A)) { n.walk(B, ...) }`)
- ❌ **Pattern D+ is forbidden** (visit(CU) and per-node visit at the same time)
- ⚠️ **Pattern A is limited** to at most 2 findAll calls; beyond that it must be downgraded to Pattern D
- ✅ **Pattern D is preferred** (per-node visit overloads, one AstDispatcher walk)

**How the walk patterns of the current plumb-style checkers evaluate**:

| Pattern | Evaluation |
| --- | --- |
| A (single findAll) | ✓ already optimal |
| B (several findAll) | ⚠️ an anti-pattern; change it to A or D |
| C (several walks) | ⚠️ an anti-pattern; change it to A or D |
| D (per-node visit overloads) | ✓ recommended, one AstDispatcher walk |
| D+ (per-node and CU at the same time) | ⚠️ pick one of the two |
| E / E0 (not part of the classification above) | needs separate confirmation |

**Direction of the work**: B and C are the main optimisation targets; changing
them to A or D brings the number of walks per file down. The quantitative
inventory script is not kept with the documentation -- when you need it, scan the
`n.walk(` / `n.findAll(` call counts of each `*Check.java` under
`plumb-style/src/main/java` directly.

### 13.1 Adding a new style rule

1. Write the rule in `plumb-style/src/main/java/org/plumb/style/<category>/FooCheck.java`, implementing the `AstChecker` interface. The `<category>` subdirectory **is** the category.
2. Run `python scripts/gen_categories.py` to regenerate `CheckerCategories.java`. That file is **auto-generated** (`// AUTO-GENERATED by scripts/gen_categories.py -- DO NOT EDIT`), and the generator derives each checker's category from the subdirectory it lives in -- so there is no hand-written `m.put` to add, and hand-editing the file is lost on the next regeneration.
3. Run `mvn -o -pl plumb-style install` to rebuild.
4. Verify with `java -jar plumb-main/target/plumb-main-0.1.0-SNAPSHOT-all.jar --list-rules | grep FooCheck`.

⚠️ A checker that lives directly in the package root has **no** category and is not emitted
into `CheckerCategories` at all -- `byCategory(...)` cannot select it. Use `load("<glob>")` or
`register(...)` for those. (There is one such checker today: `ObjectHijackCheck`.)

Note the two loading paths: `AstCheckerRegistry.builtins()` goes through a classpath scan
and does **not** depend on `CheckerCategories`; what a missing registration affects is the
category-based loading path, `byCategory(...)`.

### 13.2 Adding a new DFA unified rule

1. Write the rule in `plumb-dfa/src/main/java/org/plumb/dfa/checkers/<family>/FooChecker.java`, implementing the `DfaChecker` interface (or extending `TaintedCheckerBase`).
2. Add a line `checkers.add(new org.plumb.dfa.checkers.<family>.FooChecker());` to `ScanRunner.buildDfaCheckers()`, and attach the matching YAML flag.
3. Add a checker entry to `plumb-dfa/src/main/resources/checkers.yaml` (`enabled` decides the default switch).
4. Add a finding-key mapping to `plumb-dfa/src/main/resources/cwe-mappings.yaml` (`MyChecker: CWE-XXX`).
5. Run `mvn -pl plumb-dfa install` to rebuild.
6. Verify with `java -jar plumb-main/target/plumb-main-0.1.0-SNAPSHOT-all.jar --list-rules | grep <rule-id>`.

### 13.3 Adding a new taint rule

1. Add an `m.put("<rule-id>", TaintRule.of(...))` entry to `plumb-dfa/src/main/java/org/plumb/dfa/taint/TaintRuleRegistry.java`.
2. **Register the source / sink patterns in `plumb-dfa/src/main/resources/sink-families.yaml`** (there is no `TaintCatalog` class -- the early documentation mentioned a class that never existed). A sanitizer that is not an inherent property of some sink family is decided by `TaintedCheckerBase.isSanitizer(...)`, which is a **private static** method with a hardcoded list of callee-signature prefixes -- a subclass cannot override it, so a new sanitizer is added there.
3. Add the matching mapping to `plumb-dfa/src/main/resources/cwe-mappings.yaml`.
4. Rebuild + verify.

#### How to write a sink pattern (important)

Write sink patterns with the **fully qualified name** and **anchor** them at `^`:

```yaml
- '^org\.springframework\.jdbc\.core\.JdbcTemplate\.query(/\d+)?'
```

Anchoring is necessary: `SinkPattern` uses `Matcher.find()` for **substring**
matching, so an unanchored `^org\.apache\.commons\.io\.IOUtils\.read` also
matches methods like `...IOUtils\.readAllBytes`.

**Do not** drop the package name because you are afraid of mistyping it. A
**prefix-optional** variant is derived automatically at match time (see
`SinkFamily.SinkPattern.relaxedForm`):

```
^org\.springframework\.jdbc\.core\.JdbcTemplate\.query(/\d+)?
        ↓
^(?:[\w.]+\.)?JdbcTemplate\.query\b(/\d+)?
```

This solves a hard constraint of the TAC: **a callee signature is only a fully
qualified name when the symbol resolver can resolve the receiver type**. When
the jars of third-party dependencies are not on the analysis classpath (scanning
a project without its dependency jars is the normal case), the IR holds the
simple name:

```
org.springframework.jdbc.core.JdbcTemplate.query/2   ← resolution succeeded
JdbcTemplate.query/2                                   ← resolution failed
```

Without this prefix-optional variant, **all framework sinks (Spring
JdbcTemplate, MyBatis, Jackson, Guava) silently fail to match** -- the analysis
runs to completion and reports not a single finding.

Three boundaries of the variant:

- **It is only enabled when the receiver is a simple name**. A fully qualified
  callee goes through the strict form, so an exact match always wins.
- **Only the package prefix is relaxed**; the class name and the method name
  still have to match exactly. `JdbcTemplate.query` does not match
  `NamedParameterJdbcTemplate.query`.
- **A word boundary `\b` is added after the method name**. Otherwise
  `JdbcTemplate.query` would also match `JdbcTemplate.queryForList`, and the two
  have different parameter indices.
