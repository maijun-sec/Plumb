# Rule Authoring: AI Prompt / CWE Labels / External Tool IDs / Adding a Rule

[English](../README.md) | [中文](../zh/rules/RULE-AUTHORING.md)

This document covers how to write a rule: the AI prompt it carries, where
its CWE labels come from, the equivalent IDs in the external tools, and
the steps to add a new one. The main rule catalogue is in `RULES.md`; the
style rule operations (enabling, disabling, changing parameters) are in
`RULE-STYLE-OP.md`.

## 1. AI augmentation and the per-rule prompt

Every `DfaChecker` / `AstChecker` carries its own `getAiPrompt(Finding) -> String`:

- returning `null` = the rule does **not** go through AI dedup
- returning a non-null value = the LLM receives this rule's prompt, the finding
  details, the dataflow trace and a source window, and outputs TP / FP / UNKNOWN

The prompt is provided by the checker by default. The hand-written overrides are:

- 42 `DfaChecker`s plus `TaintedCheckerBase` (auto-generated from `TaintRule` metadata)
- `plumb-style/src/main/java/org/plumb/style/security/HardcodedCredentialsCheck.java`
- `plumb-style/src/main/java/org/plumb/style/error/EmptyCatchBlockCheck.java`
- `plumb-style/src/main/java/org/plumb/style/style/BadShiftCheck.java`

The user's `--rule-prompts-dir` still overrides (a `<rule-name>.md` file
overrides the inline `getAiPrompt` return value of the matching checker).

**A three-level override chain**:

1. `TaintedCheckerBase` generates it automatically from the `TaintRule` metadata (`ruleId` / `sourceKindName` / `sinkFamilyKey` / `cwe` / `severityLabel` / `domain`)
2. A hand-written inline `getAiPrompt` in the DfaChecker / AstChecker (a few high-value rules)
3. The user's `.md` override in `--rule-prompts-dir` (highest priority)

See `docs/usage/CLI.md` §2.2 for details.

## 2. Where the CWE labels come from

CWE labels have two independent sources. When you add a rule, you need to know
which one your rule belongs to:

| Rule type | CWE source | How to add it |
| --- | --- | --- |
| AST rules (`plumb-style`) | The CWE list in the `RuleDef` constructor arguments | Pass `List.of("CWE-xxx")` in the `RuleDef` after `new RuleId(...)` |
| DFA rules (`plumb-dfa`) | `plumb-dfa/src/main/resources/cwe-mappings.yaml` | Add an entry under `mappings:` in that YAML |

The DFA mapping key is the **finding key**: `{CheckerName}`, or
`{CheckerName}_{SinkFamilyShortName}` when one checker emits several CWE families for
different sink families. So the YAML looks like:

```yaml
mappings:
  MyChecker: CWE-XXX
  MyChecker_sub: CWE-YYY
```

The CWE of an AST rule travels with the finding into the NDJSON `cwe` field;
the finding key of a DFA rule is looked up through `cwe-mappings.yaml`.
**Changing the emit-id string does not affect the CWE** -- they are not the same
mapping.

## 3. Equivalent IDs in external tools

There are **two** different things called "an external ID", and they are not the same
mapping.

**`RuleDef.aliases` carries Plumb's OWN aliases** -- the other spellings of the same
rule that Plumb itself accepts. A rule may have a canonical id and a compatibility alias:

```java
new RuleId("ast-error-empty-catch-block", "EMPTY_CATCH_BLOCK"),
// ...
List.of("ast-error-catch-block-strict", "empty-catch-block");
```

Those are the ids a user may write in `rules.enabled` or in an allowlist. They are **not**
PMD / SpotBugs / Checkstyle / SonarQube ids.

**The external-tool equivalents are a separate, documented mapping** in the per-rule
entries of `docs/plumb-style-rules.md`, under its external-equivalents label. That
mapping is **derived by `scripts/gen_rules_doc.py`**, not declared in the source: the
generator reads the checker's javadoc for explicit mentions ("Checkstyle's `Foo`",
"SonarQube S1234") and falls back to a small table of naming patterns. It covers **PMD,
SpotBugs, Checkstyle and SonarQube**, and nothing else. A rule with no
detected equivalent says so explicitly -- that is the normal case, not a gap.

The complete table is generated by `scripts/gen_rules_doc.py` into
`docs/plumb-style-rules.md`.

**The full comparison** (implementation mechanism / CWE coverage / false-positive
rate / performance / AI integration / where Plumb sits) is in
[`RULE-TOOL-COMPARISON.md`](./RULE-TOOL-COMPARISON.md).

## 4. Steps for adding a new rule

**Choose a path first.** There are two ways to add an AST rule:

| | Write a Java checker | Write a Kotlin DSL rule |
| --- | --- | --- |
| Suitable for | Rules that ship in the product's default rule set, complex logic, rules that need an AI dedup prompt | Project-local rules, quickly adding a shape check, tracking an upstream rule |
| Lands as | The `plumb-style` module plus a `CheckerCategories` registration | A single rule file (XML / YAML) |
| Distribution | Ships with the code | Travels with the project configuration |
| Documentation | §13.1 of this document | [`../tech/KOTLIN-DSL.md`](../tech/KOTLIN-DSL.md) |

Data-flow / taint rules have **only one path**: YAML plus a checker in
`plumb-dfa` (§13.2 / §13.3 of this document). The DSL engine only does AST
rules.

### 13.0 Choosing a Pattern (a prerequisite step for style rules)

**Choose a Pattern before you write a new style checker.** `AstDispatcher`
builds its dispatch table by reflecting over the `visit(NodeType, StyleContext)`
methods a checker declares, so a single checker that calls `findAll` / `walk`
several times makes every file get walked several times. The Pattern decision
table:

```
[Before writing a new AST checker]
   ↓
[1. What kind of node do I want to handle?]
   ↓
   ├── Several unrelated node types? (e.g. "the if/else branches of a BinaryExpr")
   │     ↓
   │   1.a One visit(X, ctx) overload per type → Pattern D
   │      (one AstDispatcher walk, no visit(CU))
   │      Example: ObjectHijackCheck.visit(ClassOrInterfaceDeclaration, ctx)
   │
   └── Only one node type (e.g. only MethodCallExpr)
         ↓
      2. Use a per-node visit(X, ctx) → Pattern D
         (fires only when the AstDispatcher walk hits that node type)
         Example: EnvVarCheck.visit(MethodCallExpr, ctx)
      │
      └── 2.b You need file-level context (Imports / Comments / cross-node relations)
            ↓
         2.b.1 Hand-roll one walk in visit(CU) with instanceof dispatch → Pattern A, improved
         2.b.2 If it is a small explicit set of types such as [Import + Class + AnnotationExpr]
               → use n.findAll several times, but **guarantee fA ≤ 2**
               → Pattern A (acceptable)
         2.b.3 Only if neither works is Pattern C (several n.walk calls) allowed
```

**The red lines** (hard constraints):

- ❌ **Pattern B is forbidden** (`visit(CU) + n.findAll(A) + n.findAll(B) + ...`, 3 or more)
- ❌ **A walk inside a loop is forbidden** (`for (X : n.findAll(A)) { n.walk(B, ...) }`)
- ❌ **Pattern D+ is forbidden** (visit(CU) and per-node visit at the same time)
- ⚠️ **Pattern A is limited** to at most 2 findAll calls; beyond that it must be downgraded to Pattern D
- ✅ **Pattern D is preferred** (per-node visit overloads, one AstDispatcher walk)

**How the walk patterns of the current plumb-style checkers evaluate**:

| Pattern | Evaluation |
| --- | --- |
| A (single findAll) | ✓ already optimal |
| B (several findAll) | ⚠️ an anti-pattern; change it to A or D |
| C (several walks) | ⚠️ an anti-pattern; change it to A or D |
| D (per-node visit overloads) | ✓ recommended, one AstDispatcher walk |
| D+ (per-node and CU at the same time) | ⚠️ pick one of the two |
| E / E0 (not part of the classification above) | needs separate confirmation |

**Direction of the work**: B and C are the main optimisation targets; changing
them to A or D brings the number of walks per file down. The quantitative
inventory script is not kept with the documentation -- when you need it, scan the
`n.walk(` / `n.findAll(` call counts of each `*Check.java` under
`plumb-style/src/main/java` directly.

### 13.1 Adding a new style rule

1. Write the rule in `plumb-style/src/main/java/org/plumb/style/<category>/FooCheck.java`, implementing the `AstChecker` interface. The `<category>` subdirectory **is** the category.
2. Run `python scripts/gen_categories.py` to regenerate `CheckerCategories.java`. That file is **auto-generated** (`// AUTO-GENERATED by scripts/gen_categories.py -- DO NOT EDIT`), and the generator derives each checker's category from the subdirectory it lives in -- so there is no hand-written `m.put` to add, and hand-editing the file is lost on the next regeneration.
3. Run `mvn -o -pl plumb-style install` to rebuild.
4. Verify with `java -jar plumb-main/target/plumb-main-0.1.0-SNAPSHOT-all.jar --list-rules | grep FooCheck`.

⚠️ A checker that lives directly in the package root has **no** category and is not emitted
into `CheckerCategories` at all -- `byCategory(...)` cannot select it. Use `load("<glob>")` or
`register(...)` for those. (There is one such checker today: `ObjectHijackCheck`.)

Note the two loading paths: `AstCheckerRegistry.builtins()` goes through a classpath scan
and does **not** depend on `CheckerCategories`; what a missing registration affects is the
category-based loading path, `byCategory(...)`.

### 13.2 Adding a new DFA unified rule

1. Write the rule in `plumb-dfa/src/main/java/org/plumb/dfa/checkers/<family>/FooChecker.java`, implementing the `DfaChecker` interface (or extending `TaintedCheckerBase`).
2. Add a line `checkers.add(new org.plumb.dfa.checkers.<family>.FooChecker());` to `ScanRunner.buildDfaCheckers()`, and attach the matching YAML flag.
3. Add a checker entry to `plumb-dfa/src/main/resources/checkers.yaml` (`enabled` decides the default switch).
4. Add a finding-key mapping to `plumb-dfa/src/main/resources/cwe-mappings.yaml` (`MyChecker: CWE-XXX`).
5. Run `mvn -pl plumb-dfa install` to rebuild.
6. Verify with `java -jar plumb-main/target/plumb-main-0.1.0-SNAPSHOT-all.jar --list-rules | grep <rule-id>`.

### 13.3 Adding a new taint rule

1. Add an `m.put("<rule-id>", TaintRule.of(...))` entry to `plumb-dfa/src/main/java/org/plumb/dfa/taint/TaintRuleRegistry.java`.
2. **Register the source / sink patterns in `plumb-dfa/src/main/resources/sink-families.yaml`** (there is no `TaintCatalog` class -- the early documentation mentioned a class that never existed). A sanitizer that is not an inherent property of some sink family is decided by `TaintedCheckerBase.isSanitizer(...)`, which is a **private static** method with a hardcoded list of callee-signature prefixes -- a subclass cannot override it, so a new sanitizer is added there.
3. Add the matching mapping to `plumb-dfa/src/main/resources/cwe-mappings.yaml`.
4. Rebuild + verify.

#### How to write a sink pattern (important)

Write sink patterns with the **fully qualified name** and **anchor** them at `^`:

```yaml
- '^org\.springframework\.jdbc\.core\.JdbcTemplate\.query(/\d+)?'
```

Anchoring is necessary: `SinkPattern` uses `Matcher.find()` for **substring**
matching, so an unanchored `^org\.apache\.commons\.io\.IOUtils\.read` also
matches methods like `...IOUtils\.readAllBytes`.

**Do not** drop the package name because you are afraid of mistyping it. A
**prefix-optional** variant is derived automatically at match time (see
`SinkFamily.SinkPattern.relaxedForm`):

```
^org\.springframework\.jdbc\.core\.JdbcTemplate\.query(/\d+)?
        ↓
^(?:[\w.]+\.)?JdbcTemplate\.query\b(/\d+)?
```

This solves a hard constraint of the TAC: **a callee signature is only a fully
qualified name when the symbol resolver can resolve the receiver type**. When
the jars of third-party dependencies are not on the analysis classpath (scanning
a project without its dependency jars is the normal case), the IR holds the
simple name:

```
org.springframework.jdbc.core.JdbcTemplate.query/2   ← resolution succeeded
JdbcTemplate.query/2                                   ← resolution failed
```

Without this prefix-optional variant, **all framework sinks (Spring
JdbcTemplate, MyBatis, Jackson, Guava) silently fail to match** -- the analysis
runs to completion and reports not a single finding.

Three boundaries of the variant:

- **It is only enabled when the receiver is a simple name**. A fully qualified
  callee goes through the strict form, so an exact match always wins.
- **Only the package prefix is relaxed**; the class name and the method name
  still have to match exactly. `JdbcTemplate.query` does not match
  `NamedParameterJdbcTemplate.query`.
- **A word boundary `\b` is added after the method name**. Otherwise
  `JdbcTemplate.query` would also match `JdbcTemplate.queryForList`, and the two
  have different parameter indices.

Changing the catalogue changes the documents derived from it. `RULES.md` and
`RULE-TOOL-COMPARISON.md` quote the catalogue's SIZE, so a commit that adds a
pattern without regenerating them leaves the repository stating a number that is
no longer true -- and nothing in the commit says so. Regenerate them, and stage
the result together with the change: `python scripts/gen_rules_overview.py` and
`python scripts/gen_tool_comparison.py`.

The pre-commit hook refuses a commit that changes the catalogue without them.
`python scripts/check_generated_documents.py` says the same thing outside a
commit, and it asks the question of the INDEX rather than of the working tree:
a working tree that has been regenerated but not staged is still a commit that
would state the old number, and it is refused as well.

#### The passthrough tables: which language, and which bucket

The two passthrough tables -- `receiver-passthrough.yaml` and
`argument-passthrough.yaml` -- say which language a family is for, and they
can say which language a single pattern is for:

```yaml
families:
  collection-getters:
    enabled: true
    languages: [java, kotlin, scala, groovy, csharp]
    patterns:                     # every language of the family
      - '^((?:[\w.]+\.)*)Map\.get(/\d+)?'
    by_language:                  # only the language that can mention it
      csharp:
        - '^((?:[\w.]+\.)*)Dictionary\.get(/\d+)?'
```

`languages:` is the gate. A family that names no language applies to every
language; a family that names languages applies to those and to no other. A
bucket names ONE language, and the patterns in it fire there and nowhere
else.

A bucket for a language the family does not cover is dead: the family does
not apply to that language, so its patterns can never fire. The loader says
so when it reads one.

#### A bucket may name several languages

Two languages can reach the SAME library symbols: TypeScript and JavaScript are
read by one front end and produce the same callee signatures, so the symbols
their code can mention are one list rather than two. Writing that list twice
invites the two copies to drift, and a catalogue whose halves disagree is a
catalogue whose behaviour depends on which language the file happened to be
written in.

So a bucket key may name several languages, separated by commas:

```yaml
    by_language:
      typescript,javascript,arkts:
        - pattern: '^(?:node:)?child_process\.(exec|execSync)(/\d+)?'
          arg_index: 0
```

Each named language gets the patterns, and each is checked against the family's
own `languages:` gate on its own: a bucket that names a language the family does
not cover has that language's share dropped, and the loader says so.

#### The script languages: a catalogue keyed on the module

TypeScript, JavaScript and ArkTS reach their libraries through MODULES rather
than through classes: `child_process.exec` is a function of the
`child_process` module, and there is no class to name. The catalogue therefore
names the module the function was imported from.

| Callee key | What it is |
| --- | --- |
| `child_process.exec/2` | `exec` imported from the `child_process` module |
| `node:child_process.execSync/2` | the same module under the name Node 16 and later prefer |
| `app.eval/1` | the global `eval`: a free function has no receiver, so the owner is the module the FILE belongs to |

Naming the module is what keeps the rule precise. A catalogue that named the
method alone would claim every `exec` in the program -- including
`RegExp.exec`, which runs a regular expression and not a command, and it is one
of the most common method names in a script program.

The two shapes differ for a reason worth knowing. A module-level function is
reached through the module, so its owner is the module; a free function has no
receiver object at all, so the receiver slot holds the module's name as a
constant and the owner is the module the FILE belongs to. That is why the
`eval` pattern names the method alone (`\.eval\b(/\d+)?`) while the
module-level patterns name the module.

#### The agreement needs a test that goes through the whole chain

The catalogue and the front end agree on a CONTRACT, and the contract is the
naming convention above: the owner of a call to a module-level function is
the MODULE the function was imported from. The catalogue says
`child_process.exec`, and the front end has to produce exactly that name.

Nothing checks that agreement on its own. A catalogue test builds its TAC by
hand, so it proves the catalogue matches the names the TEST wrote down. A
front end test proves the front end emits the names it was WRITTEN TO emit.
Neither notices when the two disagree -- and they can disagree, because the
convention has to be implemented on both sides.

When they disagree, the symptom is the worst kind: no crash, no warning, a
scan that reports the program clean. A program that runs a tainted command
looks exactly like a program that does not, and the difference is a string
that does not match.

So the check goes through the whole chain -- source, front end, TAC, engine,
catalogue, FINDING -- and the assertion is on the finding, because the
finding is the product and the TAC is only a means to it.

**One chain test per CONVENTION, not one per language.** The convention is
what has to be pinned, and the script languages have more than one:

| Convention | What it looks like | Where it is pinned |
| --- | --- | --- |
| the owner is the MODULE the function was imported from | `child_process.exec`, `re.compile` | the chain test for the command family |
| the owner is a CLASS | `document.write` is owned by the `Document` TYPE | `ScriptSinkFamilyEndToEndTest` |
| the tainted value is the call's RESULT | `socket.recv` is a SOURCE: the bytes that arrived are what the call RETURNS | `ScriptSinkFamilyEndToEndTest` |
| the owner is a NAMESPACE | a PHP global function's owner is the namespace its name was qualified with | `ScriptSinkFamilyEndToEndTest` |

#### The script semantics table names the operation, not the owner

The library-semantics table decides whether a call carries its receiver's taint
into its result, and the taint engine consults it before it treats a call as a
string passthrough. It is keyed on the callee key, and a key carries an owner
only when the front end could resolve the receiver's type. In a script language
a string is a PRIMITIVE, and a primitive type carries no class symbol: measured
against the TypeScript compiler, the type of a string receiver reports no
symbol at all, while an array receiver reports `Array` and a class instance
reports its class.

So the operations that carry the taint through a script program -- the string
ones -- are exactly the ones a table keyed on owners could not name. The script
table therefore names the OPERATION:

```java
LanguageSemantics.Entry.byMethod("trim", TaintBehaviour.PRESERVES)
```

The comparison ignores case, the same way the engine's own method-name
classification does: the two have to agree, or a call the engine calls a trim
would find no PRESERVES entry and the taint would stop there. The cost is that
a method-name entry cannot tell a string's `trim` from a user object's `trim`,
which is why the table lists only operations whose behaviour is the same
wherever they are spelled.

#### Python: the same shape, and the alias resolved away

Python reaches its libraries the way the script languages do -- through MODULES
-- and the front end resolves the alias away, so the catalogue names the module
the function was IMPORTED from rather than the name the program wrote.

| Callee key | What it is |
| --- | --- |
| `os.system/1` | `os.system`, and also `from os import system` |
| `subprocess.run/1` | the subprocess family |
| `builtins.eval/1` | a builtin: the owner is the module Python itself provides it from |
| `pickle.loads/1` | the bytes are the first argument |
| `os.environ.get/1` | an environment variable: the program did not choose its value |

Two rules follow from the shape. A rule that named the method alone would claim
every `loads` in the program, and `json.loads` -- which parses JSON and builds no
objects -- is the most common one there is. And a builtin is named by the module
Python provides it from, so `eval` is `builtins.eval` and not `eval`.

Python's semantics table is a method-name table for the same reason the script
one is. A Python string is a primitive, and when the front end cannot prove a
receiver's type it falls back to the module the file belongs to: only a
parameter WITH an annotation arrives with a type, so an owner-keyed table would
name the annotated case and lose the ordinary one.

What Python does not get, and why:

- `socket.connect`, and the other methods of an object the program built: the
  receiver's type is not provable, so the owner is the module the file belongs
  to and the call has no name to be matched by.
- A file read: the content arrives through a later call on the file object, and
  that call has the same owner with no name.

#### PHP: the qualified name PHP itself writes

PHP qualifies a name with its namespace, and a global function is written with
a leading backslash. The catalogue names the qualified name PHP itself writes:

| Callee key | What it is |
| --- | --- |
| `\system/1` | a global function: `system`, and a call to it from inside a namespace too |
| `App\Support\sanitize/1` | a function of a namespace |
| `App\Http\Greeter::greet/1` | a static method |
| `<php>.include/1` | `include`, `require` and `require_once`: language constructs, so the front end gives them a synthetic owner |

Two things follow from that. A call to a built-in is a BLACK BOX -- the front
end did not resolve it -- so the semantics table decides whether the taint
crosses it, and its DISSOCIATES entries are what stop the taint at the calls
that really do drop it: a parsed number is not the text it was parsed from,
and a digest is not the text either.

And the method name has to be read with PHP's separator in mind. A global
function's key has no dot in it at all -- `\trim/1` -- so a reader that splits
on dots alone names the whole thing, and the method-name lists never match.
The engine's reader and the semantics table's reader now both split on a dot
OR a backslash, because the two have to agree.

Every name in the PHP bucket ends with a word boundary, and that is not
decoration. The engine matches a sink pattern as a SUBSTRING, so a pattern
that named `system` without a boundary would also claim `systemctl` -- and a
project that defines its own `system_info` would be reported as command
injection.

What PHP does not get, and why:

- `eval`: the front end lowers it to an unknown value rather than to a call,
  so there is no callee key for a rule to name.
- The superglobals `$_GET`, `$_POST` and the rest: they are container reads
  rather than calls, so there is no callee key for a rule to name. They are
  covered by the second kind of source declaration, below.

#### Sources that are not calls: source variables

Every other source in the catalogue is a callee signature, and the catalogue
matches on exactly that. A PHP superglobal is not a call -- `$_GET['user']` is
a container read -- so no signature exists to name, and the value arrives with
no marker at all. `$_GET['x']` flowing into `system()` is the most classic PHP
vulnerability there is, and a catalogue that can only name calls sees nothing.

So a source family may declare SOURCE VARIABLES: the names of variables that
carry untrusted data, scoped by language.

```yaml
taint.sources.web:
  source_variables:
    php:
      - '_GET'
      - '_POST'
      - '_REQUEST'
      - '_COOKIE'
```

The engine seeds them at the function entry, beside the parameters, because a
superglobal is a trust-boundary entry point in exactly that sense: the request
reached the program through it. The label it carries is the `input:` one the
rest of the engine already understands, so the value keeps its taint across a
constant assignment the way a parameter's does.

The scoping is the whole point. The name `_GET` means "the request's query
string" in PHP and nothing at all in any other language, so the declaration
names the language and the engine asks for the names of the language it is
analysing. A rule that applied everywhere would claim every Java program with
a field called `_GET`.

Two names are deliberately absent, and the reason is the difference between a
request and a configuration. `$_SERVER` mixes the request's headers with the
server's own settings, so marking the whole array untrusted claims values the
attacker does not control; `$_FILES` holds a temporary name PHP generated.

#### An entry of a container: the script languages' process-level inputs

A source is not always a variable either. The script languages read their
process-level inputs out of a container -- `process.env`, `sys.argv` -- and the
key is in the IR: the read lowers to an `ARRAYLOAD` whose base is the container
and whose index is the constant key. So a declared name may be a PATH, and the
engine recognises it where the read is.

```yaml
taint.sources.env:
  source_variables:
    typescript,javascript,arkts:
      - 'process.env'
```

The entry and not the container is the point. `process.pid`, `process.platform`
and `process.cwd` are facts about the machine, not about the attacker, so a
rule that named the whole `process` object would claim them.

This closes an inconsistency rather than adding an idea: the catalogue already
treats `os.Getenv` and `os.Args` as sources for Go, `System.getenv` for C# and
`System.getProperty` for Java. The script languages were the only ones with no
equivalent, and they are the ones whose inputs are read out of a container.

#### The script languages' own sinks: where the value lands

A rule layer that names only the sources is half a rule layer. Once the script
languages can read `process.env` and `sys.argv`, the next question is where that
value LANDS -- and the answer is a set of APIs the catalogue did not name.

Each of them lands in a family that already has a rule reading it, so a new
pattern reaches a finding instead of a match that leads nowhere:

| Family | The rule that reads it | What the scripts add |
| --- | --- | --- |
| `log.sinks` | `dfa-taint-log-injection` | `Console.log`, `logging.info`, `error_log`, `syslog` |
| `sql.sinks` | `dfa-taint-sql-injection` | `mysql.query`, `pg.query`, `knex.raw`, `mysqli_query`, `PDO::query` |
| `header.sinks` | `dfa-taint-http-response-splitting` | `header`, `mail` |
| `cookie.sinks` | `dfa-taint-cookie-injection` | `setcookie`, `setrawcookie` |
| `reflection.sinks` | `dfa-taint-unsafe-reflection` | `call_user_func`, `call_user_func_array` |

Three things decide how a pattern is written, and all three were MEASURED
against the side cars rather than guessed.

**Where the value sits in the argument list.** The engine reads the tainted
argument as `user argument N`, and the TAC keeps the RECEIVER in `args[0]`. For a
script module call the receiver is the module; for a PHP global function it is
the namespace the name was qualified with. Either way the first user argument is
`args[1]`.

| Call | The tainted value | `arg_index` |
| --- | --- | --- |
| `Console.log(input)` | the first user argument -- and the second as well, because `console.log` prints every argument it is given | `[0, 1]` |
| `logging.info(name)` | the first user argument | `0` |
| `error_log($name)` | the first user argument | `0` |
| `syslog(LOG_ERR, $name)` | the SECOND user argument -- the priority comes first | `1` |
| `mysql.query(input)` | the first user argument | `0` |
| `mysqli_query($link, $name)` | the SECOND user argument -- the connection comes first | `1` |
| `PDO::query($name)` | the first user argument | `0` |
| `header($line)` | the first user argument -- the name and the value are one string there | `0` |
| `mail($to, $subject, $body)` | the SECOND user argument -- that is the subject, and a subject is a header | `1` |
| `setcookie('a', $name)` | the SECOND user argument -- the cookie name comes first | `1` |
| `setrawcookie('a', $name)` | the second user argument -- the cookie name comes first | `1` |
| `call_user_func($name, $arg)` | the FIRST user argument -- that is the callable | `0` |

**What a name may claim.** The engine matches a pattern as a SUBSTRING, so every
name in these buckets ends with a word boundary: `Console.logger` is not a log
call, `header_size` is not a header call, and `mysqli_query_all` is not a query.

**Which language a bucket serves.** A bucket is scoped to the language it was
measured in. `error_log` is a PHP sink and not a Java one, and `Console.log` is a
script sink and not a Java one -- a Java program has neither.

**What a PHP program can shadow.** PHP lets a program define a function of the
same name as a built-in, and the front end gives both the same callee key: a
program that defines its own global `mail()` and a call to the built-in both
arrive as `\mail/3`. So a pattern that names a PHP global names that program's
own function too. That is the price of naming PHP's globals at all, and it is
the price the command functions already carry.

Three things the catalogue deliberately does NOT name, and why:

- **A response written through a variable.** In a script program the response
  object is a local -- `res.setHeader(...)`, `res.cookie(...)` -- so the owner is
  whatever the program called the variable, and a pattern loose enough to name it
  would name every `.setHeader` in the program.
- **A SQL call on a cursor.** In Python the owner of `cursor.execute` is the
  module the FILE belongs to, not the class of the cursor: the front end does
  not name the class of an object it only sees through a local. There is no name
  for a pattern to point at, so the Python SQL sink is not in the catalogue yet.
- **ArkTS's console.** Measured against its side car, the owner of `console.log`
  there is the FILE's module name and not the `Console` type. The same shape
  keeps `process.stdout.write` out of the script bucket: its owner is the module
  of the file, not a class.

#### The script languages' own sinks: the format, the pattern, the page

The second pass at the script languages' sinks asks the first pass' question --
where does the tainted value LAND -- about the APIs that turn a value into text,
into a pattern, or into a page.

| Family | The rule that reads it | What the scripts add |
| --- | --- | --- |
| `format-string.sinks` | `dfa-taint-format-string` | `util.format`, `printf`, `sprintf`, `vprintf`, `vsprintf` |
| `regex.sinks` | `dfa-taint-regex-injection` | `re.compile` and its siblings, `preg_match` and its siblings |
| `xss.sinks` | `dfa-taint-xss-injection` | `Document.write`, `django.utils.html.mark_safe` |
| `open-redirect.sinks` | `dfa-taint-open-redirect` | `django.shortcuts.redirect` |

**Where the value sits.** The same rule as the first pass: the receiver is
`args[0]`, so the first user argument is `args[1]`, and `arg_index` counts user
arguments from there.

| Call | The tainted value | `arg_index` |
| --- | --- | --- |
| `util.format(fmt, input)` | the FIRST user argument -- the format string | `0` |
| `sprintf($fmt, $x)` | the FIRST user argument -- the format string | `0` |
| `re.compile(pattern)` | the FIRST user argument -- the pattern | `0` |
| `preg_match($pattern, $subject)` | the FIRST user argument -- the pattern | `0` |
| `document.write(text)` | the FIRST user argument -- the text | `0` |
| `mark_safe(text)` | the FIRST user argument -- the text | `0` |
| `redirect(target)` | the FIRST user argument -- the target | `0` |

**Three owners, three shapes.** `util.format` is owned by the MODULE the
function came from, and that module may be spelled `util` or `node:util` -- the
name the runtime prefers -- so the pattern accepts both. `re.compile` is owned
by the `re` module. `document.write` is owned by the `Document` TYPE: it is the
one case where the owner is a class rather than a module.

**What a pattern must not claim.** A bucket that names `re.compile` must not
name `re.escape` -- that one escapes a pattern rather than using one -- and the
same goes for `preg_quote` and `django.utils.html.escape`. Nor does a name that
merely starts with the sink's name count: `util.formatAll` is not a format
call, and `Document.writeAll` is not a write. Every one of those has a test
that says so.

**A source is the other way round.** `socket.recv` is a SOURCE, and a source's
pattern matches the CALL while the tainted value is the call's RESULT -- the
bytes that arrived -- so a source bucket carries no `arg_index` at all. A sink
bucket names an argument; a source bucket names a result. That is the whole
difference between `taint.sources.network` and the four families above, and it
is why the source pattern is written without an argument index.

**What the constructor rules out.** `new RegExp(userInput)` and `new
Function(userInput)` are the script languages' regex injection and code
injection, and the catalogue has a family for each. They arrive as a NEW
instruction, and a NEW carries the class it builds but no callee signature,
while the engine's constructor path needs one to look the family up -- it
returns when there is none. The pattern would be easy to write; what is missing
is the name to write it against.
