## 0. 判定口径（沿用 `02` §0，不重新发明）

一个构念算「完整表达」，当且仅当同时满足四条：

1. **可表达**：运行期语义能由「指令流 + CFG + 元数据」完整刻画。
2. **可判定**：需要判断的性质（污点、范围、可空性）能从这份 IR 静态推出。
3. **不撒谎**：降级后的形状**不得**断言源码里没有的事实。
4. **可追责**：降级必须留下机器可读的凭证（`TacDrop`），不能只留一行日志。

**第 4 条是本轮的抓手**。过去的降级只在前端日志里留一句 `LOG.debug`，扫描照样「成功」，缺失的发现读起来和「代码是安全的」一模一样。现在每个降级都进 IR。

## 1. IR 层：这一轮补齐的两组能力

### 1.1 第一组（上一轮）：降级的机器可读凭证

| 类型 | 内容 |
|---|---|
| `TacDrop` | `construct`（稳定机器 id）、`detail`（人读文本）、`impact`、`line`、`column`、`scope` |
| `IrPrecision.SOURCE_DEGRADED` | 「语义丢了」这一档，枚举**末尾追加**（序列化按名字，追加是兼容的） |
| `TacValueDomain` | 数值宽度进类型（`INTEGRAL/FLOATING/FIXED_POINT/UNBOUNDED/DYNAMIC`） |

**精度规则（不变）**：`SEMANTICS ⇒ SOURCE_DEGRADED`；`STRUCTURE ⇒ SOURCE_LOWERED`；`VALUE`/`TYPE` 不降精度。
**精度由 drop 推导**，前端不许自报：`TacBuilder.build()` 用 `TacFunction.combine(irPrecision, drops)` 取**更差**的一档；`TacFunction.aggregatePrecision` 把同一口径提升到**文件**级。

### 1.2 第二组（本轮新增）：把「构念的种类」和「条件的形状」带进 IR

这四条能力全部是「**加字段**」或「**枚举末尾追加常量**」，没有新 opcode、没有新 operand 变体、没有新 `TacType.Kind`。

| 新增 | 位置 | 承载什么 |
|---|---|---|
| `TacGuard` | `plumb-tac/.../ir/TacGuard.java`（新） | 分支的**结构化条件**：`TRUTHINESS` / `COMPARE` / `PROPERTY_PRESENCE`。守卫是程序对自己值说的话，规则可以**用它消掉**一条发现，**绝不能**用它**加**一条发现 |
| `TacLabelRef` | `plumb-tac/.../ir/TacLabelRef.java`（新） | 标签的**种类**：`LOOP_HEAD` / `LOOP_END` / `SWITCH_CASE` / `SWITCH_END` / `BLOCK` / `CATCH` / `FINALLY_ENTRY` / `OTHER`。没有它，引擎分不清「循环的末尾」和「循环体的末尾」 |
| `TacMemberKind` | `plumb-tac/.../ir/TacMemberKind.java`（新） | 成员是**什么**：`METHOD` / `CONSTRUCTOR` / `GETTER` / `SETTER` / `FIELD_INITIALIZER` / `STATIC_INITIALIZER` / `FUNCTION` / `MODULE` / `UNKNOWN`。`null`（没人说）与 `UNKNOWN`（有人说了但本版不认识）是**两个事实** |
| `TacType.unionMembers` | `plumb-tac/.../ir/TacType.java` | 联合类型按**成员集合**保存。把成员名拼成一个字符串会产生一个程序里根本不存在的类型名 |
| `TacInstruction.ownerType` / `.guard` / `.labelRef` / `.branchRegion` | `plumb-tac/.../ir/TacInstruction.java` | 字段访问的**归属类型**、分支的守卫、跳转的标签种类、分支所属的块 |
| `TacFunction.memberKind` | `plumb-tac/.../ir/TacFunction.java` | 函数是**什么成员** |
| `BinaryOperator.LOOSE_EQ` / `LOOSE_NE` | `plumb-tac/.../ir/BinaryOperator.java` | 枚举**末尾追加**（按名字序列化，兼容） |

**`TacBuilder.setMemberKind(...)`**（`plumb-tac/.../translate/TacBuilder.java`）是这组能力进前端的入口：前端说得出就说，说不出就留空，引擎把「没人说」当成「什么也没主张」。

### 3.2 集成时发现并修掉的**两个真实缺陷**（不是风格问题，是断链）

这两个都不是「精度差一点」，是**调用边直接断了**。

#### 缺陷一：Python 匿名 lambda 的 `calleeSig` 带了**双前缀**

worker 把匿名 lambda 改成「捕获值存在闭包对象里」的形状后，闭包记录的 `name` 已经是 `module.closure$1`，而调用侧的 `calleeSig` 又拼了一次 owner ⇒

```
calleeSig = "probe_app.probe_app.closure$1/0"
```

而被调函数自己的签名是 `probe_app.closure$1(...)` ⇒ **调用方找不到被调方** ⇒ 闭包体在调用图上不可达。

**改法**：`lambda_by_node` 里存**裸名**（`closure$1`），owner 由 `calleeSig` 的拼接负责。

#### 缺陷二：Python / PHP 的闭包**捕获值不在实参里**

worker 的形状把捕获值改成「只存在闭包对象里，调用时不传」。这条在**引擎侧不成立**：

* 引擎按 `args[1..]` 位置绑定形参（`TaintedCheckerBase.java:5510` 的 `maxParams = ins.args.size()-1` ⇒ 调用方参数 0 落在 `args[1]`）。
* **引擎从不把接收者（`args[0]`）绑定给被调方的任何形参** ⇒ 闭包从接收者里读捕获值，读到的是**未绑定**的变量 ⇒ 闭包体内的 sink **看不到**捕获值的污点。
* 而「捕获值是形参」这件事，在引擎里**恰好**是安全的：形参在函数入口就被种成污点源（`markSource(p, "param:" + p.name(), …)`），闭包体因此**按最坏情况**被分析，**闭包内的发现不会丢**。

**改法**（PHP 与 Python 都改）：捕获值回到**前导形参**，调用点把捕获值作为**前导实参**传过去 —— 与仓库里 Python 嵌套 `def` 的既有做法（`sink_in_closure(any,any)`，实参 `[receiver, value, x]`）一致。

**PHP 还多一处**：worker 给闭包函数的形参列表塞了一个 `recv`（接收者）占位，于是**捕获值与用户实参整体错位一位**。接收者**不能**是形参 —— TAC 的约定是接收者住在 `args[0]`，形参从 `args[1]` 开始。

> **这一条是本轮新发现的「引擎侧能力缺口」，进 §5 的清单**：IR 能表达闭包，但**引擎没有绑定接收者的机制**，所以「把捕获值交给闭包体」只有一种不失真的做法 —— 捕获值当形参。代价是：一个**干净**的捕获值在闭包体内仍被当作污点源（过近似，方向安全）。

### 3.3 Go / C# 的 **Java 侧**接线（本轮补）

Go 与 C# 的前端**不走** `SidecarTacMapper`，各自留了一份 wire 映射。那份拷贝是 wire 协议 v2 之前的，于是：

* **没有 drop 通道** ⇒ 前端只能靠 sidecar 自报的 `precision`，而 `SOURCE_DEGRADED` 这个值**根本没有被映射**（只认 `SOURCE_LOWERED`，其余一律当 `SOURCE_FULL`）⇒ **一个降级到 `SOURCE_DEGRADED` 的函数，在 Java 侧读出来是 `SOURCE_FULL`**；
* 没有 member kind、没有 try 区域、没有注解五通道；
* 指令级的 `guard` / `labelRef` / `ownerType` 全丢；
* 类型级的 `nullable` / `unionMembers` / `domain` 全丢；
* **未知 binop 回落 `ADD`** ⇒ 一个比较被当成加法（静默错值）。

**改法**：把 `SidecarTacMapper` 变成 `public`，把它的映射公开出来，**Go / C# 两个前端改为委托**。一份映射，一套规则。

**证据**：`CSharpPropertyLoweringTest.awaitDowngradesThePrecision` 原来期望 `SOURCE_LOWERED`，读到的是 `SOURCE_FULL`；改完之后读到的是 `SOURCE_DEGRADED` —— 这不是回归，是 drop 通道带来的**更细的分级**：`await` 丢的是「挂起点」与「恢复顺序」，两者都是**运行期事实** ⇒ `SEMANTICS ⇒ SOURCE_DEGRADED`，比笼统的 `SOURCE_LOWERED` 更强、更准。

**补（本轮）**：Java 侧改成委托之后，**文件级**精度还差一步 —— Go / C# 两个前端各自算文件精度，没有用 `TacFunction.aggregatePrecision(defaultPrecision(), functions)`（TS / PHP / Python 一直用它）。后果：一个文件里只要有一个函数带 `SOURCE_DEGRADED` 的 drop，**文件级**精度仍报 `SOURCE_FULL` ⇒ 覆盖报告说这个文件「完全理解」，而它里面有一个降级函数。已改为与其它四种语言同口径。

### 3.4 Go / C# 的**协议缺陷**（本轮补）

| 缺陷 | 后果 | 改法 |
|---|---|---|
| **C# 的 `tryRegions` 在 wire 上是标签字符串**，映射器按**指令下标**读 | 异常边**一条都没接上** ⇒ `catch` 体在异常路径上不可达 ⇒ 流进它的污点**静默丢失** | `Drops.cs` 的 `TryStart/TryEnd/FinallyStart/FinallyEnd` 改为 `int`，并新增 `CatchStart/CatchEnd`；`TacTranslator.cs` 用 `_instructions.Count` 算下标（try / catch / finally 三处）。Go 侧 wire 类型同步改为 `int`（Go 无 try/catch，实际未填充，属**消除陷阱**） |
| **guard 载荷的键名不匹配**：四个 sidecar 写 `operand`，映射器读 `subject` / `lhs` | **所有真值性 guard 的 subject 为 null** ⇒ 引擎读不到被测的值 ⇒ 「条件不成立 ⇒ 不报」这条抑制失效 | `SidecarTacMapper.toGuard` 的 subject 依次回退 `subject` → `lhs` → `operand`；property-presence 回退 `property` → `propertyName` → `key`，缺 subject 时取 `receiver`。**一处修改修好四种语言**，不改 sidecar 的 wire 协议 |

> **踩坑记录**：第一次用「早退」写 finally 区域会跳过 `afterTry` / `endLabel` 标签，**破坏控制流** ⇒ 改为变量赋值（`finallyStartIndex` / `finallyEndIndex`）后再取下标。

### 3.5 TS 的**装饰器**（本轮补）

TS 前端此前只把装饰器的**名字**记进注解通道，**装饰器本身作为一次函数调用完全没有进入 TAC**。后果：装饰器实参里的污点（例如 `@Authorize(user.role)` 里 `role` 来自外部输入）在 TAC 里断了；一条按装饰器名字匹配的规则也永远匹配不到。

**改法**（照抄 Python 前端 `lower_decorators` 的既有形状）：

- 装饰器调用 = 一条 `CALL`，`calleeSig` = `<owner>.<decoratorName>/<arity>`，**owner 是装饰器自己的归属**（它被 import 的模块，或声明它的模块），**不是**占位 owner —— 占位 owner 的意义是「绝不可能和真实包名撞上」，但那会让「按装饰器名字匹配的规则」永远匹配不到，与目标相反；
- `args` = `[常量 owner 槽, 装饰器表达式的值, 被装饰函数的持有者]`，随后一条 `MOVE` 把 CALL 的结果写回持有者；
- **装饰器在「定义处」运行，不在「调用处」运行** ⇒ CALL 落在**类自己的流**（`<init>` 或字段初始化器函数）里、或**模块级的合成流**（`__top`）里，**绝不**落在被装饰函数自己的函数体里（那会让它每次调用都跑一遍）。

**降不了的形态**：**参数装饰器** `@(p: T)` 没有可写回的持有者 ⇒ 记 `UNHANDLED_NODE`（不是 `SEMANTICS` drop —— 那是另一个决定，见 §5）。

### 3.6 TS / ArkTS 的**自由全局函数**：owner 与规则目录对齐（本轮补 —— 这是**上一轮留下的真漏报**）

这一条是本轮**跑 `plumb-dfa`** 才发现的：上一轮按设计 `05` §5.3.8 改了 TS sidecar 的 owner 约定（**自由全局函数的 owner 是它来自的那个全局**），**却没同步规则目录（sink catalogue）**，也没跑引擎的测试。

**同一个问题，三处三个答案**：

| 位置 | 它说「自由全局函数的 owner 是」 | 谁在认领 |
|---|---|---|
| 规则目录（`sink-families.yaml`） | `<unknown>` —— 上一轮之前 TS 前端就是这个形状 | 目录里 `^<unknown>\.eval\b(/\d+)?` 与 `^<unknown>\.fetch\b(/\d+)?` 两条 |
| 设计 `05` §5.3.8 的**owner 五级链** | **已知全局内建 ⇒ owner = 全局名**（`require("./x") ⇒ "require"`） | —— |
| TS sidecar 的协议文档 | 「保留自己的名字作 owner，**因为目录就是照它写的**」 | —— |
| TS sidecar 的实现（上一轮） | 保留自己的名字（`eval.eval/1`） | **目录里没有任何一条能匹配 `eval.eval/1`** |

⇒ **全局 `eval` / `fetch` 不再是 sink**：一个把外部输入交给 `eval()` 的 TypeScript 程序，扫描**干净通过** —— finding 不在了，而扫描报告「成功」。这正是本项目要消灭的那种「静默」。

**为什么没被发现**：

1. 上一轮的回归表（`14` §7.2）**没有 `plumb-dfa` 这一行** ⇒ 引擎侧的白名单测试（其中 3 条正守着这件事）**根本没跑**；
2. TS sidecar 的 smoketest 里确实有一条断言守着它，但**断言写得太松**：`s.includes(".eval/")` —— 而**正确**形状 `eval.eval/1` 里**也有** `.eval/` ⇒ 它因为**分不清对错**而通过了（当时的实现形状与正确形状不同，断言却都对它成立）。

**改法**（**前端不动** —— 上一轮的实现是**对的**，它就是设计 `05` §5.3.8 的第四级）：

- 规则目录：两条 TS / JS / ArkTS 匹配式改为 `^eval\.eval\b(/\d+)?` 与 `^fetch\.fetch\b(/\d+)?`；
- 两份 sidecar 协议文档里那句「因为目录就是照它写的」在上一轮的前提是**假的**（目录写的是 `<unknown>`）；现在目录真的照它写了，那句话才成立 —— 文档补上了**为什么这个形状更好**（见下表）；
- TS smoketest 的断言改严：`.includes(".eval/")` → `.startsWith("eval.eval/")`，并把「保留文件自己的模块作 owner」的说法换成「属于它来自的那个全局，并以那个全局的名字作 owner」。

**这个形状比旧的 `<unknown>` 方案更准**（量出来的）：

| 源码 | 旧（`<unknown>` 方案） | 现在 |
|---|---|---|
| 全局 `eval(input)` | `<unknown>.eval/1` | `eval.eval/1` |
| 未知接收者的 `obj.eval(input)` | `<unknown>.eval/0` | `eval/1`（**没有 owner 段**） |
| 目录认不认领「未知接收者」那个 | **会**（两条都被认领 ⇒ 一次误报） | **不会**（键不以 `eval.eval` 开头） |
| 未知接收者的 `obj.format(input)` | `<unknown>.format/0` | `format/1`（不变） |
| `console.log(input)` | `Console.log/1` | `Console.log/1`（不变） |
| `JSON.parse(input)` | `JSON.parse/2` | `JSON.parse/2`（不变） |
| `process.stdout.write(input)` | `<unknown>.write/0` | `write/1`（不变） |

⇒ 旧方案把「全局 `eval`」与「类型定不出来的某个对象上的 `eval`」**混成同一个键**（只差一个 arity，而目录的 arity 是可选的 ⇒ 两者都认领）；新方案把它们**分开了**。

**因此有一条 finding 口径变了（不是退化，是精度提升）**：接收者类型定不出来的 `obj.eval(tainted)` / `obj.fetch(tainted)`，**旧方案会报**（那是一次误报 —— 它不是全局 eval），**新方案不报**。方向是保守的（少一次误报），代价是这类程序少一条 finding。

### 3.7 C# 的**值流与可达性**、Go 的 **channel range**（本轮补 —— 探针实测出来的）

这一轮**没有**先看设计文档，而是先写了一个**探针**：直接驱动 sidecar 走它的 wire 协议，把构造喂进去，把 TAC 打出来。设计文档的「改动清单」写着这些构念该长什么样，**代码却不是那样**。

⇒ 探针测出来的六处**真缺陷**，每一处都是「值不对」或「路径不可达」，而扫描**报告成功**。

#### 3.7.1 C# 的 `switch`：**第二个及以后的比较从不执行**

`switch` 的比较链里，每条比较的**假边**指向**下一个 case 的体**标签。而体标签定义在整条链**之后** ⇒ 假边**跳过**了后面所有比较。

```
BINOP t1 = mode == 1
BRANCH t1 ? case_2 : case_3      ← 假边直接落到 case 3 的体
BINOP t2 = mode == 2             ← 不可达：没有任何边指向这里
BRANCH t2 ? case_4 : case_5
BINOP t3 = mode == 3             ← 不可达
BRANCH t3 ? case_6 : case_8
```

⇒ 三个 case + 一个 `default` 的实测结果：**`case 2` 的体在没有被测试过的情况下进入**（程序里没有这条路径），**`case 3` 的体与 `default` 的体在 CFG 里不可达** ⇒ **里面的 sink 永远走不到** ⇒ **漏报**。

**改法**：每个 case 标签有自己的**测试标签**，假边指向**下一个测试**（不是下一个体）。这与 Go 侧车**早已有的**形状一致 —— Go 的 `translator.go` 里有一段注释写着这件事（「假分支指向**下一测试**……它以前指向**体**，于是第一个之后的每个值都不可达」）。⇒ **同一个缺陷，Go 修过、C# 没同步**。

**模式 case**（`case int i:`、`case int i when i > 3:`）原先**整个被忽略**：不比较、守卫丢失、模式变量**从未被绑定** ⇒ 那个变量是个谁都没赋过值的名字。⇒ 现在：类型测试用 `INSTANCEOF`，模式变量在匹配路径上 `MOVE`，`when` 守卫作为**第二条**分支（守卫读的就是刚绑定的变量 ⇒ 绑定必须在守卫之前）。

#### 3.7.2 C# 的 `foreach`：循环变量绑的是**集合本身**

```
MOVE item = list          ← 程序在这里是「元素」
```

⇒ 元素的值是**错的类型**、**错的污点**：元素是污点而集合不是 ⇒ 漏报；集合是污点而元素不是 ⇒ 误报。

**改法**：走**真迭代协议**（真实方法名）：`GetEnumerator/0` → `MoveNext/0` → `get_Current/0` → `Dispose/0`，循环变量拿的是 `get_Current` 的结果。**数组**走下标循环（数组的枚举器是编译器生成的隐藏类型，把它的名字写进 callee key 等于写进一个程序里不存在的类型）；**类型定不出来**时循环变量取**未知值**（`HAVOC`）—— 未知是**保守**的方向，而旧形状（绑集合）**既不保守也不正确**。

#### 3.7.3 C# 的**对象/集合初始化器**：接收者是一个**占位变量**

```
FIELDSTORE dest=CONST 2, lhs1=VAR "Sample"    ← 一个谁都没创建过的变量
```

`new Sample { Field = 2, Auto = 3 }` 原先被降成**两条独立赋值**（和语句 `Field = 2;` 一样的降法），而独立赋值是按**外层作用域**解析的 ⇒ 写到了**别的对象**的字段上；而 `Auto` 是**属性**，裸名不是属性 ⇒ 那条**被整个丢弃**（`the assignment's target could not be resolved`）。

⇒ 属性初始化器**没有产生任何 `CALL`** ⇒ 规则目录是**按 `CALL` 匹配**的 ⇒ 没有 `CALL` 就没有发现 ⇒ **漏报**。规则目录里本来就有 `^System\.Data\.SQLite\.SQLiteConnectionStringBuilder\.set_HexPassword(/\d+)?` 这一类形状 —— 现在它真的能被匹配上了。

**改法**：接收者是**刚创建的对象**；属性 ⇒ `CALL <owner>.set_P/1 args=[对象, 值]`；字段 ⇒ `FIELDSTORE` 写进那个对象；集合初始化器 ⇒ `CALL <owner>.Add/1`。

> **一个坑**：`creation.Type` 是**类型的语法**，不是符号 ⇒ 在它上面查成员永远查不到（集合的 `Add` 就这样丢的）。要查成员得用**语义类型**（`_model.GetTypeInfo(creation).Type`）。

#### 3.7.4 C# 的 `switch` 表达式 / 数组 / 元组 / `with`：**值整个丢了**

| 构念 | 原状 | 现在 |
|---|---|---|
| `switch` 表达式 | 整个表达式被丢 ⇒ 函数返回一个**谁都没算过的值** | 分支链 + **merge temp**（每个 arm 写同一个 temp） |
| `new int[] { 1, 2, 3 }` | 整个数组创建被丢 ⇒ **变量从未被赋值** | `NEWARRAY` + 逐元素 `ARRAYSTORE` |
| `(1, "two")` | 元组被丢 ⇒ 变量从未被赋值 | `NEW` + 逐元素 `FIELDSTORE`（`Item1`/`Item2`） |
| `s with { Field = 7 }` | 整个 `with` 被丢 | `NEW` 出副本 + **未改的成员逐个搬过去** + 改动的成员写进副本 |

#### 3.7.5 Go 的 `range` over channel：**循环体整块丢失**

```go
for value := range ch {
    sink(value)        ← 这条在 TAC 里不存在
}
```

实测：TAC 里只有一条 `<go>.chanRecv/1`，**循环体一个字都没有** ⇒ **循环里的 sink 永远走不到** ⇒ 漏报。

**改法**：接收放在**循环头**，接收的第二个结果（`ok`）是**退出条件**（通道关闭 ⇒ 循环结束），体在自己的标签下，`continue` 回到头、`break` 走到尾。

> **Go 侧车自己早就写好了这个形状的模板**（`rangeOverMap` 就是这么写的），只有 channel 这一支是「一次接收、然后什么都不做」。

#### 3.7.6 这一轮的**方法**：探针，而不是读代码

六处缺陷里有**五处**在代码里看不出问题 —— 降级函数返回了「看起来合理」的形状，测试全绿，门禁全绿。**只有把构造喂进去、把 TAC 打出来、把 CFG 建出来看可达性，才会发现「值是错的」或「路径不可达」**。

⇒ 因此本轮新增的测试**不看指令的位置**，只看**形状**与**可达性**：C# 的 `switch` 用例直接用 `TacCfgBuilder` 建 CFG、算可达块集合，断言**每个 case 体（含 `default`）都在可达集合里**。

### 3.8 TS / ArkTS：**条件从未求值**、带标签的 `continue` **跳错循环**、`catch` 的**模式没绑定**、展开**丢了源对象**；以及一处 **Java 侧**的 `labelRef` 丢失（本轮补 —— 探针实测出来的）

这一轮把探针从 C# / Go 扩到 **TS / ArkTS / PHP / Python**。头一个发现比上一轮那条还大：**TypeScript 的 `if` 和 `while` 的条件根本没有被求值**。

#### 3.8.1 `if` / `while` 的条件**从未求值**（TS 与 ArkTS）

实测：`if (a === b)` 降出来是一条 **`BRANCH`，它没有主语** —— `lhs1` 缺失、guard 是 `Truthiness` 但**没有 operand**、**比较本身一条指令都没有**。

根因不在翻译器，在**编译器的 AST 字段名**：`typescript/unstable/ast`（TS 7.0.2）里，`IfStatement` / `WhileStatement` / `DoStatement` 的条件字段叫 **`expression`**，而 `ForStatement` 与条件表达式叫 **`condition`**。翻译器读的是 `.condition` ⇒ 对 `if` / `while` 读到的是 **undefined** ⇒ `lowerExpression(undefined)` 返回 undefined ⇒ 分支**没有主语**。

⇒ 后果有三条，**每一条都是静默的**：比较**没有指令** ⇒ **条件的污点全丢**；分支**没有主语** ⇒ **路径条件全丢**（`GuardTracker` / `EqualityAllowlistTracker` 从 `if` / `while` 里学不到任何东西，空值守卫与等值白名单在这两种语言上等于没有）；而 TAC **格式良好、标签全解析、精度仍是 `SOURCE_FULL`、没有 drop** ⇒ **扫描报告成功**。

ArkTS **同病**：它用的是 `ohos-typescript@4.9.5`，那套 AST 里条件同样叫 `expression`；而且它的 `do` 连兜底都没有（TS 侧车至少写了 `node.condition ?? node.expression`）。

**改法**：统一读 `conditionOf(node)`（= `node?.condition ?? node?.expression`），五处读取点都用它。这个 helper 的注释里写明了**为什么不能写死一个字段名** —— 两个编译器家族各叫一个名字。

#### 3.8.2 带标签的 `continue` **跳到了内层循环**

`continue outer` 应当继续**标签所标注的那个循环**。翻译器却从**最内层**的作用域往外找第一个 `LOOP` ⇒ 拿到的是**内层**循环 ⇒ TAC 里 `continue outer` 跳的是内层循环的头 ⇒ **控制流是错的**。

标签的作用域是**先**入栈的，它标注的语句（那个 `for`）的循环作用域**后**入栈 ⇒ 正确的目标是**标签之后的第一个** `LOOP`，而不是最内层的那个。

⇒ **Go 侧车没有这个缺陷**（它用 `t.labelled[name]` 直接存被标注循环自己的 break/continue 标签），所以这是 TS / ArkTS 独有的。

#### 3.8.3 `catch ({ message })` 的名字**从未被赋值**

catch 的参数可以是**模式**。模式没有自己的名字（`parameter.name.text` 是 undefined）⇒ 翻译器走了「没有绑定」那一支 ⇒ `CATCH_HANDLER` **没有 dest** ⇒ **捕获到的值被整个丢掉**，模式里的名字**从未被赋值** ⇒ catch 体读的是一个**谁都没写过的变量**。**没有 drop，也没有 problem** ⇒ 完全静默。

**改法**：`CATCH_HANDLER` 落一个临时量，再用**已经存在**的 `bindPattern` 把模式里的名字绑上去。

#### 3.8.4 对象字面量的展开**丢了源对象**

`{ ...rec, y: "1" }`：展开项**没有 `name`** ⇒ 被 `if (!property.name) continue` 跳过 ⇒ 新对象**只有 `y`** ⇒ 源对象的属性**全丢** ⇒ **源对象的污点全丢**。没有 drop。

**改法**：建模成 `Object.assign(target, source)`，而且**故意用 `UNINTERPRETED` 而不是 `CALL`** —— 引擎看不进去 `Object.assign`，而**未知被调方按「保留实参的污点」处理**（`LanguageSemantics.preservesTaint` 对认不出来的被调方返回 **true**）⇒ 源对象的污点就进来了。若写成普通 `CALL`，因为没有 callee summary，结果**不会**被染色 ⇒ 等于没修。

#### 3.8.5 可选调用的**接收者是函数值而不是对象**

`rec.f?.()`：空值检查的对象**是函数**（对：可能缺的是函数），但**调用的接收者槽**也填了那个函数值 ⇒ 这个调用看起来像是「函数自己的方法」。接收者应当是**函数被读出来的那个对象** —— `this` 就是它。

**改法**：可选链里把两个角色分开：检查对象 = 函数值；接收者 = 对象。

#### 3.8.6 Java 侧：`labelRef` 被**整个丢掉**（影响所有 sidecar）

`SidecarTacMapper.toLabelRef` 用 `getString("scopeId")` 读一个**数字**字段 ⇒ 拿到 null；而 `name` 对所有**结构类**标签（`LOOP_HEAD` / `LOOP_END` / `SWITCH_CASE` / `SWITCH_END` / `BLOCK` / `CATCH` / `FINALLY_ENTRY`）本来就是 null（结构类标签没有自己的名字）⇒ `name == null && scopeId == null` ⇒ **整个 labelRef 被丢弃**。

⇒ 后果：**所有 sidecar** 的「哪个标签是循环头 / 循环尾 / case 体」这一层事实**全部消失** ⇒ 引擎无法判断「这条分支是不是离开了它所在的循环」——而那正是 `TacLabelRef` 存在的理由。

**改法**：数字按数字读；并且**只要 kind 认得出来就保留** labelRef。

#### 3.8.7 这一轮**没有**改的（记在案，附原因）

| 项 | 为什么不改 |
|---|---|
| **默认参数把传入的值盖掉**：`f(a, b = "d")` 在被调用方里无条件 `MOVE b "d"` | 引擎在调用点把实参绑给形参之后，这条 `MOVE` 又把它盖成常量 ⇒ **实参的污点在这里断掉**。两条修法都不是实现细节：① 不覆盖形参（但默认表达式里的**副作用**会一起消失：默认里若有 sink 就走不到）；② 在**调用点**把默认值补成实参（会改**调用的元数**，而目录按 `owner.method/arity` 匹配 ⇒ 规则的匹配面会变）。先要定一个口径 |
| **两条协议调用把实参放在 `args[0]`**：`Iterator[Symbol.iterator]/1` 与 `Object.keys/1` | 按约定 `args[0]` 是接收者、实参在 `args[1..]`。**但这两处不能"修正"**：引擎的 `propagateIteratorTaint` 正是从 `args[0]` 取**被迭代的数组**（Java 形状里 `args[0]` 就是接收者=数组），`isIteratorFactory` 认的也正是 `iterator` / `next` 这两个方法名 ⇒ 把实参挪到 `args[1]` 会让**迭代器的污点跨不过去** ⇒ 那是把「多报」改成「漏报」 |
| **基类构造器的实参没传**：`CALL Base.<init>/N args=[this]` | N 个声明参数一个都没传。改法要知道基类构造器的形参表，且要决定补出来的实参放在哪一格 |
| ~~**Python 的迭代器协议引擎认不出来**~~ | **这一条在本轮的后半段修掉了**（见 §3.9）：它不是一个缺口，是**三处叠在一起**的缺口 —— 方法名、容器元素污点所在的跟踪器、以及「容器本身就是污点」时的答案 |
| **类成员的 getter 被当成属性读** | `h.value`（`value` 是 getter）降成 `ARRAYLOAD h[value]`，getter 的函数体不执行。要改成「读属性 ⇒ 调 getter」需要知道这个属性是访问器 |
| **对象字面量里的 getter / 方法被存成属性值** | 读 `o.g` 拿到的是那个函数，不是 getter 的结果 |
| **IIFE 的函数体静默丢失** | `(() => src)()` 降成 `CALL <call>/0`，**没有 drop** —— 箭头函数当**被调方**时没有走「函数值」那条会记 drop 的路 |

#### 3.8.8 这一轮的**方法**：探针扩到四门语言，外加一条**结构不变式**

PHP 与 Python 的 `if` / `while` 条件**都在**（它们的解析器给的是正确的字段名），`foreach` / `for` 的迭代协议也都成形 ⇒ **四门里只有 TS 那一支有这个缺陷**，而 TS 那一支的根因是**字段名**，不是翻译逻辑。

这一轮还给探针加了一条**自动判据**，不必再靠人眼扫输出：**任何 `BRANCH` 都必须有主语**（`lhs1`）、guard 必须有 operand、每个 `CALL` 必须有 `calleeSig`、每个 `JUMP` / `LABEL` 必须有标签名。修复前，TS 的输出过一遍这条检查就报了 `BRANCH has no subject`；修复后干净。

### 3.9 Python：迭代协议**认不出来**、元素**读成了另一个东西**（本轮补 —— 探针实测出来的）

这一轮继续用探针，但探针的对象从「TAC 的形状」换成「**污点能不能穿过**」：把 Python 侧车真正降出来的 TAC 原样喂给引擎，看引擎的**结论**（`os.system` 有没有被报出来）。

上一轮（§3.8.7）记下过一条「Python 的迭代器协议引擎认不出来」，但只记了**症状**。这一轮把它**测透**了 ⇒ 症状是**三处**叠在一起，**每一处都得单独修**，只修一处仍然不报。

#### 3.9.1 探针实测：同一个程序，十种形状，十种结果

探针把 Python 侧车的真实输出（`__iter__` / `__next__` 两条 `CALL`）原样喂给 `DfaEngine`，看 `os.system/1` 有没有被报出来。**修复前**：

| 变体 | 修复前 | 修复后 | 说明 |
|---|---|---|---|
| Python 协议（`__iter__` / `__next__`），元素是容器的元素 | ❌ | ✅ | **本轮修的主目标** |
| Python 协议，容器**本身**就是污点 | ❌ | ✅ | `cmds = request["cmds"]` |
| Python 协议，但元素按**下标**读（没有协议） | ✅ | ✅ | **本来就是好的** —— 说明容器的元素污点**在**，只是迭代器**够不着** |
| Python 协议，但协议调用**穿 Java 的名字** | ❌ | ✅ | **名字不是唯一的障碍** |
| Python 协议，元素是 `__next__` 结果的 `["value"]` 成员 | ❌ | ✅ | 侧车原来的形状 |
| Java 形状（`iterator` / `next`） | ✅ | ✅ | **对照**：引擎的老路没坏 |
| 容器是干净的 | ❌ | ❌ | **反向对照**：干净容器**不该**报 |

⇒ **两条结论**：① 「引擎不认 Python 的方法名」只是**障碍之一**；② **同一个容器，按下标读元素是好的，按协议读元素就断了** ⇒ 断点在**迭代器与容器之间的那一步**，不在容器的污点记录上。

#### 3.9.2 侧车侧：Python 的 `__next__` 返回**元素本身**

侧车原来把元素读成 `ARRAYLOAD element = step["value"]` —— **`{value, done}` 那个形状是 JavaScript 的迭代器结果**，Python 的 `__next__` 返回的是**元素本身**，它到头时抛 `StopIteration`，不是返回一个带 `done` 标志的对儿。

⇒ 后果：**TAC 说「元素是 `__next__` 结果的一个成员」**，而引擎的迭代器传播染色的是**`__next__` 的结果** ⇒ 两者不是同一个值 ⇒ 元素**干净**。

**改法**：`__next__` 的 dest **就是**元素临时量（少一条 `ARRAYLOAD`）。JavaScript 侧车的同一处**不动** —— 那里 `step["value"]` 是**对的**。

#### 3.9.3 引擎侧：两个方法名认不出来

`isIteratorFactory` 认的是 `iterator`、`isIteratorNext` 认的是 `next`（Java / C# 的名字）。

**为什么不改侧车去凑这两个名字**：`02` §2 的 **IR-P** 写死了「迭代协议的 callee 名**必须是真实存在的语言方法名**」。Python 的迭代协议**就是** `__iter__` / `__next__` 这两个方法 ⇒ 侧车写的名字是**对的**，要改的是**引擎**。把侧车改成 `iterator` / `next` 反而是**把一个 Python 程序里不存在的方法名写进 TAC**。

**改法**：两个判定各自多认一个名字（`__iter__` / `__next__`）。这两个是 Python 的 **dunder** 名，其它语言不会撞上 ⇒ 对 Java / C# / Go 的行为**零影响**。

#### 3.9.4 引擎侧：**keyed 容器的元素污点不在数组跟踪器里**

这一条是探针逼出来的**最深**的一处，也是**只改名字不够**的原因。

引擎的迭代器传播问的是「这个容器的**元素**有没有污点」，问的是**数组跟踪器**（`ArrayTaintTracker.elementTaintOf`）。但 **Python 的下标是 keyed 的**（`SourceLanguage.PYTHON3.hasKeyedContainers()` 为 true）⇒ Python 的 `ARRAYSTORE` 走的是 **keyed store**（`AccessPathTaintStore`），**数组跟踪器是空的** ⇒ `elementTaintOf` 恒为 null ⇒ **迭代器永远拿不到元素的污点**。

⇒ 而「按下标读元素是好的」这件事**恰好证明了元素污点是在的**：那条路读的是 keyed store。

**改法**：容器的元素污点**按语言分开问** —— 数组位置的语言问数组跟踪器（**一个字都不改**，Java / C# / Go 的行为因此**逐字节不变**）；keyed 的语言问 keyed store，而**问的键是「每一个键」**（store 自己有 `MapKeySet` 这个通配符，它的含义正是「这个命名空间的每一个条目」）—— 因为迭代器问的是「容器里有没有脏东西」，不是「某个键上有没有」。

⇒ **顺带查清了一件事**：keyed store 的对象标签是 `type@site:context`（见 `AccessPathBuilder` 的注释），而 **store 是 `static` 的**（`TaintedCheckerBase.accessPathTaintStore`，在每次 `DfaEngine` 跑完时清空）⇒ **同一个 JVM 里，两个「签名相同、在同一个站点分配同一种类型」的程序会共用同一批键**。本轮实测就撞上了：临时探针（已删）与本轮的新测试用了同一个函数签名和同一个分配行 ⇒ 探针的条目把新测试的条目**盖掉了** ⇒ 新测试在**全量回归里红、在单跑里绿**。
⇒ **这条对写测试的人是真规则**：**测试的函数签名要能认出是它自己的**（本轮改成 `app.py_iterator_handler(any):any`），否则它会与**任何**先跑的、签名相同的测试共用 keyed store 的键。

#### 3.9.5 引擎侧：容器**本身就是污点**时，迭代器交出来的也是污点

`cmds = request["cmds"]; for x in cmds:` —— 容器是**从请求里读出来的**，它里面的东西**从没被单独写过** ⇒ keyed store 里**没有**它的任何条目 ⇒ 唯一的证据就是**容器自己的污点**。

**改法**：容器的污点本身也是答案 —— 容器脏了，它里面的东西都来自程序之外 ⇒ 迭代器交出来的也是脏的。

这条规则**只加在 keyed 的那一支**：数组位置的那一支**一个字都没改** ⇒ **Java / C# / Go 的结论逐条不变**（§3.9.6 记了那里为什么不变）。

#### 3.9.6 这一轮**没有**改的（记在案，附原因）

| 项 | 为什么不改 |
|---|---|
| **数组位置语言里「容器本身就是污点」也不算数** | 探针实测：**Java 形状下 `arr` 本身带污点、但没有元素被写过时，迭代器交出来的元素是干净的**。这条在 Java / C# / Go 上**同样存在**，但它**不是本轮要修的东西**（本轮修的是 Python 的迭代协议），而且改它会**新增发现**（⇒ 直接动 Juliet 的误报率）。⇒ **记在案，不在本轮动**；要动就是另一轮的事，而且要跑一遍 Juliet |
| **TS / ArkTS 的迭代协议** | **已在下一轮修掉**（见 §3.10.2）：引擎的工厂判定多认**计算属性名** `Symbol.iterator`。⇒ **顺带更正上一轮的一处错记**：上一轮写「TS 的 `for..of` 现在**绑的是可迭代对象而不是元素**」—— **那是错的**。探针实测：TS 侧车发的是 `ARRAYLOAD item = step["value"]` 再 `MOVE item = …` ⇒ **绑的是元素**，与 Java / Python 一样。TS 的元素是从**结果对象的成员**读的，引擎的成员读会把接收者的污点传给成员 ⇒ **不需要为它单独加规则** |
| **PHP 的 `foreach`** | PHP 侧车的 `foreach` 走的是**下标读**，不发迭代协议 ⇒ 本轮的改动对它**零影响** |
| **Python 字典迭代得到的是键不是值** | `for k in d` 交出来的是**键**。引擎在 keyed 这一支是**保守**的（容器里**任何**脏东西都算）⇒ 会**多报**。要精确就得区分「列表的值」与「字典的键」，那要 keyed 的键**语义**（不是一个路径能说的）⇒ 留作已知偏差 |

#### 3.9.7 这一轮的**方法**：把「形状对不对」的判据换成「**污点过不过得去**」

前两轮的探针问的是「TAC 的形状对不对」（分支有没有主语、`continue` 跳对没有）。这一轮问的是**引擎的结论**：把侧车**真正降出来的** TAC 原样喂给引擎，看**该报的是不是报了、不该报的是不是没报**。

这个转向抓到了**三处叠在一起的缺陷** —— 只修其中任何一处，探针都仍然是红的。

⇒ 而且这一次探针自带了**反向对照**：干净容器**不该**报 ⇒ 它没报 ⇒ 说明改完不是「什么都报」。

### 3.10 TS / ArkTS 的迭代协议、ArkTS 的自由全局函数、IIFE 的函数体（本轮补 —— 探针实测出来的）

这一轮换了**目标**：从「某个构念降得对不对」换成「**引擎的结论对不对**」—— 把侧车真正降出来的 TAC 原样喂给 `DfaEngine`，看该报的是不是报了。上一轮（§3.9）已经把这个转向用在 Python 上；这一轮把它用在 TypeScript 与 ArkTS 上，而它**一次撞上了四个不同的缺陷**。

#### 3.10.1 探针实测：同一个程序，十种形状

| 变体 | 修复前 | 修复后 | 说明 |
|---|---|---|---|
| TS 的 `for..of`，元素是容器的元素 | ❌ | ✅ | **本轮修的主目标** |
| TS 的 `for..of`，容器**本身**就是污点 | ❌ | ✅ | `items = request["cmds"]` |
| TS 的 `for..of`，元素按**下标**读（没有协议） | ✅ | ✅ | **本来就是好的** —— 元素污点**在**，只是迭代器**够不着** |
| ArkTS 的 `for..of`，同上 | ❌ | ✅ | 协议形状与 TS 相同，但**自由全局函数的 owner 也坏了**（§3.10.4） |
| TS / ArkTS 的 IIFE，函数体里有 sink | ❌ | ✅ | 函数体**整个不在 TAC 里**（§3.10.5） |
| TS 的 `for..of`，干净容器 | ❌ | ❌ | **反向对照**：干净容器**不该**报 |
| Java 形状（`iterator` / `next`） | ✅ | ✅ | **对照**：引擎的老路没坏 |
| C# 形状（`GetEnumerator` / `get_Current`） | ❌ | ✅ | 协议名不同（§3.10.3） |

⇒ **一条结论**：**协议的名字**是这一族缺陷的共同根因。六个语言里迭代协议的名字**各不相同**，而引擎按名字认它 ⇒ 少认一个名字，那个语言的 `for` / `foreach` 的元素污点就**整个断掉**。

⇒ **另一条结论**：**探针必须同时带「按下标读」和「干净容器」两条对照**。前者证明污点**在**、断点在协议；后者证明改完之后不是「什么都报」。少任何一条，这条修复都只是「看起来对」。

#### 3.10.2 TS / ArkTS：协议的名字是**计算属性名**

TypeScript 把迭代协议写成 `Iterator[Symbol.iterator]` —— 一个**计算属性名**。引擎的 `methodNameOf` 按最后一个 `.` 切分，于是切出来的是 **`iterator]`**（带一个方括号）⇒ 两个判定都不认。

⇒ **为什么不改侧车去凑名字**：`02` §2 的 **IR-P** 写死了「迭代协议的 callee 名**必须是真实存在的语言方法名**」⇒ TypeScript 的协议**就是**这个计算属性名 ⇒ 侧车写的名字是**对的**，要改的是**引擎**。把侧车改成 `iterator` / `next` 反而是**把一个 TypeScript 程序里不存在的方法名写进 TAC**。

⇒ **改法**：`methodNameOf` **一个字都不动**（它还被通用的方法名判定 `isMethodNamed` 用着，动它会误伤别处）⇒ 另加一个专门解开计算属性名的辅助，工厂判定多认它。

⇒ **顺带一条**：TypeScript 的**元素**是从结果对象的 `value` 成员读的，而引擎的成员读会把**接收者的污点**传给结果 ⇒ 所以**引擎不需要按语言分派**：工厂认出来之后，链条自己就通了。**协议名按语言分派，元素取法不用** —— 这是这一族能修得这么小的原因。

#### 3.10.3 C#：枚举器的元素**不是**推进的结果

C# 的枚举器**没有**一个「返回元素」的 `next`：`MoveNext` 说**还有没有**下一个（结果是布尔），元素在 `Current` **属性**上（所以调用是它的 getter，`get_Current`）。

⇒ 染色 `MoveNext` 的结果等于染色一个布尔 ⇒ 元素拿不到污点。
⇒ **改法**：新增一条规则 —— **对已知迭代器的 `Current` 调用继承迭代器的污点**。判定同时看**名字**与**接收者**（接收者必须是引擎认得的迭代器）⇒ 世界上任何叫 `Current` 的方法都不会被误认。
⇒ **`MoveNext` 刻意不认**：把一个布尔染色成带污点的，程序里没有任何东西会用到它。

#### 3.10.4 ArkTS：自由全局函数的 owner 少了 `eval`

**调用方类型定不出来**的调用**没有 owner**，键就是 `eval/1`；而目录的 pattern 是 `^eval\.eval\b` ⇒ **认不到** ⇒ ArkTS 的 `eval` **从来不是 sink**（代码注入的**漏报**，且**静默**）。

⇒ 根因**不在** owner 的**规则**（ArkTS 侧车与 TS 侧车的规则**一模一样**）⇒ 在**那张「语言提供的全局名」的表**里**没有 `eval`**。
⇒ **改法**：把 `eval` 加进 ArkTS 的那张表。**不加 `fetch`**：ArkTS 没有 `fetch`（鸿蒙用 `@ohos.net.http`），加了等于让一个不存在的 API 被认领。

#### 3.10.5 IIFE：函数体**整个不在 TAC 里**，而且**零记录**

`(() => { ... })()` 的函数体是**代码**。之前它**不在 TAC 里**：不是「降得粗」，是**没有指令、也没有 drop**。外层函数**报 `SOURCE_FULL`**，扫描**报成功** ⇒ 双重违反：既「零静默」，又「谎报精度」。

⇒ **改法**：函数体被**提升成一个自己的函数**，调用点**指向它** ⇒ 引擎能解析这个调用，函数体里的 sink 也**可达**。两个 IIFE 得到**不同的名字** —— 否则函数表按签名索引，第二个会**覆盖**第一个（§3.10.7 里 auto-accessor 那一条是同一个道理）。
⇒ **捕获没有被建模**：提升出来的函数有自己的作用域，函数体从外面读的名字**不在里面** ⇒ 这一条**记成 drop** ⇒ 精度不再谎报。

#### 3.10.6 上一轮留下的一个**真漏洞**：测试**不在允许列表**里

`plumb-dfa` 的 surefire 是一张**允许列表** ⇒ 不在名单上的测试类**正常构建不跑**。上一轮新增的 `PythonIteratorTaintTest` **不在名单上** ⇒ 它的四条用例在正常构建里**从来没有跑过**。

⇒ 而上一轮的回归命令带了 `-Dtest=!R253JulietProjectRootSweepTest` ⇒ **`-Dtest` 会覆盖那张允许列表** ⇒ 上一轮跑的是「全部测试」，**不是**「允许列表那一层」⇒ **两件事被同一个参数遮住了**。

⇒ **这一轮**：三个测试类都进了名单；`scripts/check_test_coverage.py` 抓的就是这个洞（它**上一轮没有跑**）⇒ 现在它**是绿的**。

⇒ **给写测试的人的真规则**（与上一轮那条并排）：**测试类必须在自己的模块的允许列表里**，否则它只是一份没人执行的代码；而**验证时不要用 `-Dtest`** —— 它会把允许列表绕过去，于是「白名单层跑过了」这句话可以是假的。

#### 3.10.7 这一轮**没有**改的（记在案，附原因）

| 项 | 为什么不改 |
|---|---|
| **C# 集合的元素写入** | 探针实测：`new List<string> { cmd }` 降成 `NEW` + `CALL List.Add/1`，**没有 `ARRAYSTORE`** ⇒ 集合的元素**不在任何跟踪器里** ⇒ 即使协议名认对了，元素**仍然干净**。这一条**不是引擎的协议问题**，是「集合方法的实参 ⇒ 容器元素」这条传播规则**还不存在** ⇒ 要动就要在目录里加一族「哪些方法往容器里写元素」⇒ 那是**另一轮**的活 |
| **C# 的 `new[] { … }`（隐式数组创建）** | 探针实测：**整个表达式没有降级**，只记了一条 `csharp.unmodelled` 的 drop ⇒ 数组是空的。**显式**的 `new T[] { … }` 上一轮已做，**隐式**的这一种没有 ⇒ 补它是一处小改动，但它与上一条一样是「C# 的集合面」，本轮不拆开做 |
| **TS / ArkTS 的默认参数** | 被调用方**无条件**用默认值覆盖形参 ⇒ 调用方的实参污点在那里断掉。修法要定口径：IR 里没有「形参有默认值」这个表示 ⇒ 要么给 IR 加一个字段，要么让引擎按「实参数 < 形参数数」推断 ⇒ 两边都要动 ⇒ **先要定口径**（§6.2） |
| **TS / ArkTS 的基类构造器实参** | `CALL Base.<init>/N args=[this]`，N 个声明参数一个都没传 ⇒ 不知道基类的形参表 ⇒ 要读类型信息。**已知**：同文件内的顶层类能读到，跨文件的读不到 ⇒ 跨文件时键是 `/0`，与真实的 `Base.<init>/N` 对不上 ⇒ 基类构造器不可达 |
| **TS / ArkTS / Python 的 getter** | 属性读被降成 `ARRAYLOAD(obj, "name")`，访问器的**函数体不执行** ⇒ 访问器里的 sink 不可见。TAC 的 keyed namespace **不区分「数据属性」与「访问器属性」** ⇒ 要么在 IR 里加标记，要么在侧车里把访问器读降成一次调用 ⇒ 两者都要动 |
| **TS 的 auto-accessor：getter 与 setter 签名相同** | 两者都是 `mod.Cls.x()`，而函数表按签名索引 ⇒ **后写覆盖先写** ⇒ 一个的函数体整段消失。修法是给签名加上区分（读/写）⇒ 波及所有按签名索引的地方 |
| **PHP 的 `__get` 魔术访问器** | 同 getter：属性读不触发魔术方法 |

⇒ **这七条的共性**：**六条要类型信息或 IR 的新字段，一条要目录里的一族新规则** ⇒ 它们不是「长尾」，是**下一轮的入口**：每一条都有明确的落点，但**都不是一行能改完的**。

### 3.11 C# 集合的元素写入：污点在**容器里**，读不出来（本轮补 —— 探针实测出来的）

这一轮继续用 §3.10 的判据：**引擎的结论对不对**。目标定在 C# 的集合：

```csharp
var list = new List<string>();
list.Add(input);
foreach (var item in list) {
    Process.Start(item);
}
```

#### 3.11.1 前提核实：「Add 没进 TAC」**不成立**

送来的症状是「C# 集合 Add **未进入 TAC**」。探针实测：**Add 在 TAC 里**，而且形状是对的：

| 源 | TAC |
|---|---|
| `list.Add(cmd)` | `CALL System.Collections.Generic.List.Add/1 args=[list, cmd]` |
| `new List<string> { cmd }` | `NEW` + `CALL System.Collections.Generic.List.Add/1 args=[t_t1, cmd]` + `MOVE` |

⇒ callee 名是**真实存在的 C# 方法名**（IR-P）⇒ 接收者槽是**集合**，实参槽是**被加进去的值** ⇒ **侧车没有错** ⇒ **要改的是引擎，不是侧车**。

⇒ 而且这正是**上一轮 §3.10.7 记下的那一条**（「C# 集合的元素写入」＝「要动就要在目录里加一族『哪些方法往容器里写元素』」）的**下一轮入口** ⇒ 这一轮就是那一轮。⇒ 症状描述里的前提**只有一半成立**：写**在** TAC 里，**读不出来**。

#### 3.11.2 探针实测：十种 C# 集合写法，修复前后

| 变体 | 修复前 | 修复后 | 说明 |
|---|---|---|---|
| `List.Add(input)` + `foreach` | ❌ | ✅ | **本轮修的主目标** |
| `new List<string> { input }` + `foreach` | ❌ | ✅ | 集合初始化器走的是同一条 `Add` |
| `list[0]`（**下标**读） | ❌ | ✅ | **另一条读法**：索引器的 getter（§3.11.4） |
| `Queue.Enqueue(input)` + `foreach` | ❌ | ✅ | 目录不认这个**方法**拼法 |
| `Stack.Push(input)` + `foreach` | ❌ | ✅ | 目录不认这个**类型名** |
| `List.Insert(0, input)` + `foreach` | ❌ | ✅ | 目录不认这个**方法**拼法 |
| `List.AddRange(items)` + `foreach` | ❌ | ✅ | 目录不认这个**方法**拼法 |
| `Dictionary` 下标写 + `foreach` | ❌ | ✅ | 目录不认 `dictionary` 这个**类型名** |
| `list.Add("safe")` + `foreach` | ❌ | ❌ | **反向对照**：干净容器**不该**报 |
| 容器**本身**就是参数（从外面来） | ❌ | ✅ | 另一半：容器脏了，里面都脏 |
| `Process.Start(input)`（直接） | ✅ | ✅ | **对照**：整条链本来就是好的 |

⇒ **一条结论**：**同一个缺陷，十种写法全中** ⇒ 根因**不在**某一种拼写上 ⇒ 修的是**三处通用规则**，不是十个特例（§3.11.3 / §3.11.4 / §3.11.5）。

⇒ **另一条结论**：**探针必须带「按下标读」与「干净容器」两条对照**。前者证明**元素污点确实在容器里**、断点在**读**的那一环；后者证明改完不是「什么都报」。

#### 3.11.3 断点一：集合的污点**取不到**（`elementTaintOf` 的两半不对称）

引擎问「迭代器从这个容器里交出来的东西有没有污点」，问的是 `elementTaintOf`，而它有**两半**：

- **keyed 的语言**（JS / TS / ArkTS / Python / PHP）：问 keyed store，**并且**在 store 里没有答案时**回退到「容器自己的污点」**；
- **数组位置的语言**（C# / Java / Go / Kotlin / Scala）：**只**问数组跟踪器，**没有**那个回退。

⇒ 集合是**用调用**填的（`list.Add(x)`），**不是**用数组写填的（`a[i] = v`）⇒ 数组跟踪器**从来没听说过**这个集合 ⇒ keyed 那一半靠「容器自己的污点」拿到答案，数组位置那一半**拿不到** ⇒ **同一个程序在 TypeScript 里报、在 C# 里不报**。

⇒ **改法**：把 keyed 那一半**已有的**回退**补到数组位置那一半**。两个分支现在问的是**同一个问题**（「容器里有没有脏东西」），答案也该**来自同一个地方**。

⇒ **顺带一条**：这个回退**上一轮明确记过、并且刻意没动**（「数组位置语言里『容器本身就是污点』也不算元素污点」，§3.9.6 / §6.2），当时的理由是「会**新增发现** ⇒ 直接动 Juliet 的误报率」⇒ **这一轮动了 ⇒ 必须跑一遍 Juliet**（前后对照见 §7.2）。

#### 3.11.4 断点二：目录不认 C# 的集合写法

引擎的「哪些调用把值写进容器」这一族（`AccumulatorCatalog`）认的是「owner 的**类型名后缀** + 方法名」：

- owner：`list` / `set` / `collection` / `queue` / `deque` / `array` / `map`
- 方法：`add` / `addall` / `set` / `offer` / `push`（集合）；`put` / `putall`（map）

⇒ **C# 的拼法大半不在这张表里**：`Enqueue`、`Insert`、`AddRange` 不在；**`Stack`（类型名）不在** ⇒ `push` 认不到；**`Dictionary`（类型名）不在** ⇒ `Add` / `set_Item` 认不到。

⇒ **改法**：补上这些拼法。**判据是「这个类型名是不是同一个家族」，不是「这个语言是谁的」** ⇒ C# 的 `Dictionary` 与 Java 的 `Map` 落进**同一族**，因为它们的**语义**是同一个东西（同理，`Stack` 与 `List` 同族，`Enqueue` 与 `add` 同族）。

⇒ **顺带一条**：**读**的那一端也有同样的毛病 —— `list[0]` 是 `CALL List.get_Item/1`，而那一族只认 `get` ⇒ **按下标读**也是干净的 ⇒ 补了 `get_item`（.NET 的索引器 getter）。

#### 3.11.5 断点三：map 的 **key 不是 value**

补上 `dictionary` 之后，一个**新的**精度问题出现了：map 的写是 `map.put(k, v)` / `dict.Add(k, v)` ⇒ **key 在前、value 在后**。若照搬「实参的污点都进容器」，那么**被污染的 key 会让 map 的每一个 value 都看起来脏** ⇒ 读一个**从没被污染的数据写进去**的 value 也会报。

⇒ **改法**：map 家族的**值**取**最后一个实参**（key 只命名槽位）⇒ 引擎里**已经有这个先例**：Go 的 map 写（`mapstore`）当初就是这么处理的（`mutatorArgIndices` 的注释里写着原因）⇒ 这一次只是把同一条规则**推广到「用方法写的 map」**。

⇒ **副作用（记在案）**：Java 的 `Map.put` 也在这一族里 ⇒ 它的行为**也**从「key 也染容器」变成「只有 value 染容器」⇒ 这是**精度变好**（少一类误报），但**是行为变化** ⇒ 回归与 Juliet 都要看。

#### 3.11.6 落点：为什么落在 `AccumulatorCatalog`，而不是新开一族 YAML

上一轮 §3.10.7 写的是「要动就要在**目录里加一族**『哪些方法往容器里写元素』」。

⇒ 这一轮**确实加了一族**，但落在**引擎侧那个目录**（`AccumulatorCatalog`），不是新开一个 YAML：理由是这一族要回答的问题**有两个** —— 「这个调用是不是往容器里写」**和**「哪个实参是那个值」—— 而**后一个问题**决定了前一问的**粒度**（map 的 key 与 value 必须分开）⇒ YAML 家族只带「pattern + 一个实参位置」，放不下这个区分 ⇒ 而 `AccumulatorCatalog` 本来就是**同一个问题的另一半**（「哪些调用把容器的内容读出来」）⇒ 两个方向放在一处，才不会**一边认得、一边不认**。

⇒ **也**因此**没有**往 `sink-families.yaml` 里加任何东西：那个文件的 managed region 是厂商派生的，加东西会落进去（提交纪律）。

⇒ **也**因此 **`design/tac/07`（设计台账）一个字没动**：这一轮**既没改 IR，也没改侧车** ⇒ **降级形状本来就是对的**（设计里写的「集合：逐元素 `CALL <owner>..Add/1`」正是侧车发的东西）⇒ 错的是**引擎怎么读它** ⇒ 台账记的是**该降成什么**，而它**已经**降成那个了。

#### 3.11.7 这一轮**没有**改的（记在案，附原因）

| 项 | 为什么不改 |
|---|---|
| **C# 的 `new[] { … }`（隐式数组创建）** | 探针实测：**整个表达式没有降级**，只记了一条 `csharp.unmodelled` 的 drop ⇒ 数组是空的。⇒ 后果：`list.AddRange(new[] { cmd })` 的**实参没了** ⇒ 这一种写法仍然不通（`AddRange` 那一族里，**传进来一个集合**的那种写法是通的）。⇒ **下一轮（§3.12）已做** |
| **集合的逐元素精度** | 现在是「容器里**有一个**脏元素 ⇒ 迭代器交出来的**都**是脏的」⇒ **保守但粗**。要精确就得区分「第 0 个元素脏、第 1 个不脏」⇒ 那是 keyed store 的**键语义**，不是一条能加进数组跟踪器的规则 |
| **Python 的 `list.append`** | **引擎侧已认**（`append` 与 `add` 同族，§3.11.4）。但**前端侧还有一半**：Python 侧车只在**类型定得出来**时才发 `CALL list.append/1`；类型定不出来时发的是 `UNINTERPRETED <unknown>.append/1` **加一条 drop** ⇒ 那条路的元素污点**仍然取不到** ⇒ 那是**前端**的缺口，不是引擎的 |
| **`await foreach`** | C# 的异步迭代协议（`IAsyncEnumerable<T>`）**整套没降** ⇒ 不是污点的问题 |
| **集合写进另一个集合**（`list.Add(otherList)`） | 实参是**容器**而不是元素 ⇒ 现在的模型是「实参的污点进容器」⇒ 结论**恰好是对的**（容器脏了，它的内容也脏），但**路径**写的是「元素的污点」⇒ 语义上说得过去，只是**粗** |

⇒ **这五条的共性**：**四条要前端降级，一条要 keyed store 的键语义** ⇒ 它们不是「长尾」，是**下一轮的入口**。

#### 3.11.8 顺带查出来的一件事：**量具自己坏了**，而且坏得「很像结论」

这一轮要跑 Juliet 的**前后对照**（改了「数组位置语言」的回退 ⇒ 会动 Juliet 的数）。第一次跑完的结果是：

| CWE | recall | precision | 说明 |
|---|---|---|---|
| CWE129 / CWE190 / CWE191 / CWE369 | **0.0000** | 0.0000 | TP=0，**每一个 finding 都被判成 FP** |
| CWE252 / CWE253 | 1.0000 | 1.0000 | **正常** |

⇒ 「四个 CWE 一条都报不出来」这件事本身**可疑**：这些 CWE 的语料各有几千个文件，引擎不可能一条都找不到。⇒ 所以先查**量具**，而不是先怀疑引擎。

查出来的原因：**`scripts/juliet_measure.py` 在语料目录的第一层找测试文件**，而 Juliet 的布局是**两种都有** —— **多变体 CWE 的文件在 suite 子目录里**（`s01/`、`s02/`、…），**单文件 CWE 的文件直接躺在 CWE 目录里**。

⇒ 量具**只**找得到后者 ⇒ 前者的文件**一个都定位不到** ⇒ 定位不到的文件**没有方法区间** ⇒ 落在它里面的每个 finding 都被判成「**不在 `bad` 方法里**」⇒ **全是 FP** ⇒ recall = **恰好 0.0000**，precision 也是 0.0000。

⇒ **它为什么骗得过人**（这四条里，每一条都单独成立）：

- 数字**看起来**很正常：两个整齐的 `0.0000`；
- **没有一行报错**，脚本正常退出；
- **有两个 CWE 测得正常**（252 / 253 的文件在第一层）⇒ 看上去像「这四个 CWE 引擎就是不行」，而不是「量具找不到文件」；
- 而**触发**它的那些规则恰好是 **DFA 规则**（129 / 190 / 191 / 369 的白名单里 `dfa-taint-*` / `dfa-boundary-*` 是主力），**AST 规则**命中的那两条（252 / 253）**毫发无损** ⇒ 看上去像「**引擎的 DFA 规则不行**」。

⇒ **探针实测**（不跑扫描，只问量具「你找得到自己的语料吗」）：修复前，CWE129 / 190 / 191 / 369 的 **4392 / 7015 / 5612 / 3050** 个语料文件**一个都定位不到**；修复后**全部定位到**，且算出的 `bad` 方法行区间与源码对得上（`bad` 在 27–63、`goodG2B` 在 67–73，…）。

⇒ **修法两处**：① 找文件改成**递归**（`rglob`）⇒ 两种布局都找得到；② **把「找不到语料文件」变成会出声的事**：数出来、打印 `WARNING`，并写明「recall 与 precision **不可信**」。

⇒ **同一轮还撞上第二个量具缺陷**（Windows 专属）：量具用 `subprocess(text=True)` 跑 `java -jar …`，**按本机 locale 编码解码子进程输出**，而本机 locale 是 **GBK**、Plumb CLI 打印的中文是 **UTF-8** ⇒ **整轮测量在吐出任何结果之前**就抛 `UnicodeDecodeError` ⇒ 第一次跑出来的只有一个 traceback。⇒ 改成用 `-X utf8` 跑（UTF-8 模式下 `locale.getencoding()` 就是 utf-8）。

⇒ **两条给写量具的人的真规则**：

1. **「找不到语料」必须是一件会出声的事**。一个因为找不到自己的语料而报出「**恰好 0**」的量具，比一个**不肯报**的量具**更坏** —— 因为 **0 看起来像一个结论**，而「不肯报」至少还会让你去查。
2. **量具的数字要分两半看**：**「引擎报了多少条」是量具测出来的**，**「这些条里多少算对」是量具**分类**出来的** ⇒ 这两半会**各自**坏掉，而且**坏的方式不同**：前半坏了是**数字变小**，后半坏了是**数字变大**（FP）⇒ **一个 0 既可能是「引擎什么都没报」，也可能是「量具把每一条都判成了错」** ⇒ 区分它们的唯一办法是**让量具说出它干了什么**（本轮加的 `WARNING` 就是这个）。

#### 3.11.9 再一件：**对照的两端会「一样」，而且一样得不报错**

§3.11.8 说「量具坏了比引擎坏了更危险」。这一轮**亲身**撞上了这句话的另一半：**对照的两端也会「一样」**。

第一版的「before」脚本这样取基线：

```python
blob = subprocess.run(["git", "show", "HEAD:" + rel], ...)   # 「改动前」的版本？
```

⇒ 那个脚本是在**本轮改动已经提交之后**写的 ⇒ `HEAD` **就是改动之后** ⇒ 「before」构建出来的 jar 里装的是**改后的引擎** ⇒ **前后对照变成了拿同一份东西比两次**。

⇒ 它**不报错**：构建成功、脚本成功、两组数字都打印了 ⇒ 从表面上看完全是一次正常的对照。

⇒ **抓住它的是「产物级内容对比」**：逐条目比 CRC ⇒ 两份 jar **83949 个条目、CRC 逐条相同、差异 0 条** ⇒ **「差异 0」这件事本身就是结论：这不是一次对照**。

⇒ **修法两条**：① 基线取**明确的、改动前的那个提交**（本轮是 `a5aa4c1`），**不用 `HEAD`** —— 尤其在**改动已经提交之后**；② **对照的两端先做一次内容对比**，**差异集合必须正好等于你声称的差异**。

⇒ 修好之后的对比结果：**两份 jar 各 83949 个条目、条目集合完全相同**，**内容差异正好 3 条**：

| 差异条目 | 是什么 |
|---|---|
| `org/plumb/dfa/taint/AccumulatorCatalog.class` | 本轮改的**集合目录** |
| `org/plumb/dfa/taint/TaintedCheckerBase.class` | 本轮改的**迭代器污点读取** |
| `org/plumb/dfa/taint/TaintedCheckerBase$1.class` | javac 为 `TaintedCheckerBase.java` 生成的 **enum-switch 合成映射类**（`$SwitchMap$…` 数组）⇒ 它随该文件一起重新编译 |

⇒ **差异集合恰好等于「我改的那两个文件的编译产物」** ⇒ **两端可比** ⇒ 这才是一次真的对照。

⇒ **顺带一个坑**：做「基线是不是干净」的守卫时，**不能用通用词** —— 本轮先用 `enqueue` 查基线文件，**基线里本来就有这个词**（在 worklist 的注释里）⇒ 守卫误报 ⇒ 守卫要用**这一轮引入的独特行**（本轮是 `private static boolean isMapWrite(String calleeSig)`）。

⇒ **两条给做对照的人的真规则**：

1. **基线要用「改动前」那个提交，不是 `HEAD`** —— 尤其在**改动已经提交之后**（提交之后 `HEAD` 就是改后）。
2. **对照的两端先做一次产物级内容对比**（逐条目 CRC / 哈希）：**差异集合必须正好等于你声称的差异**；**差异为 0 ⇒ 这不是对照**；差异超出声称范围 ⇒ 两端不可比。

### 3.12 C# 的隐式数组创建：整个表达式被丢掉 ⇒ 集合写的实参整个没了（本轮补 —— 探针实测出来的）

这一轮接着 §3.11 的集合面往下走：上一轮把「集合的元素污点」在引擎里接通了，但 C# 里最常见的写法之一 —— `list.AddRange(new[] { cmd })` —— 仍然不通。文档上一轮记的是「C# 的 `new[] { … }`（隐式数组创建）**未做**」。

#### 3.12.1 前提核实：症状**成立**，而且是**两处**，不是一处

探针实测（修复前）：

| 源 | TAC |
|---|---|
| `new string[] { cmd }`（**显式**） | `MOVE t_t2 = 1` + `NEWARRAY t_t3` + `ARRAYSTORE t_t3[0] = cmd` + `MOVE explicitArr = t_t3` ✅ |
| `new[] { cmd }`（**隐式**） | **一条指令都没有**，只多了一条 drop：`csharp.unmodelled` / `the expression ImplicitArrayCreationExpression was not lowered`（impact `SEMANTICS`）❌ |
| `list.AddRange(new[] { cmd })` | `HAVOC t_t5` + `CALL List.AddRange/1 args=[list, t_t5]` ⇒ **实参是个「未知」占位** ❌ |

⇒ 函数的精度是 `SOURCE_DEGRADED`（那两条 drop）⇒ 修复后回到 **`SOURCE_FULL`**。

⇒ ⇒ **两处断点**：数组**根本没降下来**（前端），而且**就算降下来了污点仍然断**（引擎）⇒ 下面两小节。

#### 3.12.2 断点一（前端）：侧车的表达式分派**没有这一支**

Roslyn 里 `new T[] { … }` 与 `new[] { … }` 是**两个不同的节点类型**（`ArrayCreationExpressionSyntax` 与 `ImplicitArrayCreationExpressionSyntax`）⇒ 侧车的 `TranslateExpression` 只认前者 ⇒ 隐式形式落进 `default:` ⇒ `Report(…, "UNHANDLED_NODE")` ⇒ 记一条 `csharp.unmodelled` 并**返回 null** ⇒ **整个表达式消失**（不是「降级得粗」，是「没有」）。

⇒ **改法**：加一支，与显式形式**同形**（`NEWARRAY` + 逐元素 `ARRAYSTORE`）。唯一的差别是**元素类型不是写下来的**，而是由**语义模型**推断出来（`_model.GetTypeInfo(creation).Type` 是 `IArrayTypeSymbol` ⇒ 取它的 `ElementType`）⇒ 探针实测推断出来的是 `System.String` ✅。

⇒ **不变量**：两种写法是**同一个构念的两种写法** ⇒ 落到**同一个 helper**（`LowerArrayFromElements`）⇒ **显式路径的指令序列逐条未变**（连临时量编号顺序都没变：探针里显式形式仍然是 `t_t2` / `t_t3`）⇒ 改动没有碰到已经对的那条路。

#### 3.12.3 断点二（引擎）：mutator 问的是「实参**本身**脏不脏」，而脏的是**元素**

⇒ 即使侧车把数组降下来了，污点**仍然断在这一步** ⇒ 因为引擎的 mutator 规则问的是 `taintedVars.get(arg)` —— 实参这个**变量**自己的污点 —— 而 `AddRange(new[] { cmd })` 的实参是**数组**：数组这个**引用**从来不脏，脏的是它的**元素槽**。

⇒ **而且这不是 C# 独有**：Java / Go / Kotlin / Scala 的同一个写法（`list.addAll(new String[]{ cmd })`）也一样断 ⇒ 这是**共享规则** ⇒ 对所有语言都有影响（§7.2 必跑 Juliet）。

⇒ **引擎其实已经有这个问题的答案**：迭代器那条路问的是「这个容器**交出什么**」，答案是 `elementTaintOf(container, fn, ctx)`（上一轮刚把它补成两个分支**同一个答案**）⇒ 而 mutator 问的其实是**同一个问题**的另一半：「这个实参把什么**带进**接收者」⇒ 两个问题问的是**同一件事**。

⇒ **改法**：mutator 的实参贡献改为 **`elementTaintOf(arg, fn, ctx)`** ⇒ **与迭代器路径同问同答**（不再制造新的分支不对称 —— 上一轮刚吃过「同一个问题，两个分支给两个答案」的亏）。

⇒ **副作用（记在案）**：显式写法 `list.AddRange(new string[] { cmd })` **也从「不报」变成「报」** ⇒ 那是**同一处规则**的效果，**不是**新加的一条规则 ⇒ 两种写法从此**同进同退**。

#### 3.12.4 探针矩阵：修复前 → 修复后

| 变体 | 前 | 后 |
|---|---|---|
| `new[] { cmd }`（单独的表达式） | ❌ 一条指令都没有 + 一条 drop | ✅ `MOVE` + `NEWARRAY`（元素类型 `System.String`）+ `ARRAYSTORE` |
| `new string[] { cmd }`（显式） | ✅ | ✅ **指令序列逐条未变** |

| `list.AddRange(new string[] { cmd })` 端到端 | ❌ 不报 | ✅ **报**（同一处规则的效果） |

#### 3.12.5 落点与两条不变量

| 改动 | 文件 | 性质 |
|---|---|---|
| 侧车：隐式数组降级 | `plumb-frontend/csharp-sidecar/TacTranslator.cs` | **只影响 C#**（侧车**不进 jar** ⇒ 对别的语言零影响；本轮的 jar 对比也证明了这一点：差异里没有它） |
| 引擎：mutator 的实参贡献它携带的污点 | `plumb-dfa/.../TaintedCheckerBase.java` | **共享规则** ⇒ 影响所有语言 ⇒ **Juliet 前后对照必跑**（§7.2） |

⇒ **两条不变量**（这一轮真正想留下的东西）：

1. **同构念同形状**：显式与隐式数组落到**同一个 helper** ⇒ 以后再有人加第三种写法（集合表达式 `[cmd]` 就是），也是同一条路。

#### 3.12.6 本轮**没有**改的（记在案，附原因）

| 项 | 为什么不改 |

| **集合的逐元素精度** | 现在是「容器里**有一个**脏元素 ⇒ 交出来的**都**是脏的」⇒ 保守但粗。要精确到「第 0 个脏、第 1 个不脏」⇒ 那是 keyed store 的**键语义**，不是一条能加进数组跟踪器的规则 |
| **C# 的集合表达式**（`[cmd]`） | `CollectionExpressionSyntax` 是**第三种**数组/集合写法 ⇒ 本轮只补了「隐式数组创建」这一种 ⇒ 它是**同一个 helper** 的下一次调用 ⇒ 下一轮 |
| **`new T[n]`（有长度、无初始化器）** | 显式形式的这一支**已经**能降（`NEWARRAY` + 长度）⇒ 本轮没动 |
| **`await foreach`** | C# 的异步迭代协议**整套没降** ⇒ 不是污点的问题 |
| **keyed 语言里「对象带脏属性 ⇒ 当成脏值」** | 本轮把 mutator 的实参改成问 `elementTaintOf`，keyed 那一支会走 keyed store ⇒ 它的答案粒度是「这个命名空间里有没有脏条目」⇒ 是否过粗，**留给语料**（§7.2 的 Juliet 对照）与**下一轮**再判 |

### 3.13 C# 的集合表达式 `[…]`：第三种字面量写法，也是整条表达式消失（本轮 —— 探针实测出来的）

这一轮接着 §3.12 的数组面往下走。上一轮把「隐式数组创建」补上了，但 C# 12 还有**第三种**写法 —— **集合表达式**（collection expression）`[a, b]` —— 而上一轮的文档早就把它的落点写好了：「它是**同一个 helper** 的下一次调用」。

#### 3.13.1 前提核实：症状成立，而且**四种目标形态**各不相同

探针实测（修复前）：

| 源码 | TAC |
|---|---|
| `list.AddRange([input])` | `HAVOC t_t2`（未知占位）+ `CALL List.AddRange/1 args=[list, t_t2]` ⇒ **实参整个没了** ❌ |
| `string[] items = [input]` | **一条指令都没有** —— 连 `MOVE items = …` 都没有 ⇒ **变量从未被赋值** ❌ |
| `List<string> items = [input]` | 同上，`items` 从未被赋值 ❌ |
| `list.AddRange(["safe"])` | 同上 ❌ |

⇒ 四个方法的精度都是 `SOURCE_DEGRADED`，各带一条 `csharp.unmodelled` / `the expression CollectionExpression was not lowered`（impact `SEMANTICS`）。

⇒ ⇒ **同一个语法，四种目标形态，而目标不同 ⇒ 该走的路也不同** —— 这是这一轮与上一轮最不一样的地方：**上一轮三种写法共用一个形状，这一轮不是**。

#### 3.13.2 断点：侧车的表达式分派没有这一支，**而且它的元素不是表达式**

`CollectionExpressionSyntax` 落进 `default:` ⇒ 整条表达式消失 ⇒ 记一条 drop。

⇒ **它的元素不能直接当表达式用**：Roslyn 4.12 的 `CollectionExpressionSyntax.Elements` 是 `SeparatedSyntaxList<CollectionElementSyntax>`，而 `CollectionElementSyntax` **不是** `ExpressionSyntax`（编译器实测：`无法从 CollectionElementSyntax 转换为 ExpressionSyntax`）⇒ 元素被包在 `ExpressionElementSyntax`（有 `.Expression`）里，spread（`..x`）是另一种 ⇒ **不解包就会把每个元素都读成「未知」**。

> ⇒ **这一条是实测出来的，不是查文档猜的**：先按文档的印象写（元素是表达式），编译器当场拒绝；再用**一次临时构建**（放一个探针文件进侧车工程，让编译器逐条回答）把继承关系问清楚，最后删掉探针文件。⇒ **反射在这里不管用**：从 NuGet 缓存加载 DLL 时它的依赖不在旁边，类型查找全部落空 ⇒ 那个「NOT FOUND」是**假阴性**，差点让人以为类型不存在。

#### 3.13.3 落点：**目标类型决定形状**

| 目标 | 形状 | 理由 |
|---|---|---|
| **数组**（`string[] items = [x]`） | `NEWARRAY` + 逐元素 `ARRAYSTORE` ⇒ **与显式 / 隐式形式共用同一个 helper** | 同一个构念的同一种写法 ⇒ 同构念同形状 |
| **具名集合**（`List<string> items = [x]`） | `NEW`（**带 `calleeSig`**）+ 逐元素 `List.Add/1` | C# 的**集合构造器模式**就是「构造 + Add」⇒ 这是**忠实的**形状，不是近似 |
| **接口**（`list.AddRange([x])`，形参是 `IEnumerable<string>`） | 数组形状 | 接口没有可构造的集合；数组**就是**同样元素的 `IEnumerable` |

⇒ **目标类型从语义模型取**：`_model.GetTypeInfo(expr).ConvertedType`（**被转换到的**类型）才是目标 —— 集合表达式**没有自己的自然类型**，`[x]` 是数组、是 `List` 还是 `IEnumerable` 全由目标说了算；`Type` 只作兜底（`var items = [1, 2]` 的自然类型是编译器选的数组）。

⇒ **两条不变量继续成立**：**同构念同形状**（数组目标 ⇒ 与另外两种数组写法同一个 helper）、**同问同答**（**引擎侧一个字没改** —— 上一轮修好的「实参携带什么」对两种形状都适用）。

#### 3.13.4 探针矩阵：修复前 → 修复后

| 变体 | 前 | 后 |
|---|---|---|
| `list.AddRange([input])` 的**实参** | ❌ `HAVOC`（未知占位） | ✅ 真数组（`NEWARRAY` + `ARRAYSTORE`，元素类型 `System.String`） |
| `string[] items = [input]` | ❌ 变量从未被赋值 | ✅ `MOVE items = t_t2` |
| `List<string> items = [input]` | ❌ 变量从未被赋值 | ✅ `NEW`（`List.<init>/0`）+ `List.Add/1` + `MOVE items = t_t1` |
| 函数的精度 | `SOURCE_DEGRADED` | ✅ **`SOURCE_FULL`**（drop 消失） |
| spread（`[..rest]`） | —— | 记一条 drop（它代表另一个集合的**内容**，写不出「一个槽一个值」） |

#### 3.13.5 A/B：**同一份 jar，只换侧车** ⇒ 0 findings → 2 findings

这一轮**只改了侧车**（引擎主源码一个字没动 ⇒ `git diff plumb-dfa/src/main/` 为空）⇒ 所以对照要换的是**侧车**，不是 jar —— 换 jar 会得到一次**空对照**（两份引擎一模一样）。

⇒ 两端**只差侧车**（jar 是同一个文件，sha256 `fed96555304b866b`，两次跑的是同一份）⇒ 差别**只能**来自这一轮的改动。

⇒ **第二条 finding 要老实说清楚它是什么**：它是「枚举器可能为 null」的判定，而它出现的原因是**那段代码路径这一轮才第一次变得可达**（之前集合表达式整个消失，枚举器那条路根本没进 TAC）⇒ 它不是新规则误报，是**可见性变好**的副产品。

#### 3.13.6 本轮**没有**改的（记在案，附原因）

| 项 | 为什么不改 |
|---|---|
| **spread 元素**（`[..rest]`） | 它代表另一个集合的**内容**，写不出「一个槽一个值」⇒ 记一条 drop，其余元素照常降下来 |

| **集合的逐元素精度** | 仍是「有一个脏元素 ⇒ 交出来的都脏」⇒ 保守但粗（要 keyed store 的**键语义**） |
| **`await foreach`** | C# 的异步迭代协议**整套没降** ⇒ 不是污点的问题 |

## 4. Kotlin / Scala（Java 侧前端）

这两个前端**不走 sidecar**，直接建 IR，所以 IR 的新面必须在这里填。

### 4.1 上一轮做的：通道

| 改动 | 内容 | 位置 |
|---|---|---|
| **drop 通道** | 每个「没能降下来」的构念现在**同时**记一条 `TacDrop`：Kotlin 5 处（`kotlin.statement.unmodelled` / `kotlin.expression.unmodelled` / `kotlin.binaryOperator.unmodelled` / `kotlin.when.isBranch` / `kotlin.translation.failed`），Scala 8 处（`scala.expression.unmodelled` / `scala.name.unresolved` / `scala.methodReference.asValue` / `scala.assignment.unmodelled` / `scala.if.condition` / `scala.while.condition` / `scala.match.bindings` / `scala.lambda.unnamed`） | `KotlinTacTranslator.java` / `ScalaTacTranslator.java` |
| **memberKind** | 类里的函数是 `METHOD`，顶层函数是 `FUNCTION` | `KotlinTacFrontend.java` |
| **注解通道** | 类的注解、函数自身的注解、形参的注解（按名索引）都进 IR；注解名取**简单名**（`org.springframework.web.bind.annotation.RequestParam` ⇒ `RequestParam`），与 Java 前端同口径 | `KotlinTacFrontend.java` `annotationNames` |

**drop 的 impact 一律 `STRUCTURE`**：这两个前端本来就声明 `SOURCE_LOWERED`，drop 必须与之一致 —— 两者不一致时 `combine` 取更差的一档，把它们改成 `SEMANTICS` 会把精度推到 `SOURCE_DEGRADED`，那是**另一个决定**（它会改变引擎的输出，见 §5 第 6 条）。

### 4.2 本轮做的：**语法面**（不是通道，是真的降下来了）

这一轮的判据是用户给的第 3、4 条口径：**TAC 服务于源码**，不承载分析过程态的信息；**不影响分析结果的信息不必完整翻译**，能说清楚、或 lower 之后不影响分析结果即可。于是取舍很明确：**凡是影响污点流、调用图、字段跟踪、可达性的构念，必须落成真实形状**；其余的要么落成保守形状并记账，要么写进 §5 的例外表。

#### Kotlin（`KotlinTacTranslator.java` / `KotlinTacFrontend.java`）

| 面 | 之前 | 现在 |
|---|---|---|
| **`this` 接收者** | 常量在表里，**从未注册** ⇒ 属性读走「没有接收者」分支，**一条指令都不产生** | 注册为局部量 ⇒ 属性读是 `FIELDLOAD`（带 `ownerType` = 类的 FQN） |
| **类没有构造器** | `translateClass` 只遍历 `KtNamedFunction` ⇒ **主构造器、次构造器都没有函数** ⇒ `new Foo(x)` 指向一个不存在的被调方，**调用图的边断了**，进对象的值到不了它初始化的字段 | 主构造器 = `CONSTRUCTOR` 函数：构造器形参 ⇒ backing field，属性初始化器 ⇒ `FIELDSTORE`，`init` 块 ⇒ 顺序执行；次构造器各自成函数 |
| **属性没有访问器** | 类属性**完全没被访问** | 每个属性一个 `GETTER`（默认访问器 = 读 backing field；自定义访问器 = 用户代码）；`var` 另有 `SETTER` |
| **循环** | `while` / `do-while` / `for` 全部落进兜底分支，**循环体一条指令都没有** ⇒ 循环体里的污点全部不可见 | `while` / `do-while` = 标签 + `BRANCH` + 回边 `JUMP`（标签带 `TacLabelRef`）；`for` = **迭代协议**（`java.lang.Iterable.iterator/0` → `java.util.Iterator.hasNext/0` → `java.util.Iterator.next/0`），协议名是**真名**（共享语义表按真名索引） |
| **`break` / `continue`** | 落兜底 | `JUMP` 到循环的结束标签 / 条件标签；带标签的 `break@label` 跳到**那个**循环 |
| **`try` / `catch` / `finally`** | 落兜底 | 与 Java 前端同形状：`L_CATCH_<Type>` + `CATCH_HANDLER`（`ctorType` = 异常类型，`dest` = 捕获参数）+ `L_FINALLY` + `FINALLY_ENTER`，并 `recordTryRegion` ⇒ CFG 构建器接上异常边 |
| **`throw`** | 落兜底 | `THROW` |
| **赋值** | `x = v` 只求值两侧、**结果丢掉** ⇒ **写操作从未发生** | `MOVE` 到局部量；属性写 = `FIELDSTORE`（带 `ownerType`）；数组元素写 = `ARRAYSTORE`；复合赋值 `x += v` = `BINOP` + 写回 |
| **`?.`（安全调用）** | 落兜底 | 先测接收者：非空分支做调用/读，空分支整体为 `null`（与 TS sidecar 的 `lowerOptionalChain` 同款）⇒ **不会**在 `?.` 上误报空指针 |
| **`!!`** | 落兜底 | `NULL_CHECK` ⇒ 程序员写的非空断言对引擎可见 |
| **`as` / `as?`** | 「不支持的二元运算符」 | `UNARYOP CAST`；`as?` 的目标类型**可空**（失败产出 null 而不是抛异常，路径继续） |
| **`is` / `!is`** | 落兜底 | `INSTANCEOF`（`!is` 再取反） |
| **`in` / `!in`** | 落兜底 | `CALL <owner>.contains/2`（owner 由符号解析给出） |
| **Elvis `?:`** | 落兜底 | 与 null 比较的 `BRANCH`：左非空取左，否则取右 |
| **数组下标** | 落兜底 | `ARRAYLOAD`（元素类型取表达式的类型） |
| **`++` / `--`** | 落兜底 | `UNARYOP` 的 `POST_INC` / `POST_DEC` / `PRE_INC` / `PRE_DEC` |
| **lambda** | 落兜底 ⇒ **lambda 体里的污点全部不可见** | 合成函数（`<宿主函数>$L$<n>`）+ 调用点 `CALL`；**捕获值当前导形参**（引擎按 `args[1..]` 绑定形参，从不绑定 `args[0]` 接收者槽 ⇒ 捕获值只能当前导形参走） |
| **`when` 的 `is` 分支** | 整条分支被跳过并记 `UNSUPPORTED_CONSTRUCT` | `INSTANCEOF` + `BRANCH` |
| **`when` 的多条件条目** | `firstConditionOf` **只取第一个条件** ⇒ 条目匹配得比源码少 | 每个条件都测一次，用布尔或合并 |
| **枚举条目** | 不被访问 | `ENUM_ENTRY` 函数（`memberKind` 新增该枚举值，末尾追加） |
| **顶层属性** | 不被访问 | `FIELD_INITIALIZER` 函数（体 = 求值 + `FIELDSTORE`，`ownerType` = 文件类） |
| **不可解析的条件** | 降级成常量 `false` ⇒ **该分支静态不可达**，分支里的污点全丢 | `HAVOC`（引擎对它一无所知 ⇒ **两个分支都可达**） |

**这一轮 Kotlin 侧最要紧的三件事**，按对分析结果的影响排：

1. **类没有构造器** ⇒ 跨构造函数的污点流整体断链（调用图上没有这条边）。
2. **`this` 从未注册** ⇒ 属性读不产生任何指令 ⇒ 字段的污点停在属性访问处。
3. **循环 / `try` / 赋值全部落兜底** ⇒ 循环体里的污点、异常路径上的污点、以及**写操作**全部不可见。

**会跳变的地方（预期，不是回归）**：属性读从「没有定义指令的临时量」变成 `FIELDLOAD` ⇒ 此前被静默丢弃的字段污点会开始流动 ⇒ finding 数量会跳变。这一点在 `04` §14 风险 5 里已经预告过。

#### Scala（`ScalaTacTranslator.java` / `ScalaTacFrontend.java`）

| 面 | 之前 | 现在 |
|---|---|---|
| **`match` 的模式种类** | 类型 / 常量 / 绑定 / 守卫 / 提取器全部落兜底 | 类型模式 = `INSTANCEOF` + `BRANCH`；常量模式 = `BINOP EQ` + `BRANCH`；绑定模式 = `MOVE`；提取器 = `INSTANCEOF` → `unapply` → `isDefined` → `get` → `FIELDLOAD`；`case 1 \| 2` = 逐个测 + 布尔或合并；守卫 = 第二个 `BRANCH`（失败落到**下一个** case） |
| **匹配链吞掉后续 case** | 无法识别的模式被当成通配符，**通配符终止整条链** ⇒ 它后面的 case 全丢 | 每种模式都有各自的测试；无法分类的模式 = `HAVOC` 条件（**两个分支都可达**）+ 记 drop ⇒ **一个 case 都不丢**，也不谎称「匹配上了」 |
| **`if` 作为表达式** | 落兜底 | `BRANCH` → 两臂 `MOVE` 进同一个结果临时量 → `LABEL endif` |
| **字符串插值** | 落兜底 | 文字与值交错的 `BINOP ADD` 链 |
| **`&&` / `\|\|`** | 落兜底 | 短路分支链（不是一条 `LAND`/`LOR`） |
| **`!x`** | 落兜底 | `UNARYOP NOT` |
| **`::` / `:::` / `++` / `++=`** | 落兜底 | `CALL <owner>.<op>/1`（接收者在 `args[0]`） |
| **`->` / `<-` / `?`** | 落兜底 | 两个操作数都求值，**零条运算符指令**（这三个是类型级算子，运行期没有对应物）⇒ 值记为 `HAVOC`（未知，而不是没有）+ 记 drop |
| **命名实参** | 实参按源码序发 ⇒ 与声明序错位 | 按声明序重排 |
| **`super.f(x)`** | 落兜底 | `CALL probe.Base.greet/1 args=[this, msg]` ⇒ **接收者在 `args[0]`** |
| **多参数表** `f(a)(b)` | 只有第一张表 | 全部参数表**摊平**成一张 |
| **类字段** | 模板里的 `val` 不被访问 | 独立的 `FIELD_INITIALIZER` 函数，由 `<init>` 调用 |
| **`try` / `catch` / `finally`** | 整块落兜底 | 与 Java 前端同形状（`L_CATCH_*` + `CATCH_HANDLER` + `L_FINALLY` + `FINALLY_ENTER`）+ `recordTryRegion` |

**提取器的形状是「量出来的」，不是猜的**：用 dotc 自己的 `-Xprint:typer` 实测，Scala 3.10 里 `scala.Tuple2$.unapply` 与 `scala.Some$.unapply` 返回的都是 **`Option[...]`**（实测类型 `PolyType(..., MethodType(..., Option[Tuple2]))`），而 case class 的 `unapply` 返回**它自己**。⇒ 三种提取器形状由**提取器的实际返回类型**驱动，不按名字分：返回 `Option` 的问 `isDefined` 再取内容；返回产品自身的直接读字段；返回内容本身的把内容当整体。

### 4.3 **补测时发现的真实缺陷**（这一轮新测出来的）

新写的逐项语法测试不是「把已有的东西再测一遍」—— 它们当场测出了 **6 个真实缺陷**，每一个都是「源码里有的东西，TAC 里没有」：

| 缺陷 | 后果 | 改法 |
|---|---|---|
| **Kotlin 的 `as` 强转根本没被降级** | `x as String` 在 Kotlin PSI 里是 `KtBinaryExpressionWithTypeRHS`，**不是** `KtBinaryExpression`（它直接继承 `KtExpression`）⇒ `instanceof KtBinaryExpression` 永远匹配不上 ⇒ 每个强转都落进兜底、被报成「不支持」，**一条指令都不产生** | `translateExpression` 增加该类型分支；`as?` 的目标类型**可空**（失败产出 null 而不是抛异常，路径继续） |
| **Kotlin 的 `!!` 落到了错的那个分支** | `!!` 在 Kotlin 语法里是**后缀**运算符（先读值、再断言），而实现把它写在了**前缀**分支里 ⇒ 前缀分支永远看不到它 ⇒ `NULL_CHECK` 一条都不产生 ⇒ **程序员写的每一个非空断言，引擎都看不见** | 挪到 `translatePostfix`；前缀分支里那段死代码删掉（一个永远走不到的分支，比没有分支更糟：它让人以为前端处理过它） |
| **Kotlin 的 `n++` 作为语句没被降级** | `KtPostfixExpression` 不在 `translateStatement` 的分派表里 ⇒ 落兜底 ⇒ **变量自增从未发生** | `translateStatement` 增加后缀 / 前缀表达式分支 |
| **Kotlin 的 `n++` 变了变量却没写回** | `UNARYOP` 只把新值写进 `dest`，**不动操作数** ⇒ 写回是**翻译器的活**。实现没写回 ⇒ 变量**从未改变** ⇒ 之后每次读到的都是自增前的值，每个循环计数器都少走一步 | 照抄 Java 前端的既有形状（`ExpressionTranslator.java:458-483`）：后缀形先 `MOVE` 快照旧值，再 `UNARYOP`，再 `MOVE` 写回 |
| **Kotlin 的 lambda 体降成了空函数** | lambda 体的**最后一条语句是它的值**，但按「语句」降级只求值操作数、**把结果丢掉** ⇒ `{ prefix -> prefix + input }` 降成**零条指令**的函数 ⇒ 体里的污点全丢 | lambda 体的最后一条按**表达式**降级 |
| **映射器会丢掉读不出来的实参** | `SidecarTacMapper` 把**映射失败**的实参直接从列表里删掉 ⇒ **后面每一个实参都前移一位** ⇒ 引擎按「`args[0]` 是接收者、实参从 `args[1]` 起」的约定读，会把 `args[1]` 的值当成 `args[0]` ⇒ **finding 报在错的参数上，或者根本不报** | 映射失败的位置用常量占位（常量不带污点 ⇒ 方向保守） |

> **最后一条是跨六种语言的**：这个映射器是 TS / ArkTS / PHP / Python / Go / C# 六个前端共用的。一个实参读不出来，其后的实参**全部错位**，而这种错位**不留任何痕迹** —— TAC 看起来完全正常。

### 4.4 一条**核实后不成立**的「缺陷」（记录下来，免得再被人当真）

勘察报告说「Go 的 builtin 调用漏掉了 `args[0]` 接收者槽」，并建议像静态调用那样塞一个常量占位。**这条前提不成立**，照做会造成**分析结果的退化**：

`AccumulatorCatalog`（`plumb-dfa/.../taint/AccumulatorCatalog.java`）把 `args[0]` 读作**接收者**，把其后的实参读作「进入接收者状态的值」：`<go>.append` / `<go>.copy` 是 **mutator**（值进容器 ⇒ 容器变脏），`<go>.mapStore` / `<go>.chanSend` 同理。Go sidecar 现在把**被操作的容器**放在 `args[0]`（`args = [dst, elem]`），这正是这套目录依赖的形状。

若在 builtin 前面塞一个常量槽：`append(dst, tainted)` 会变成 `args = [常量, dst, tainted]` ⇒ 引擎读到「接收者 = 常量」⇒ **目标 slice 再也不会变脏** ⇒ 一个收集了攻击者输入的 slice 读回来是干净的。⇒ **不改**，并把这条口径写进 `go-sidecar/README.md`（说明合成调用的槽位与包级调用的不同，以及为什么不同）。

同理，**程序级 drop 通道**（`TacProgram.addProgramDrop`）两侧都是死的：四个 sidecar 的响应里 `programDrops` 恒为 `[]`，Java 侧也没有任何调用方。要接通它必须改 `plumb-main`（`CompilationDatabaseBuilder` / `CaptureTacBuilder` 负责组装 `TacProgram`）—— 那是**他人正在改的文件**，按既定处置原则不动 ⇒ 记入 §6 的诚实清单。

## 5. 实战确实做不到的部分

### 5.1 口径

这一节只收**源码文本里根本没有那个事实**的构念。前端工作量不足、IR 少字段，都**不算**「做不到」——那是待办，不是例外。分类沿用 `02` §3 的四类根因。

### 5.2 根因一：结果由**运行时**决定

| 构念 | 为什么静态表达不了 | 保守形状 | 精度影响 |
|---|---|---|---|
| 反射 / `eval` / 动态属性 | 属性是否存在、值是什么，取决于运行期对象状态，源码里没有这个事实 | `CALL` + `UNINTERPRETED`；结果按**未知**处理 | 依赖它的规则**不出结论**（而不是出错结论） |
| Go 的求值顺序未定义处 | Go 规范明确部分表达式的求值顺序未指定 | 固定一种顺序 + `drop(SEMANTICS)` | 「先校验后使用」类规则在该函数上不成立 |
| 运行期才定的类型（TS `any`、Python 鸭子类型、C# `dynamic`） | 类型在运行期才定 | `TacType.UNKNOWN` + `domain=Dynamic` | 类型门控类规则在这些点上**不触发**（不误报，也漏报） |

### 5.3 根因二：**并发 / 调度**决定顺序

| 构念 | 保守形状 | 精度影响 |
|---|---|---|
| 线程交错的具体序列（data race 的实际发生顺序） | 顺序路径 + `Effect.CONCURRENT` 标记 | 竞态类规则报「**可能**发生」，不报「发生了」 |
| Go `select` 哪个 channel 就绪 | 保守展开成「**所有** case 都可达」 | 分支可达性被过近似 ⇒ 多报 |
| `synchronized` / `lock` 的争用顺序 | 临界区范围进 IR（IR-M）+ `Effect` 标记 | 死锁 / 顺序类规则**不报**（无法判定），原子性规则照报 |
| 协程 / 异步的**恢复顺序**（本轮由 C# 的 `await` 暴露） | 哪一个 continuation 先恢复，是运行期事实 | 挂起点进 IR（`CALL` + `effect: SUSPEND`）+ `drop(SEMANTICS, "csharp.await.suspend")` + `drop(SEMANTICS, "csharp.concurrency.order")` | 跨挂起点的数据流被过近似；函数的精度落到 `SOURCE_DEGRADED`（比笼统的 `SOURCE_LOWERED` 更强） |

### 5.4 根因三：**求解器侧**能力（不是 IR 的缺口）

| 构念 | 现状 | 保守形状 | 精度影响 |
|---|---|---|---|
| IEEE-754 浮点的精确舍入 | bridge 把所有数建成无界 Int（`Z3Bridge.java:266-278`） | `TacValueDomain.Floating(53,11)` 声明形状；**bridge 侧要接 Z3 的 FP 理论**才可能精确 | 浮点边界推理**不可用**（当前就已经不可用） |
| C# `decimal` 的 128 位定点舍入 | Z3 无十进制定点理论 | `FixedPoint(128, scale)`，按 Real 近似 | 同上 |
| 字符串的**内容级**性质 | bridge 把字符串折成**长度**（`Z3Bridge.java:258-260`） | 维持现有简化 | 内容类规则**不走 Z3** |

### 5.5 根因四：**没有运行时对应物**

| 构念 | 保守形状 | 精度影响 |
|---|---|---|
| 类型级计算（TS conditional / mapped types、Scala 3 路径依赖类型） | 运行期语义不受影响 ⇒ **对运行时不产生影响** | 只影响「按类型推断的规则」，不影响运行时分析 |
| 编译期宏 / `inline` 展开（Kotlin `inline`、Scala 3 `inline`、C# `where` 展开） | 展开是**编译期行为** | 展开前 ⇒ 内联体的控制流不可见 |

**根因四的第二条不是「能力缺口」，是前端工作量**：`inline` 展开后的形态 IR 已经能表达，缺的是前端去做这个展开。它留在路线图里，不进「例外」。

### 5.6 本轮新发现的第 5 类根因：**引擎侧没有绑定接收者的机制**

| 构念 | 为什么现有引擎表达不了 | 保守形状 | 精度影响 |
|---|---|---|---|
| **闭包 / 委托的捕获值交给闭包体** | 引擎把调用方的用户实参绑定给被调方的形参（`args[1..]`），**从不**把接收者（`args[0]`）绑定给被调方的任何形参 ⇒ 闭包从接收者里读捕获值，读到的是**未绑定**变量 | 捕获值当**前导形参**，调用点当**前导实参**传过去 | 一个**干净**的捕获值在闭包体内仍被当作污点源（过近似，方向安全）；闭包内的 sink **不会丢** |
| **把捕获值与用户实参分开计数** | 捕获值若不计入 `calleeSig` 的元数 ⇒ 引擎的形参绑定与实参位置错位；若计入 ⇒ sink 目录按元数匹配时会把捕获值当成用户实参（**可能多报**） | 捕获值计入元数（与 Python 嵌套 `def` 的既有做法一致） | sink 元数匹配按「含捕获值」的口径；这一口径是**过近似**方向 |

⇒ 这一条是**引擎侧**的能力缺口，不是 IR 的缺口：IR 有位置放捕获值，缺的是「接收者 → 被调方形参」的绑定。

### 5.7 结论

**真正「实战做不到」的是 5 类根因、14 个具体条目**（3 + 4 + 3 + 2 + 2），其中：

- **没有一条是「IR 表达不了」** —— 要么是运行期事实（源码里没这个信息），要么是求解器能力（bridge 侧可补），要么是没有运行时对应物，要么是**引擎侧的绑定缺口**。
- 唯一「IR 侧要做事」的是 `inline` 展开，而它是**前端工作量**。

⇒ **IR 足以支持全部语言的全部特性**（除类型级计算，因为它没有运行时对应物）。

下面这些**不是**「做不到」，是**这一轮没做完**。逐条给出原因与落点，避免被当成「已支持」。

### 6.2 其它语言

| 项 | 状态 | 原因 |
|---|---|---|
| Kotlin / Scala 的**语法面**扩展 | **本轮已做一大块**（见 §4.2 / §4.3）：Kotlin 的 `this`、构造器 / 次构造器、属性访问器、`init` 块、循环、`break`/`continue`、`try`/`catch`/`finally`、`throw`、赋值、`?.`、`!!`、`as`/`as?`、`is`/`!is`、`in`、`?:`、数组下标、`++`/`--`、lambda、`when` 的 `is` 分支与多条件、枚举条目、顶层属性；Scala 的 `match` 全部模式种类、`if` 表达式、插值、短路、`!`、集合运算符、命名实参、`super`、多参数表、类字段、`try`/`catch`/`finally`。**仍未做**：Kotlin 的 `data class` 合成成员改成真实体、委托属性；Scala 的 `sealed` 子类型集合（IR-N）、`is`/`as?` | 剩下的都在设计 `04` §11 的整张表里；`sealed` / `final` / `case` 这些**类修饰符**没有 IR 落点（`TacTypeDecl` 不存在），**没有丢东西**，所以不记 drop，只在 `ScalaTacFrontend` 的类注释里写明「IR 里没有家」 |

| **程序级 drop 通道**（`TacProgram.addProgramDrop`） | **未接通** | 两侧都是死的：四个 sidecar 的响应里 `programDrops` 恒为 `[]`；Java 侧**没有任何调用方**，`programDrops()` 也没有读取方。接通它必须改 `plumb-main`（`CompilationDatabaseBuilder` / `CaptureTacBuilder` 是组装 `TacProgram` 的地方）—— 那是**他人正在改的文件**，按既定处置原则不动。**影响**：文件级 / 程序级的损失（整个文件解析不了、某个依赖解析不出来）目前只能进 `programProblems`，进不了 drop 通道 ⇒ 覆盖报告看不到它们 |

### 6.3 已知但本轮不修的「静默丢失」

这些是**已定位**的真实缺陷，本轮没动，列在这里以免被当成不存在：

1. **`<clinit>` / `<init>` 同名覆盖**：静态初始化块与静态字段初始化器都叫 `<clinit>`，实例初始化块与合成 `<init>` 都叫 `<init>`；函数表按签名索引，两者签名相同 ⇒ **后写覆盖先写**，其中一个整段消失。
2. **Kotlin / Scala 的属性访问器没有独立的 TAC 函数**：属性读被降成一条 `FIELDLOAD`，没有「合成 getter」这个成员 ⇒ 依赖「合成成员」的规则在这两种语言上不可达。
3. **TS / ArkTS / Python 的 getter 读不执行访问器的函数体**：属性读被降成 `ARRAYLOAD(obj, "name")` ⇒ 访问器里的 sink **不可见**，而且**没有 drop** ⇒ 它连「降级」都不是，是**消失**。TAC 的 keyed namespace **不区分「数据属性」与「访问器属性」** ⇒ 要区分，要么在 IR 里加一个标记，要么在侧车里把访问器读降成一次真实的调用。
4. **TS 的 auto-accessor：getter 与 setter 挤在同一个签名上**：两者都是 `mod.Cls.x()`（构造器参数类型是空串），而函数表按签名索引 ⇒ **后写覆盖先写** ⇒ **一个的函数体整段消失**。C# 侧车的属性读**会**真的调 getter（`CALL … get_Current` 那一类），所以这条是 **TS 特有的**。
5. **C# 的基类构造器调用整个不存在**：`: base(a, b)` 那个**初始化器**是构造函数节点的**兄弟**节点，代码里**从来没有访问过它** ⇒ TAC 里**没有** `CALL Base.<init>/N` ⇒ 基类的构造器体**没有任何入边** ⇒ 里面的 sink **不可达**，而且**没有 drop**。

⇒ 这五条与 §3.10.7 那七条的**区别**：§3.10.7 的七条是「**做起来要动设计**」，这五条是「**已定位、落点清楚、但工作量都不小**」⇒ 它们是**下一轮的入口清单**，不是「长尾」。

### 6.4 实现期发现的设计文档与真实 API 的冲突（Go / C#）

这几条是**设计文档写错了 API**，不是实现偷懒。实现按**真实 API**做，设计文档的相应行号需要修订：

| 设计文档写的 | 真实 API（Roslyn 4.12.0 / go/types） | 实现怎么做的 |
|---|---|---|
| `PropertyPatternSyntax` | **无此类型**；真实是 `RecursivePatternSyntax`（含 `PropertyPatternClause`） | 用真实的那个 |
| `AwaitUsingStatementSyntax` | **无此类型**；`await using` 是 `UsingStatementSyntax` + `AwaitKeyword` | 用 `UsingStatementSyntax` + 关键字判定 |
| `UncheckedStatementSyntax` | **不存在**；`checked`/`unchecked` 共用 `CheckedStatementSyntax`，差别在 `Keyword` | 用 `CheckedStatementSyntax` |
| `GotoStatementSyntax` 有标签成员 | 真实 API 只有 `Expression` + `CaseOrDefaultKeyword`（**无** `Label`/`CaseLabel`） | `goto case` 单独记 `csharp.goto.caseTarget` |
| 程序级数组叫 `drops`（任务书） / `programDrops`（`08`） | 两者都发 | 两者都发（纯增量，旧解析器忽略） |
| `parameters`（任务书） / `params`（`08`） | 两者都发 | 两者都发（host 读 `params`） |

Go 侧另有一条：`defer` / `go` 语句的损失此前**既没有 problem 也没有 drop** ⇒ 静默。已按设计台账的判定补上：`defer` 记 `go.defer.order`（STRUCTURE），`go` 不记（台账判为 KEPT，其损失由 `Effect.CONCURRENT` + `startsGoroutine` + 降级精度承载）。

### 7.3 门禁

- **门禁 A（声明面完备性）**、**门禁 B（分支与异常的结构断言）**、**门禁 C（求解器可判定性）**：口径见 `02` §4。
- **「零静默」**：任何降级必须有 `drop` 或 `problem`；`UnhandledNodeReportingTest` 继续守着「支持的构念不产生问题」这一侧。
- **构造器必须可命名**：`SidecarConstructorSignatureTest` 逐个前端检查「每一次 `NEW` 都带 `calleeSig`」—— 本轮由它发现了 TS / ArkTS 的四处普通 `Object` 构造缺签名，已补。**这一轮它又抓到两处新的**：C# 的 `with` 表达式与元组各发了一条**没有 `calleeSig` 的 `NEW`** ⇒ 那个构造对**每一条构造器家族规则**都不可见 ⇒ 门禁把它拦下来了，补上之后变绿。⇒ **这条门禁是源码级的**（扫 sidecar 的源码），所以它对新加的构造**立刻**生效，不需要有人记得写用例。
- **引擎侧的白名单测试必须跑（上一轮的漏洞）**：`plumb-dfa` 的 surefire 有一张**白名单**（`plumb-dfa/pom.xml` 的 `<includes>`），**只有名单上的测试类会跑**。上一轮改了 TS sidecar 的 owner 约定，却**没跑这一层** ⇒ 3 条**正在维护**的测试变红，而且**全局 `eval` / `fetch` 不再是 sink**（真漏报，见 §3.6）。⇒ **前端改动之后，`plumb-dfa` 的白名单测试是必跑项**，不是「有空再跑」。
- **本轮新跑的一层**：这一轮改了 **Java 侧的 `SidecarTacMapper`**（`labelRef` 的读取），它影响**所有** sidecar 的引擎输入 ⇒ `plumb-dfa` 的白名单测试同样**必跑**，而且不能只看 `plumb-frontend` 绿了就收工。
- **门禁的判据**：本轮新增的两个测试类**做过变异测试**（见 §7.1 的表：四次变异，**每一次都被咬住**）。**「门禁绿」不等于「门禁有效」** —— 一个从没红过的门禁和一个没有门禁，在结果上长得一模一样。
- **侧车自己的 smoketest 也是一道门**：本轮给 Python 的 `smoketest.py` 加了四条断言（迭代协议的元素读法）⇒ 它也做过变异（把侧车退回 `step["value"]` 形状 ⇒ **FAIL: the loop variable must be the result of __next__**）⇒ **不是空门禁**。**它比 Java 侧的测试更早暴露问题**：它不需要 Java 侧那套 IR 映射就能跑。
- **一条给写测试的人的真规则**（本轮实测踩到）：**测试的函数签名必须能认出是它自己的**。keyed store 的键是**对象标签**（`type@site:context`），而 store 是 **`static` 的** ⇒ **同一个 JVM 里，签名相同、分配点相同的两个程序会共用同一批键** ⇒ 一个先跑的测试可以把后跑的测试的条目**盖掉** ⇒ 后者**在全量回归里红、单跑里绿**。本轮的临时探针（已删）就撞上了这个 ⇒ 新测试的签名改成了 `app.py_iterator_handler(any):any`。
- **一条本轮才补上的门禁**：`scripts/check_test_coverage.py` —— 它检查「每个**没有被** `@Disabled` 的测试文件**都被自己模块的 surefire 允许列表点到**」。**上一轮没有跑它** ⇒ 它这一轮跑起来就抓到了**上一轮的真漏洞**：`PythonIteratorTaintTest` **不在允许列表上** ⇒ 它的四条用例**在正常构建里从来没有跑过**（§3.10.6）。⇒ **这道门禁必须每轮都跑**，它守的是「测试**存在**」与「测试**被执行**」之间那道缝。
- **验证时不要用 `-Dtest`**：`-Dtest=...` 会**覆盖** surefire 的 `<includes>` ⇒ 于是「允许列表那一层跑过了」这句话可以是假的，而**没有任何东西会报警**。上一轮正是被它遮住的（§3.10.6）。⇒ **要跑哪一层，就把哪一层写进允许列表，然后不带 `-Dtest` 跑。**
- **另一条给写测试的人的真规则**（本轮实测踩到）：**一个测试类必须在自己的模块的允许列表里**，否则它只是一份没人执行的代码 —— 它单跑是绿的，全量里也「看起来」是绿的（因为它根本没跑）。
- **本轮新跑的一层**：这一轮改的是**引擎侧**的两处 —— `TaintedCheckerBase` 的「迭代器交出什么」与 `AccumulatorCatalog` 的「哪些调用往容器里写」—— 而它们是**所有语言共用**的一段 ⇒ 它影响**所有**语言的引擎输入 ⇒ `plumb-dfa` 的**允许列表**测试**必跑**，不能只看 `plumb-frontend` 绿了就收工。
- **本轮必须跑 Juliet 的理由（不是「有空再跑」）**：上一轮**刻意没动**「数组位置语言里『容器本身就是污点』也算元素污点」那条，理由写得很清楚：「它会**新增发现** ⇒ 直接动 Juliet 的误报率。⇒ 记在案；要动就是另一轮的事，而且要跑一遍 Juliet」（§3.9.6）。**这一轮动了它** ⇒ 那句话里的义务**这一轮到期** ⇒ 前后的 Juliet 数**必须**并排给出（§7.2）。
- **改「共享规则」时，要问「它对别的语言意味着什么」**：这一轮改的两处都是**所有语言共用**的 ⇒ 它们同时**改变**了 Java / Go / Kotlin / Scala 的结论 ⇒ 回归里**只有 Juliet 语料**能看见那个变化 ⇒ 语料**不是**额外的「锦上添花」，它是**唯一的量具**。
- **量具本身也是一道门，而且这一轮它差点变成「唯一的证据」**：Juliet 的**前后对照**是这一轮的**唯一量具**（改了共享规则 ⇒ 只有语料看得见）⇒ 所以**量具坏了比引擎坏了更危险**。这一轮量具确实坏了（§3.11.8：找不到 Juliet 的 suite 子目录 ⇒ recall 假 0；Windows 上按 GBK 解码 UTF-8 输出 ⇒ 整轮崩溃）⇒ 修了两处，并给量具加了**会出声的告警**（找不到语料文件 ⇒ 打印 `WARNING` 并声明 recall/precision 不可信）。⇒ **一条给每一轮验收的纪律**：**量具的输出要有一条「我自己干了什么」的旁证**（这次是：语料文件定位率 **4392/7015/5612/3050 全部命中**，且 `bad` 方法的行区间与源码逐个对得上）。
- **对照的两端也要先证明「真的不同」**：这一轮的「before」基线用 `git show HEAD:` 取，**而改动已经提交** ⇒ `HEAD` 就是改后 ⇒ 两份 jar **逐条目 CRC 零差异** ⇒ **那不是一次对照**（§3.11.9）⇒ 修法：基线取**改动前的那个提交**（`a5aa4c1`），并加一道**产物级内容对比**（逐条目 CRC）⇒ 修好后差异**正好 3 条**（两个引擎类 + javac 为其中一个生成的 enum-switch 合成类）⇒ **差异集合恰好等于「我改的那两个文件的编译产物」** ⇒ 两端可比。⇒ **这一层现在是门禁**：差异为 0 ⇒ 判失败；差异超出声称范围 ⇒ 判失败。

- **本轮的五道门禁全绿**：`format.py --check` / `check_i18n_docs.py` / `check_vendor_attribution.py` / `check_generated_documents.py` / `check_test_coverage.py`。**format 门禁抓到了一处**（新增的 `CsharpCollectionTaintTest.java` 没格式化）⇒ 修法：**只格式化那一个文件**（调仓库自己的 `_formatter.format_paths`），**不重排整个树** —— 因为这个工作树里还有**别人 531 处**未提交改动，整体重排会碰到**不是自己的文件** ⇒ **一条给共享工作树里干活的人的真规则**：**门禁要修，就修自己那一个文件**；**整树重排是一种越权**。

- **C# 侧车这一轮改了 ⇒ 它必须被重建，也必须被「真跑」证明**：侧车**不进 shaded jar**（jar 里只有 class 与三个配置文件）⇒ 它的正确性**只由 Java 侧那两条走真侧车的测试**证明 ⇒ 两条证据**缺一不可**：① `dotnet build -c Release` **0 错误**；② surefire 报 **0 跳过**（C# 的用例带 `@EnabledIf("toolchainAvailable")` ⇒ **侧车缺失时它们会被跳过**）⇒ **「跳过」和「通过」在报告里长得不一样** ⇒ 而 **C# 侧车没有自己的 smoketest**（它没有 `smoketest.py` / `smoketest.mjs`）⇒ **它的门禁就是那两条 Java 侧用例**。

- **本轮的 Juliet 对照多了一道**：除了「对照的两端要证明**真的不同**」，还要「**差异必须被定位**」—— 这一轮两个输出文件**不再逐字节相同**（41 行差异全在「FP examples」样本块内）⇒ 如果只写「数字一样」就收工，那个样本差异就成了**没人解释的差异** ⇒ 定位之后还要**证**它是显示层（§7.2.2.1 的三道旁证）。⇒ **一条给量具维护者的纪律**：**输出里的样本块不能当证据**。

- **「跳过」不等于「通过」**：上一轮第一次回归里有 **11 条**测试是**跳过**的（前端 7 + dfa 4），根因是 **Go 工具链不在进程的 `PATH` 里**（机器级那条指向一个只剩模块缓存的目录）⇒ 详见 §7.2 的那个现场。⇒ **汇总里的 `Skipped` 必须归零，或者写清楚为什么跳过**。

- **本轮（集合表达式）的五道门禁全绿**：`format.py --check`（**1427 个源文件**，全已格式化）/ `check_i18n_docs.py`（**36 英文 / 34 中文**成对，488 条相对链接全部解析）/ `check_vendor_attribution.py`（**OK: the vendor's name is only in the comparison table**）/ `check_generated_documents.py`（**ok: the commit does not touch a file the derived documents are built from**）/ `check_test_coverage.py`（**450 个测试文件，OK: every test file the build should run is named**）。⇒ **本轮新增的两条用例都在已有白名单的测试类里**（`CSharpValueFlowLoweringTest` 与 `CsharpCollectionTaintTest`）⇒ **`plumb-dfa/pom.xml` 一个字没动** ⇒ 也就**不需要**动别人正在改的那份 pom。

- **本轮的门禁判据**：`CsharpCollectionTaintTest` 与 `CSharpValueFlowLoweringTest` 的**新增部分**做过**变异测试**（§7.1 的 M1 / M2 / M3，**三次都被咬住**，且红的集合**精确对应**）⇒ **不是空门禁**。

##### 7.2.2.1 这次**不是**逐字节相同 —— 差在哪，怎么查出来的

上一轮写的结论是「两侧的 38 行数字逐行完全相同」；这一轮把**整个文件**逐行 diff 之后，发现**文件本身不再一样**：155 行里 **41 行**有差异，而**这 41 行全部落在「FP examples」块内** ——

- 四个「FP examples」块里，三个是**同样的 8 行、只是顺序不同**；
- 第四个是**样本成员换了一个**：CWE190 里 before 抽到 `int_getParameter_Servlet_multiply_02.java:207`，after 抽到 `int_database_multiply_02.java:385`；
- `missed positives`（**排序过**的列表）、`FP by rule`（每条规则的数量）、以及全部 TP / FP 计数**完全一致**。

⇒ ⇒ **「数字一样」与「文件一样」是两句不同的话**，而这一轮它们**真的不同**了。⇒ 差异必须被**定位**，否则它就是一个没人能推理的差异。

⇒ **原因被「证」出来了，不是被「说」出来的**（三道旁证）：

1. **同一个文件、两份 jar ⇒ finding 集合完全相同**：把那两个文件**单独**用 before-jar 与 after-jar 各扫一遍 ⇒ 两边都是 **8 条** finding，**行号与消息逐条相同** ⇒ 那个「只在 after 里出现」的条目**在 before 里也存在**，只是没被抽进样本。
2. **同一个 jar、同一个文件、扫 3 遍 ⇒ 集合相同、顺序三个都不同**：8 条 finding 在三次运行里的排列互不相同 ⇒ **「前 8 条」这个切法本身就不稳定**。
3. **量具的「FP examples」取的就是 findings 流的**前 8 条**（`scripts/juliet_measure.py:266-297`），而 findings 是**引擎写出的 NDJSON**，引擎是**并行 worker** 跑的 ⇒ **顺序不稳定** ⇒ 从不同顺序的流里切「前 8 条」，切出来的成员当然会不一样。

⇒ ⇒ **结论**：这一轮两个文件之间唯一不同的东西，是**一段样本的排列**，**不是发现**。⇒ **计数与规则分布才是承重的那一层**，而它们**逐条相同**。

##### 7.2.2.2 为什么计数一条没动（**数**出来的，不是猜的）

本轮改的规则是「mutator 的实参贡献它**携带**的污点」⇒ 它与旧规则**只有在实参是容器时**才有差别（实参是标量时，`elementTaintOf` 的回退分支就是「这个变量自己的污点」⇒ **与旧规则同一个答案**）。

⇒ 所以问题是：**这个语料里有没有「实参是容器」的集合写？** ⇒ 这是**可以数**的，不必推理：把五个语料目录里所有 mutator 调用的**实参文本**收集起来去重 ⇒

| 项 | 数 |
|---|---|
| mutator 实参的**不同文本** | **3 种** |
| 具体是什么 | `0, data`（2961 处）、`1, data`（2961 处）、`2, data`（2961 处） |
| 合计调用点 | **8883** |
| 其中**实参是容器**（数组字面量或集合变量）的 | **0** |

⇒ ⇒ **一处都没有** ⇒ 本轮改的那条规则**在这个语料上根本没有分支可走** ⇒ 计数**必然**一条不动。⇒ 而这些写法的形状正是「**key 是常量、value 是脏标量**」（`map.put(0, data)`）⇒ 新旧规则**同进同退**。

⇒ **一条给量具维护者的纪律**：**「数字一样」这句话，必须能回答「为什么一样」** —— 上一轮靠逐个统计（§7.2.1）回答了；这一轮也是靠**逐个统计**回答的（3 种实参文本、0 处容器实参），**不是**靠「规则看起来不影响 Java 语料」。⇒ 而**这一轮还多出一条**：**输出文件的「样本块」不能当证据** —— 它是**并行顺序**的切片 ⇒ 要比就比**计数与规则分布**，或者**把样本排序后再比**。

⇒ **两条并列的教训**（这一轮的对照同时踩到了两头）：**对照的两端要证明「真的不同」**（上一轮：基线取错了提交 ⇒ 差异 0 条）；**对照的两端还要证明「差异在哪」**（这一轮：文件不再逐字节相同 ⇒ 差异必须被定位到具体的块，并被证明是显示层）。

#### 7.2.3 本轮**只改侧车** ⇒ Juliet 两侧对照**不必跑**，但**不是**「懒得跑」

前两轮（§7.2.1 / §7.2.2）都跑了 Juliet 的**前后对照**，而那两轮**都改了引擎的共享规则** ⇒ 那些改动**必然**会改变引擎的输出 ⇒ 对照是**必跑项**。

⇒ 但「跑不出新信息」这句话**不能靠推理交差** ⇒ 它要被**证**出来。这一轮给了**三条结构性证据 + 一次抽点复核**：

### 7.4 两处测试口径的同步（需要读者知道）

1. `R1108AliasNullGuardTest` 的辅助函数原本在 `args[0]` 找被探测的值。这依赖「非限定调用没有接收者槽位」这个**旧形状**。J8 之后 IR 的约定是 `args[0]` 恒为接收者槽位，该辅助函数改为**在实参里找**被探测的值 —— 它问的问题（「这个值被用到的那个点上，它是否已证明非空」）没有变，只是找的位置变了。

## 8. 给读者的七句话

1. **探针连着五轮找出真缺陷，而这一轮的第一件事是核实症状的前提：「集合 Add 没进 TAC」—— 不成立。** 探针实测：`list.Add(cmd)` 在 TAC 里是**一条 `CALL System.Collections.Generic.List.Add/1`**，接收者槽是**集合**、实参槽是**被加进去的值** ⇒ **侧车没有错、IR 没有错、IR-P 的「callee 名必须是真实方法名」也没有错** ⇒ **要改的是引擎怎么读这条 TAC**。真正的断点有三处**通用**规则（不是十个 C# 特例）：① 「迭代器交出什么」在**数组位置**语言那一支**不读容器自己的污点**（keyed 那一支早就有）⇒ 集合的污点**取不到**；② 集合目录**不认** C# 的拼法（`Enqueue` / `Insert` / `AddRange` / `Stack` / `Dictionary`）；③ map 的**脏 key** 会让它的 **value** 看起来脏。⇒ **十个变体全中**（§3.11）。
2. **「同一个问题，两个分支给两个答案」是最难查的一类缺陷，因为它看起来像「语言不同」。** 引擎问「迭代器交出什么」时，keyed 的语言问 keyed store **并回退到容器自己的污点**，数组位置的语言**只**问数组跟踪器 ⇒ **同一个程序在 TypeScript 里报、在 C# 里不报**，而两边的**源代码一模一样**。⇒ 而这条回退**上一轮明确记过、并且刻意没动**（理由：「它会**新增发现** ⇒ 直接动 Juliet 的误报率。⇒ 要动就是另一轮的事，而且要跑一遍 Juliet」）⇒ **这一轮动了 ⇒ 那笔债这一轮到期** ⇒ Juliet 的前后数**并排**给出（§7.2）。⇒ **一条给改引擎的人的真规则**：**改「共享规则」时，要问「它对别的语言意味着什么」** —— 回归里**只有语料**能看见那个变化。
3. **这一轮还多出两个教训：量具坏了，比引擎坏了更危险；而对照的两端会「一样」，且一样得不报错。** 引擎的缺陷给出「少报」或「多报」的**数字**；量具的缺陷给出的是「**恰好 0.0000**」这种**看起来像结论**的数字，而且**一行错都不报**。⇒ 第一次跑 Juliet 得到的正是 `0.0000 / 0.0000`（四个 CWE 全部），它差点被当成「**引擎的 DFA 规则在这四个 CWE 上完全不行**」写进文档 ⇒ 真因是**量具找不到 Juliet 放在 suite 子目录里的语料文件**（两个 CWE 测得正常、而它们的规则恰好是 AST 规则 ⇒ 更像「引擎的 DFA 规则不行」）⇒ 修量具，并给它加了**会出声的告警**（§3.11.8）。⇒ 而第一版的「before」用 `git show HEAD:` 取基线，**改动已经提交** ⇒ `HEAD` 就是改后 ⇒ **对照变成拿同一份东西比两次**，**构建成功、数字照打、零报错** ⇒ 抓住它的是**产物级内容对比**（两份 jar 逐条目 CRC **差异 0 条** ⇒ 「没有对照」）（§3.11.9）。⇒ **两条纪律**：**当语料是唯一的量具时，先证明量具自己是对的**；**对照的两端，先证明它们真的不同**。
4. **剩下的缺口都写着落点，而这一轮把「缺口」与「已修」分得比上一轮更干净。** §6.2 与 §6.3 里的每一条都带着**证据**与**下一步怎么做**：集合的**逐元素精度**（要 keyed store 的**键语义**，不是一条能加进数组跟踪器的规则）、Python 的 `append` 在**类型定不出来**时没降级（**前端**的缺口 ⇒ 引擎侧已经认 `append` 了）、`await foreach`（整套没降）、C# 集合表达式的 **spread 元素**（`[..rest]`）与**字典的集合表达式**（`[("k", v)]`）⇒ 它们**不是「长尾」**，是**下一轮的入口**。
5. **这一轮留下的不是「多支持了一种写法」，而是两条不变量。** ① **同构念同形状**：显式 `new T[] { … }` 与隐式 `new[] { … }` 落到**同一个 helper** ⇒ 以后再有人加第三种写法（**集合表达式** `[cmd]` 就是），走的也是同一条路 —— **这句话在下一轮被改了边界**（见第 7 句：同一个构念**加上同一个目标类型**才同形状）；② **同问同答**：mutator 与迭代器问的**是同一个问题**（「这个容器带了什么」）⇒ 用**同一个函数**回答 ⇒ 上一轮刚吃过的「同一个问题，两个分支给两个答案」不会再回来。⇒ 而这一轮的两个断点**分处前端与引擎**：隐式数组**根本没降级**；就算降级了，引擎问的也是「实参**本身**脏不脏」，而脏的是**元素** ⇒ **只修前端，污点仍然断在引擎那一步** ⇒ 两者**都**要修，才轮到 `list.AddRange(new[] { cmd })` 通。
6. **这一轮还多出两条纪律，都是关于「证据长什么样」的。** ① **「跳过」不是「通过」**：第一次回归里前端 7 条、dfa 4 条 Go 测试是**跳过**的（机器级 `PATH` 那条 Go 条目指向一个**只剩模块缓存**的目录，真正的工具链只在**用户级** `PATH` 里）⇒ 照抄汇总就会写成「320 通过 / 0 失败」，而**那 7 条一次都没跑** ⇒ **汇总里的 `Skipped` 必须归零，或者写清楚为什么跳过**。② **「数字一样」不等于「文件一样」，而差异必须被定位**：这一轮两个 Juliet 输出**不再逐字节相同**（41 行差异全在「FP examples」样本块内）⇒ 那个样本是**并行顺序**的切片（**同一个 jar、同一个文件、扫三遍 ⇒ 集合相同、三个不同顺序**）⇒ 承重的是**计数与规则分布**，而它们**逐条相同**；至于「为什么一样」—— 语料里 **8883 处** mutator 写的实参只有 **3 种文本**（`0, data` / `1, data` / `2, data`）⇒ **一处容器实参都没有** ⇒ 本轮改的那条规则**在这个语料上根本没有分支可走** ⇒ 计数**必然**不动 ⇒ **「为什么」也是数出来的，不是猜的**。
7. **这一轮把上一轮的两条不变量改了边界，并多出三条纪律。** ① **「同构念同形状」的准确说法是「同一个构念 + 同一个目标类型 ⇒ 同一个形状」**：集合表达式 `[x]` 在**数组目标**下走的是与显式/隐式数组**同一个 helper**，但在**具名集合目标**（`List<string> items = [x]`）下必须是 `NEW` + `Add`（那是 C# 的**集合构造器模式**），在**接口目标**（`AddRange([x])`）下没有可构造的集合 ⇒ 走数组形状 ⇒ **目标类型决定形状，而目标类型得从语义模型的 `ConvertedType` 取**（集合表达式**没有自己的自然类型**）。② **只改侧车时，A/B 要换的是侧车，不是 jar**：侧车**不进 jar** ⇒ 换 jar 得到的是一次**空对照**（两份引擎一模一样）⇒ 这一轮用 `PLUMB_CSHARP_SIDECAR` 指向两份不同的侧车、**jar 用同一份** ⇒ **0 findings → 2 findings**。③ **变异脚本自己会造假，而且有三种形状**：**reactor 停在第一个红的模块** ⇒ `plumb-dfa` 根本没跑 ⇒ 脚本读到**上一轮的旧报告** ⇒ 报出「引擎侧全绿」这个**假绿**（⇒ 修法：分开跑 + 跑前删报告 + **报告必须比本次运行新**）；**`read_text`/`write_text` 把 CRLF 变成 LF** ⇒ 恢复文件时行尾被改掉（⇒ 一律**按字节**读写）；**字节模式与文件行尾不一致** ⇒ 匹配 0 处（⇒ 先探测**主导行尾**）⇒ **「被咬住」这句话，必须由报告的新鲜度来保证**。④ **「这一轮不必跑 X」和「这一轮没跑 X」必须分开说**：本轮只改侧车 ⇒ 引擎的**输入**没变 ⇒ Juliet 的数**不可能**变 ⇒ 两侧对照**跑了也没有新信息** ⇒ 但这句话**不能靠推理交差**，它带了**三条结构性证据**（引擎主源码的 diff **为空**、jar 的 sha256 **没变**、`plumb-main` **不在 reactor 里** ⇒ jar 没重建、侧车**根本不在 jar 里**）**加一次 CWE369 抽点复核**（TP **1900** / FP **7943** / recall **0.3652** / precision **0.1930** / f1 **0.2526** ⇒ 与上一轮记录**逐字相同**，且量具**无 `WARNING`**）⇒ **判据是「X 的输入变没变」，而「输入」这件事要能验** ⇒ **输入没变 ⇒ 不必跑；输入变了 ⇒ 必跑，没有例外**。⇒ 而这一轮的回归是 **1802 通过 / 0 失败 / 0 跳过**（前端 **322**、dfa **1089**，连续第四轮**不带 `-Dtest`** ⇒ 跑的是允许列表那一层）、五个侧车 smoketest 全绿、五道门禁全绿。
