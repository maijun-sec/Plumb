## 1. 现状：Z3 今天是怎么被用的

### 1.1 三层结构

| 层 | 类 | 职责 |
|---|---|---|
| 判定接口 | `SolverZ3Bridge` | `check(String predicate, Map<String,Object> bindings)`（`SolverZ3Bridge.java:76`）；默认 `implies`（`:87-121`） |
| 本地求解 | `LocalSolverBridge` | 纯 Java 的递归下降解析器 + 解释器，永远可用 |
| 真求解 | `Z3Bridge` | 包 `com.microsoft.z3`（`tools.aqua:z3-turnkey:4.14.0`）；原生库不可用时**回落**到本地求解器（`Z3Bridge.java:93-101`） |

### 1.2 谓词是**字符串 mini-DSL**

`Z3Bridge.Z3AstBuilder`（`Z3Bridge.java:114-311`）自己写的文法：

- 逻辑：`||`、`&&`、`!`（`:138-164`）
- 比较：`==`、`!=`、`<`、`<=`、`>`、`>=`（`:166-198`）
- 算术：`+`、`-`（`:200-213`）、`*`、`/`（`:215-228`）
- 原子：括号（`:234-247`）、`true`/`false`（`:248-249`）、带符号字面量（`:250-256`）、
  字符串字面量（`:258-260`）、数字（`:261-263`）、标识符（`:265-278`）

`PathCondition.extractVars`（`PathCondition.java:175-188`）用正则
`[A-Za-z_][A-Za-z0-9_]*` 抽变量名 ⇒ **谓词里的标识符必须是合法标识符**。

### 1.3 语义映射（**这里有四个重要近似**）

| 输入 | Z3 里的表示 | 证据 | 近似程度 |
|---|---|---|---|
| 整数 | `mkInt` | `Z3Bridge.java:266-271` | **无界** ⇒ int32 的溢出/回绕**不是** Z3 推的，是 checker 的区间事实推的 |
| 浮点 | 也是 `mkInt`（`nv.longValue()`） | `Z3Bridge.java:269-271` | **整数化** ⇒ 浮点语义不可判定 |
| 字符串 | `mkInt(tok.length())` | `Z3Bridge.java:258-260` | **折成长度** ⇒ 内容级性质不可判定 |
| 布尔 | `mkITE(e, 1, 0)` | `Z3Bridge.java:285-287` | 精确 |
| 数字当布尔 | `mkNot(mkEq(e, 0))` | `Z3Bridge.java:301-306` | 「非零即真」，与本地求解器一致 |
| 未绑定的标识符 | `mkIntConst(tok)` | `Z3Bridge.java:278` | **自由变量**（正确行为：未知就是未知） |

### 1.4 守卫从哪来：**今天全部来自 checker 自己**

| 写入点 | 写什么 | 证据 |
|---|---|---|
| `DivByZeroChecker` | `guardStore().add(var.name(), "data != 0")` | `DivByZeroChecker.java:215-216` |
| `BoundaryConstraintChecker` | 每个变量的区间守卫（字符串形式） | `BoundaryConstraintChecker.java:692` 附近；区间表在 `:654-659` 的 `STATIC_FINAL_TABLE` |
| `IntOverflowChecker` / `IntUnderflowChecker` / `ArrayIndexChecker` | **消费** `impliedGuard` | `IntOverflowChecker.java:431-433`、`IntUnderflowChecker.java:394-396`、`ArrayIndexChecker.java:220-222` |

`GuardStore.impliedGuard`（`GuardStore.java:115-131`）是两级：
1. **结构快路径**：`PathCondition.structurallyImplies`（`:157-165`）+ `StructuralImply.match`；
2. **SMT 回落**：`PathCondition.implies`（`PathCondition.java:106-131`）问「前提 ∧ ¬结论 是否 UNSAT」。

### 1.5 结论：**Z3 今天的盲区**

> **没有任何一条路径条件是从 CFG 推出来的。**
> Z3 只能回答「某个 checker 已经想到的守卫之间是否蕴含」，回答不了「这条路径上的条件是什么」。

后果有三层：
1. **路径敏感分析拿不到路径条件**（`PathSensitiveCheckerBase` 存在，但没有条件来源）；
2. **开关支、循环条件、`if (x > 0 && x < 10)` 的合取**全部丢失；
3. **审计 P0-2 认定控制流建错了**（Java `switch` 多标签 arm 只测第一个、
   `&&` 不短路、ArkTS switch 按顺序执行 case）⇒ **守卫本身就是错的**，
   送进 Z3 只会更快得到错答案。

⇒ **IR-C 的 `TacGuard` 是 Z3 侧的根**：把「分支条件」变成 IR 的一等数据，
路径条件才能从 CFG 自动推出来。

## 2. 目标架构

```
        源码
          │  前端（各语言）
          ▼
    TAC 指令流 + TacGuard（IR-C） + TryRegion（IR-F） + TacDrop（IR-B） + 类型维度（IR-D/K/N）
          │
          ▼
     TacCfgBuilder：切基本块、连异常边、连 finally 出口
          │
          ▼
   ┌──────────────────────────────────────────────┐
   │ 路径条件推导（新增）                            │
   │  走到一条边 ⇒ 把该边的 TacGuard 渲染成 DSL 谓词  │
   │  ⇒ 累积成 PathCondition（按块、按路径）         │
   └──────────────────────────────────────────────┘
          │
          ▼
   GuardStore（按变量名聚合） → PathCondition.implies → Z3Bridge / LocalSolverBridge
          │
          ▼
   checker：消费既有 impliedGuard 调用（**消费侧零改动**）
```

**关键设计点**：新推导出的守卫与 checker 手写的守卫**进入同一个 `GuardStore`**，
用**同一套字符串 DSL**、**同一套变量名**。

⚠ **但「进入同一个 `GuardStore`」今天并不成立，必须先补一处**（实测，`01` §0.2 同源核对）：

| 事实 | 证据 |
|---|---|
| `GuardStore` 的载荷是**字符串 DSL 谓词**，不是 `TacGuard` 对象 | `GuardStore.java:54`（`Map<String, List<String>> byVar`）、`:69`（`add(String var, String predicate)`） |
| `GuardStore` 全仓**只有一个生产点** | `DivByZeroChecker.java:216`（`this.currentCtx.guardStore().add(g.boundedVar().name(), arithDesc)`） |
| 边界 checker 的守卫**不进 `GuardStore`**，写的是**自己的局部 map** | `BoundaryConstraintChecker.java:117`（`private final Map<TacOperand.TacVar, List<String>> guards`）、`:694`（`emitGuard`）、`:718`（`guards.computeIfAbsent(v, …).add(desc)`） |
| 该类的 javadoc **声称**会 surfacing，与代码不符 | `BoundaryConstraintChecker.java:73`、`:107` 都写着 "surfaced into {@link GuardStore}"；代码没做 |
| 局部 map 的实际用途只有它自己的 Tier-1 | `BoundaryConstraintChecker.java:830`（Tier 1 合取）、`:1115`（`withGuardsMetRanges`） |

⇒ **因此「现有 checker 一行都不用改」要拆成两半**：

| 侧 | 改动 | 说明 |
|---|---|---|
| **消费侧** | **零改动** ✅ | checker 只调 `ctx.guardStore().impliedGuard(...)`（`IntOverflowChecker.java:431-433`、`IntUnderflowChecker.java:394-396`、`ArrayIndexChecker.java:220-222`），签名与语义都不变 |
| **生产侧** | **必须改 1 处** ⚠️ | `BoundaryConstraintChecker.emitGuard`（`:694`）要**双写**：局部 map（保留 Tier-1 行为）+ `GuardStore`（让跨 checker 蕴含成立）。否则新推导的守卫与边界 checker 的守卫**永远碰不到面**，「互相蕴含」这个收益拿不到 |

⇒ **这个 1 处改动是 IR-C 收益的前置条件**，不是可选项。已列入 `10` 的改动清单（`K`/阶段依赖）。

## 3. `TacGuard` → DSL 的渲染规则

### 3.1 渲染表

| `TacGuard` | 渲染 | 备注 |
|---|---|---|
| `Compare(a, EQ, b)` | `a == b` | `a`/`b` 是 `Const` 时直接写字面量 |
| `Compare(a, NE, b)` | `a != b` | |
| `Compare(a, LT/LE/GT/GE, b)` | `a < b` / `a <= b` / `a > b` / `a >= b` | |
| `Truthiness(v, TRUE)` | `v != 0` | **与 `Z3Bridge.java:301-306` 的「非零即真」一致** |
| `Truthiness(v, FALSE)` | `v == 0` | |
| `Membership(v, opts)` | `(v == o1 \|\| v == o2 \|\| …)` | switch 的多 case 合并 |
| `TypeTest(v, T, false)` | **`true`**（不可表达） | 类型测试不是数值命题 |
| `Always(true/false)` | `true` / `false` | |

**`TypeTest` 渲染成 `true`** 是刻意的：它**不贡献任何数值约束**，
但它**不丢失信息**——类型事实走**另一个事实域**（空值事实 / 类型事实），不进路径条件的数值部分。
⇒ 这是「不撒谎」原则的一个具体落点：**不能表达成数值谓词的东西，就不要硬塞进数值谓词**。

### 3.2 变量名契约（**必须写死，否则与 `GuardStore` 对不上**）

- 谓词里的标识符 = **`TacOperand.TacVar.name()`** 原文。
  这是 `GuardStore` 的 key（`GuardStore.java:35-37`：「Keys are the guarded variable's name」）。
- ⇒ **前端必须保证 TAC 变量名是合法标识符**：`[A-Za-z_][A-Za-z0-9_]*`。
  今天的临时变量名形如 `t_t12`（`TacOperand.java:64-66` 的注释说 raw name 已经是唯一的）⇒ 合规。
  **新前端必须遵守这条**：临时变量名不得含 `.`、`[`、`]`、`#` 等。
- 若某个变量名不合规 ⇒ 渲染器把它**映射成一个安全别名**，并在**同一个函数内**保持映射一致；
  同时 `GuardStore` 的 key 也要用同一个别名 ⇒ **改名要改两处**，所以更好的做法是**前端就不产生非法名**。

### 3.3 算子覆盖的限制（**必须诚实标注**）

DSL 的文法里**没有**：位运算（`&`、`|`、`^`、`<<`、`>>`）、取模（`%`）、一元负号之外的算术函数。

⇒ **含位运算的守卫无法渲染成 DSL 谓词**。
处理方式（三级）：
1. **能改写成等价比较的**（如 `x & 0xFF == y` 在某些形态下可改写）⇒ 改写；
2. **改写不了的** ⇒ **不渲染成字符串**，而是走**区间层**（`BoundaryConstraintChecker` 的 Tier 0）；
3. **两层都办不了的** ⇒ 该守卫**不进入 `GuardStore`**，并**在函数的 `drops` 里记一条**
   （`construct = "guard.unrenderable"`, `impact = STRUCTURE`）——
   **静默丢掉一条守卫，正是审计里最贵的那类丢失。**

⇒ 这条是「守卫可渲染率」这个指标的意义：**它必须被测量，而不是被假设。**

## 4. Z3 侧的三处增强

### 4.1 排序与有界性（IR-D 的兑现）

**今天**：所有数都是无界 `Int`（`Z3Bridge.java:266-278`）。

**v2**：按 `TacValueDomain` 生成约束：

| domain | Z3 排序 | 附加约束 |
|---|---|---|
| `Integral(bits, signed)` | Int | `-2^(bits-1) <= x <= 2^(bits-1)-1` |
| `Unbounded` | Int | 无 |
| `FixedPoint(bits, scale)` | Real | scale 注释；**标为不精确** |
| `Floating(m, e)` | Real | **标为不精确**（IEEE 754 的舍入未被建模） |
| `Dynamic` | 不参与数值约束 | — |

⇒ **int32 的溢出/回绕第一次可以由 Z3 推**，而不是由 checker 的区间表推。

**但要诚实**：`Z3Bridge` 目前把浮点也建成 Int（`:269-271`）⇒
`Floating` 走 Real 是**行为变更**，会让浮点相关的既有判定改变。
⇒ **建议：v2 先只对 `Integral` / `Unbounded` 启用有界约束**，
浮点与定点保持现状并显式标注「近似」，等桥接侧接了 Z3 的 FP 理论再说。

### 4.2 从 CFG 推路径条件（IR-C 的兑现）

**推导算法**（在 CFG 上做一次数据流）：

```
对每个基本块 B：
  in[B] = ⋃ over 前驱 P of ( out[P] ∩ {该边上的守卫} )
  out[B] = in[B] ∪ {块内的守卫}
  若块内有 CATCH_HANDLER / FINALLY_ENTER ⇒ 该块额外引入一条「异常路径」的守卫集
```

**边上的守卫从哪来**：IR-C 把 `TacGuard` 挂在 `BRANCH` 指令上 ⇒
`trueLabel` 边取守卫本身，`falseLabel` 边取**它的否定**。
⇒ **否定由渲染器负责**（`Compare(a, EQ, b)` 的否定是 `a != b`；`Membership` 的否定是 `a != o1 && a != o2`）。

**为什么这很值钱**：一条路径上的条件现在**是算出来的**，而不是每个 checker 各写各的。
⇒ 「`x != 0`」这件事，源码里 `if (x != 0)` 写了、或者 `DivByZeroChecker` 写了，
**在 `GuardStore` 里是同一条**，可以互相蕴含。

### 4.3 蕴含查询的复用（不改现有 API）

`PathCondition.implies`（`PathCondition.java:106-131`）已经是通用形式
（前提 ∧ ¬结论 是否 UNSAT）。⇒ **不需要新 API**。

**唯一要改的**：`GuardStore.impliedGuard`（`GuardStore.java:115-131`）的两级顺序可以保留，
但**第二级（SMT）之前应先做「路径条件查询」**：
「当前路径条件是否蕴含结论？」比「全局已记录的守卫是否蕴含结论？」**强得多**
（全局守卫是所有路径的并集 ⇒ 更弱 ⇒ 更容易得出「不能蕴含」）。

⇒ **建议新增**：`GuardStore.impliedGuardOnPath(var, consequent, bindings, pathCondition)`，
或者把 `PathCondition` 作为 `impliedGuard` 的一个可选参数。
**这一条是 IR-C 最大的实际收益**：守卫从「全局并集」变成「当前路径」。

## 5. 数据流侧的集成

### 5.1 类型维度的兑现（IR-D / IR-K）

| 消费点 | 今天 | v2 |
|---|---|---|
| **`Range.ofType(TacType)`**（`checkers/boundary/Range.java:133-143`） | 按 `TacType.Kind` 查整数区间表：`BYTE`/`SHORT`/`CHAR`/`INT`/`LONG` 各有精确区间，**`UNKNOWN` 兜底成 int32 区间**（`:141`），其余 `default -> BOTTOM` | 改为**先读 `domain`**（无则按 Kind 兜底）⇒ 区间来自语言事实，不是硬编码表 |
| **四份逐字复制的 `isArithType`**：`checkers/boundary/OverflowConstraintChecker.java:159-165`、`UnderflowConstraintChecker.java:142-148`、`DivZeroConstraintChecker.java:95-101`、`ArrayBoundsConstraintChecker.java:109-115` | 判定「是否算术类型」；四份 switch **形状完全相同**，且都把 `UNKNOWN` 列入算术类型 | 统一读 `domain`；**四处必须一起改** —— 漏一处 ⇒ 该 hazard 仍按旧口径判 |
| `checkers/boundary/BoundaryConstraintChecker.java:654-659` 的 `STATIC_FINAL_TABLE` | 硬编码 `Integer.MAX_VALUE` 等（Java 专属常量） | 保留，但**优先用 `domain`** |
| `checkers/taint/NumericTruncationChecker.java:149` | 按 kind 区分窄化 | 加 `domain` 区分「等宽」与「窄化」 |
| `checkers/taint/IntOverflowChecker` / `IntUnderflowChecker` | 各自的区间（与上面 `boundary` 包里的 `OverflowConstraintChecker` / `UnderflowConstraintChecker` **是不同类，只是名字相近**） | 统一读 `domain` |
| 类型门控（sink 要求某类型） | `UNKNOWN` ⇒ 门控失效 | 联合类型/泛型实参进 IR 后，门控可以精确到 `string \| null` 的非空分支 |

> ⚠ **值域消费点是 6 处，不是 1 处。**
> 上面这张表是逐处枚举的结果，**不是**「一个 `switch(kind)`」。初稿曾把它记成
> `BoundaryConstraintChecker.java:135` 的单个 `switch(kind)` —— 那个行号是**空行**
> （它上面那行 `:134` 才是分隔注释 `// ─────────── Subclass hooks ───────────`），
> 而且该文件里**根本没有**按 `TacType.Kind` 的 switch（它只在 `:615` 判 `Kind.CLASS`
> 用来回退到 receiver 变量名）。真正的分派点是 `Range.ofType`（`Range.java:135` 的
> `switch (t.kind())`，`:141` 把 `UNKNOWN` 兜底成 int32 区间）加四份复制的
> `isArithType`。⇒ **IR-D 落地时漏改任意一处，那个 hazard 就仍按旧口径判定。**
>
> ⚠ **`UNKNOWN` 被当成 int32。** `Range.ofType` 对 `UNKNOWN` 返回
> `of(Integer.MIN_VALUE, Integer.MAX_VALUE)`（`Range.java:141`），
> 四份 `isArithType` 也都把 `UNKNOWN` 列为算术类型。
> ⇒ 一个**没有类型信息**的整数变量，溢出判定按 **32 位**做。
> ⇒ 对 Python（任意精度）、Go（平台相关 32/64）、PHP（平台相关）而言，
> **只要前端没把 `domain` 填出来，这些语言的整数溢出判定就是错的**（按 int32 判，
> 但语言里不会溢出）⇒ 这是**误报**，且是 IR-D 落地前就存在的误报。
> ⇒ IR-D 必须**先于**这些语言的前端上线，否则「填了 domain 但引擎不读」等于白填。

### 5.2 泛型与联合类型的兑现（IR-K）

- `TacType.typeArguments` ⇒ **`List<User>` 与 `List<Order>` 不再是同一个类型**（今天是同一个 `CLASS`）。
- `TacType.unionMembers` ⇒ **`string | null` 不再塌成 `STRING`**（今天 TS 的 flag 首位匹配直接塌掉）。
  ⇒ 空值检查可以区分「这个值是 `string`」与「这个值是 `string | null`」。
- `TacType.bound` ⇒ 类型变量 `T` 不再被当成 `Object`（今天只剩上界，身份丢了）。

⇒ **假类名的终结**是这一节的主要收益：今天 `"A|B"` 不是一个类型 ⇒
**任何按类型匹配的规则都永远不命中**（不是误报，是漏报）。

### 5.3 `calleeSig` 规范化（IR-P）的兑现

**这是跨函数污点的总开关。** 今天的三个具体故障：

| 故障 | 今天 | v2 |
|---|---|---|
| Python 方法调用解析不了 | 引擎的 `declared_arity` 减接收者、签名不减 ⇒ 两边对「参数个数」的约定不一致 | **统一规范**：arity 永远只数显式实参；接收者一律显式放 `args[0]` |
| Java for-each 的迭代协议 | 合成短名 `"iterator/0"`、`"hasNext/0"`、`"next/0"` ⇒ 不是任何真实方法名，调用图解析不到 | 必须是**真实方法名**（如 `java.util.Iterator.hasNext/0`） |
| TS/ArkTS 的 owner 未知 | `UNKNOWN_OWNER` 占位符 | **不允许占位**：owner 缺失要结构化表达（`ownerType = null` + `calleeSig` 只含方法名与 arity） |

⇒ **规范必须写在一处**（`08-wire-协议-v2.md` §2 / 引擎的 resolver），
并由**门禁**校验：每个 sidecar 产出的 `calleeSig` 都能被引擎的 resolver 解析。

### 5.4 丢弃可见性的兑现（IR-B）

| 消费点 | 动作 |
|---|---|
| `ModelCoverageComputer.java:133`（今天唯一的 `irPrecision()` 生产读点） | 扩展为三档统计，并**列出 `SOURCE_DEGRADED` 的函数与它们的 drops** |
| 报告器（`plumb-dfa/.../engine/FindingReporter.java`） | 报告尾部附「本次扫描的丢弃清单」（按 `construct` 聚合计数） |
| 覆盖率门禁 | 「每个语言的声明种类清单 100% 被覆盖」⇒ 缺项就是红 |

## 6. 精度门控：哪些 checker 在 `SOURCE_DEGRADED` 上必须停

**方向性规则**（`IrPrecision.java:42-56`）：精度只能**压制误报**，不能**证明安全**。

⇒ 在 `SOURCE_DEGRADED` 的函数上：

| checker 类别 | 行为 | 理由 |
|---|---|---|
| **结构敏感**（穷尽 switch、死代码、不可达代码） | **停** | 语义有损 ⇒ 结构更不可信 |
| **语义敏感**（污点、空指针、注入、路径穿越） | **照跑** | 丢的是局部，语义敏感的部分仍然成立 |
| **类型敏感**（sink 的类型门控） | **照跑，但门控按 `domain` 放宽** | `UNKNOWN` ⇒ 门控不触发（既有行为） |

**关键**：`SOURCE_DEGRADED` **不能**用来压制污点告警。
理由：`SOURCE_DEGRADED` 表示「有一块语义没读进来」⇒ 那块里可能有真问题。
⇒ **降级只让结构类 checker 停，不让语义类 checker 闭嘴。**

## 7. 性能预算

Z3 查询不是免费的。v2 会**大幅增加**查询量（守卫从「checker 想到的」变成「CFG 推出的」）。

| 措施 | 说明 |
|---|---|
| **两级判定保留** | `GuardStore.impliedGuard` 的结构快路径先跑（`GuardStore.java:122-124`）⇒ 大多数蕴含是语法可判的，不进 Z3 |
| **查询缓存** | 引擎已有 `CachedZ3Bridge`（`plumb-dfa/.../solver/CachedZ3Bridge.java`）⇒ 同一谓词 + 同一绑定只查一次 |
| **有界桥** | `DfaEngine.java:581`/`:1913`/`:1964` 已在用 `boundedSolverBridge(ctx)` ⇒ 沿用同一入口 |
| **按需求解** | 路径条件**只在需要判定「这条路径可达吗」时**才求解；污点传播本身不需要 Z3 |
| **预算与降级** | 超过预算 ⇒ 退回「保守可达」（多报，不漏报）⇒ **必须记录**（记进 `drops` 或分析日志），不能静默 |

⇒ **度量口径**（每个阶段都要报）：
- 「自动推出的守卫数」；
- 「守卫可渲染率」（不可渲染的占比，见 §3.3）；
- 「Z3 查询次数 / 命中缓存比例 / 超出预算次数」。

## 9. 风险

1. **守卫写错 ⇒ Z3 更快地给出错答案**（§1.5 的第 3 点）。
   ⇒ 对策：**守卫必须来自语言语义**（`TacGuard` 的每个变体对应一种语言语义），
   不是「前端觉得大概是这样」。⇒ **门禁**：每个语言的前端必须为它的每种条件形态
   给出**对照表**（语言写法 → `TacGuard` 变体），并由测试验证。
2. **有界约束会改变既有判定**（int32 从「无界」变成「有界」）⇒ 溢出类 finding 的数量会变。
   ⇒ 必须**先跑基线、再改、再对比**，且差异必须逐条可解释。
3. **浮点走 Real 是行为变更** ⇒ 按 §4.1 的建议，v2 先不动浮点。
4. **查询量爆炸** ⇒ §7 的预算与降级；**超出预算必须被记录**，不能静默。
5. **`TypeTest` 不进数值路径条件** ⇒ 「`if (x is String)` 之后 `x.length()` 安全」这类推断**不受本设计保护**，
   需要另设事实域。这是已知的能力边界，不是遗漏。
