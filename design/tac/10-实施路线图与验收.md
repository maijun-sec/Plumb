> 配套：`01`（IR 设计）、`02`（覆盖矩阵）、`08`（wire v2）、`09`（引擎与 Z3）、`11`（新发现与原审计修正）。

## 0. 三条铁律

### 铁律一：**「能表达」与「已实现」分开记账**

一个构念的覆盖状态是**两维**的：

| | 前端已实现 | 前端未实现 |
|---|---|---|
| **IR 能表达** | ✅ 覆盖 | 🟡 **工程债**（IR 够用，缺实现） |
| **IR 表达不了** | ❌ 不可能 | ❌ 不可能 |

⇒ **门禁只允许红色出现在「🟡 工程债」格**。
「IR 表达不了」那一格在本设计里**必须是空的**（见 `02` §3：**13 个例外**（4 + 4 + 3 + 2）全部是运行时事实 / 求解器能力 / 无运行时对应物）。

⇒ 这条铁律把「丢弃率」这个指标**从单维变成双维**：
原审计的「丢弃 505 条 / 34.9%」里，**真正需要改 IR 的只有一小部分**，
其余是「前端没写」。把它们混在一起，会让优先级完全错位（见 `11` §3.1）。

### 铁律二：**每一步都要能证明「没变坏」**

每个阶段的验收必须包含一条**差分口径**：

> 同一份语料、同一份配置，新旧两版各跑一次；
> **要求**：新增能力生效的地方 finding **增加**（原来漏的现在找到了），
> 其它地方 finding **逐条一致**。
> 出现「不相等但解释不了」的差异 ⇒ 阶段不算完成。

### 铁律三：**数字必须可追溯**

禁止把「上一轮的 finding 数」当基线。每一轮的数字必须**当场跑出来并落盘**
（导出 CSV 或一个 md），并在 commit message 里记录。
理由（这是本轮已经踩过的坑）：报告目录会被下一轮覆盖 ⇒ 「历史基线」会变成幽灵数字。

## 2. 三个门禁

### 门禁 A：**声明面完备性**

> 对每个语言：**枚举该语言的全部声明种类**，逐个断言：
> 要么 TAC 里有对应物，要么有一条 `TacDrop` 记录。

**实现**：每个前端维护一张**声明种类清单**（语言定义 ⇒ 清单）；
前端每遇到一个声明，**打勾或记 drop**；
门禁脚本读清单与实际产出，断言清单 100% 被覆盖。

**它抓什么**（本轮的新发现证明它有价值）：
- Kotlin 的 `for`/`while`/`try` 整个不存在（按构念计数抓不到，按清单能抓到）；
- Kotlin 的类属性 / 顶层属性 / `init` 块 / 嵌套类不产生任何东西；
- TS/ArkTS 的类字段 / 构造器 / 访问器 / 静态块被静默丢弃；
- Scala 的类级字段 / `given` / enum case 值 / `lazy val` 不产生任何东西。

### 门禁 B：**控制流结构断言**

> 对每个 `BRANCH` / `CATCH_HANDLER` / `FINALLY_ENTER`，断言：
> ① 每个分支区域都能被 `TacBranchRegion` 描述；
> ② 每个 case 的守卫非空（`default` 除外）；
> ③ `finally` 的每个出口都有边（try 完成 / 每个 catch 完成 / rethrow / `return` ——**四类都要**）。

**在 CFG 构建后做结构校验**；不满足 ⇒ 报**前端 bug**，**不是「降级」**。

### 门禁 C：**求解器可判定性**

> 对每条路径，断言：路径上的守卫集合可被渲染成 solver DSL；
> 且渲染后的谓词数量 ≥ 1（否则说明这条路径的守卫全丢了）。

**度量**：自动推出的守卫数、守卫可渲染率、Z3 查询次数 / 缓存命中 / 超预算次数。
**超预算必须被记录**，不能静默（见 `09` §7）。

> **C 档例外也有自己的验收矩阵**：`02` §3.6 的 **29 条语言级 C 档真例外**，逐条映射到「① 实现步骤 ② 测试用例 ③ 预期证据」，见 `13-例外验收矩阵.md`。⇒ 其中 **S2（IR-B + IR-A：丢弃记账与精度三档）是全部 29 条的公共前置**：没有 drop 通道，C 档就退化成静默丢失。

## 4. 回归基线纪律

1. **当场跑、当场落盘**：每个阶段的基线是**这一次跑出来的**，不是上一轮的。
2. **语料固定**：用同一份语料（审计期已有 `probes/` 294 个探针），
   每阶段前后各跑一次。
3. **差异逐条解释**：不允许「整体差不多」。
4. **数字进 commit message，不进产品文档**：产品文档里出现「语料名 + 百分比」会被文档卫生门禁拦下
   （语料不在版本控制里，读者无法复现）⇒ 数字属于 git 历史或命令输出。
5. **变异门禁的残骸要清理**：跑「植入一个弱化变异、验证门禁会失败」的测试后，
   若进程被杀/超时，**变异会留在工作树里**并伪装成别人的在飞改动 ⇒ 提交前必须比对并还原。

## 6. 风险

1. **「全覆盖」会被当成「可以一次做完」** ⇒ 实际上 S7 是五条语言线 × 各自清单的总和，
   量级远大于 S0~S6。⇒ **建议先做 S0~S6 中「IR 能表达但没人接线」的部分**（S1），
   它们改动最小、收益最大。
2. **协议升级可能引入静默行为变化**（例如 `CONST.value` 从「可缺省」变成「必须存在」，
   会让老 sidecar 的常量语义改变）⇒ S0 必须配套「老新组合的差分测试」。
3. **有界约束改变溢出类判定** ⇒ S4 必须有差分与逐条解释。
4. **门禁 A 的清单要维护**：语言版本升级会新增构念 ⇒ 清单要跟着升，
   否则门禁会因为「清单没变」而放过新构念。⇒ 清单要**从语言规范自动生成或至少定期复核**。
5. **`SOURCE_DEGRADED` 追加在枚举末尾**会让枚举顺序失去语义 —— **已裁定采纳追加末尾**
   （`01` §8.1）：全仓 `IrPrecision` 的使用点**零处**按序比较（只有 `==` 跟具名常量），
   ⇒ 安全。**配套硬规则**：判断一律走 `preservesSemantics()` / `hasSemanticLoss()`，
   且**新增精度档位时用 grep 确认没有引入 `<`/`>`/`ordinal()`**。
6. **`TacType.domain` 不参与 `equals`**（`01` §8.2 已裁定）⇒ 三个已知依赖点必须同步改成
   `sameDomain()`：常量折叠的宽度选择（`ExpressionTranslator.java:1430`）、
   指向对象的身份（`AbstractObject.java:97`）、CFG 的类型同一性（`TacCfgBuilder.java:158`）。
   ⇒ **漏改任一处 ⇒ 数值宽度静默错判**（比漏报更糟）。
