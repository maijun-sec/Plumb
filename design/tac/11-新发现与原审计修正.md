## 0. 为什么要单列一份

原审计的结论是「**丢弃了哪些构念**」；本轮复核问的是「**丢弃发生在哪一层、后果是什么**」。
两者的差别在这三个层面体现出来：

1. **有些「丢弃」其实是「建错」**（给了错误答案），原审计归为同一类；
2. **有些「丢弃」根本没进过任何报告通道**（静默到连精度都不降）；
3. **有些结论的原表述过宽或过窄**，需要修正（§1）。

⇒ 这些差别直接改变整改的**优先级排序**：有的条目「改一个 `else`」就够，
有的条目「IR 少一个字段」才够，还有的条目**根本不该用丢弃的方式修**。

## 1. 对原审计结论的修正（4 条）

### 1.1 修正：Java `switch` 的 **fall-through 其实已经建模了**

**原审计**（总报告 P0-2）称：「Java `switch` 只有第一个 case 比较是活的」。
**复核结论**：**不准确**。

事实（`plumb-tac/.../translate/StatementTranslator.java` 的 `translateSwitch`）：
- case 体末尾**不发射 JUMP** ⇒ **fall-through 是建模的**（与 Java 语义一致）；
- `default` 被建模为「链中当前位置的无条件 JUMP」⇒ **当 `default` 不在源码末尾时，后续 case 永远不可达**
  （这是真缺陷，但性质是「顺序错」，不是「只测第一个」）；
- **多标签 entry（`case 1, 2:`）只有第一个标签被测**：每个标签的 BRANCH 的 false 目标都是
  **下一个 entry**（不是下一个标签）⇒ 第二个标签的比较**永远不执行**。

⇒ **整改方向要改**：不是「把 fall-through 建出来」（已经有了），而是
「把 `default` 排到链尾」+「多标签要 OR 起来（可复用表达式形式的写法）」。

### 1.2 修正：`tryRegions` 不是「IR 缺能力」，是「wire 没填」

**原审计**把 `tryRegions` 硬编码列为 IR 侧缺口。
**复核结论**：IR 侧**早就有**完整的 `TryRegion`（含 try/catch/finally 的索引区间 + 标签），
Java 前端也在调用（`TacBuilder.recordTryRegion`）；**只是 6 个 sidecar 路径的共享 mapper 把它硬编码成空**
（`plumb-frontend/.../sidecar/SidecarTacMapper.java:150`）。

⇒ **这是本轮性价比最高的一条**：协议字段早已存在，只差接线（见 `08-wire-协议-v2.md` §6 W2）。

### 1.3 修正：注解/特性 **不需要新增 IR 能力**

**原审计**把「注解/特性/装饰器无线上字段」列为 IR 侧工作。
**复核结论**：**IR 侧四个注解通道 + `annotationValues` 全都存在**（`TacFunction.java:123-154`），
Java 前端已经在用（`TacTranslator.java:941-960`）。缺的是：
- **Kotlin / Scala 前端从不读注解**（IR 通道全空）；
- **6 个 sidecar 的 wire 协议没有这个字段**。

⇒ **注解这条路不需要设计任何新 IR 字段**，只需要「前端去读」+「wire 加字段」。

### 1.4 修正：精度的生产消费方**不是零**

**原审计**称 `IrPrecision` 的消费者只在测试里。
**复核结论**：**有一个生产消费方** —— `plumb-dfa/.../engine/ModelCoverageComputer.java:133`
（`fn.irPrecision() == IrPrecision.SOURCE_FULL`）。
另一处 `ScannedOrigin.java:81` 只打印。

⇒ 「补精度声明不改变任何 finding」这个判断**对 finding 成立**（没有 checker 读它），
但对**覆盖率报告**不成立（`ModelCoverageComputer` 读它）⇒ P0-4 的修法应写成
「让精度有 finding 级的消费方」，而不是「让精度有消费方」。

### 2.6 第六类：**引擎侧把「未知」悄悄当成「32 位整数」**

这一类不是前端丢信息，也不是协议缺字段，而是**引擎消费端自带了一个隐藏假设**，
且这个假设**与三种语言的语义直接冲突**。

| 事实 | 后果 | 证据 |
|---|---|---|
| `Range.ofType(TacType)` 对 `UNKNOWN` 返回 **int32 区间** | 一个**没有类型信息**的整数变量，溢出/下溢判定按 **32 位**做 | `checkers/boundary/Range.java:133-143`（`:141` = `case UNKNOWN -> of(Integer.MIN_VALUE, Integer.MAX_VALUE)`） |
| 四份**逐字复制**的 `isArithType` 都把 `UNKNOWN` 列为算术类型 | 同上；且这是**四处**独立副本 | `checkers/boundary/OverflowConstraintChecker.java:159-165`、`UnderflowConstraintChecker.java:142-148`、`DivZeroConstraintChecker.java:95-101`、`ArrayBoundsConstraintChecker.java:109-115` |
| 值域消费点**分散在 6 处**，不是「一个 `switch(kind)`」 | 改漏任意一处 ⇒ 该 hazard 仍按旧口径判定 | 上两行 + `checkers/taint/NumericTruncationChecker.java:149` + `checkers/boundary/BoundaryConstraintChecker.java:654-659`（`STATIC_FINAL_TABLE`） |
| `checkers/boundary/` 与 `checkers/taint/` 各有一套**名字相近但不同类**的溢出 checker（`OverflowConstraintChecker` vs `IntOverflowChecker`） | 按名字找会**找错文件** ⇒ 改错地方还以为改对了 | 两个包下的同名族 |

⇒ 对 **Python（任意精度）/ Go（平台相关 32 或 64）/ PHP（平台相关）** 而言：
只要前端没把宽度信息填进 IR，这些语言的整数溢出判定就是**按 int32 做的误报**
——语言里根本不会溢出，引擎却按会溢出去报。⇒ 这是 **IR-D 落地之前就已经存在**的误报，
不是 IR-D 引入的；但它会被误记成「IR-D 没修好」。

⇒ **推论（直接改变实施顺序）**：**IR-D（值域）必须先于这几个语言的前端上线**。
理由：若前端先填 `domain` 而引擎还不读 ⇒ 填了白填；而引擎先读 `domain`、
前端后填 ⇒ 每上线一个语言就立刻消掉这一类误报，收益可逐语言度量。

## 3. 这批新发现对设计的三个影响

### 3.1 优先级要重排

| 序 | 动作 | 为什么提前 | 原审计的排序 |
|---|---|---|---|
| **1** | **wire 接线**（`tryRegions` + 五个注解通道 + `returnType`） | 协议字段**早已存在**，只差填 ⇒ 一次性修好 6 个语言的异常流 / 注解 / 返回类型 | P0-3 / P0-6 / P1-6（原排序分散在 P0/P1） |
| **2** | **`calleeSig` 规范化**（IR-P） | 一条就能修好 Python 在**每个方法边界**断掉的跨函数污点；Java 的 for-each 调用图也一起修 | 散落在 P1 |
| **3** | **短路 + finally + 标签跳转 + switch 顺序**（IR-C/IR-G/IR-I） | 这四条是**错答案**，不是缺信息 ⇒ 危害最大 | P0-2 |
| **4** | **声明面兜底**（IR-E + 各前端 `else`） | 影响 6 个面；但其中 Kotlin/Scala 是「整类不存在」⇒ 要连函数一起建 | P0-1（原本第一） |

### 3.2 「门禁 A」（声明面完备性）必须**逐语言列清单**

原审计用「台账行数」证明「无遗漏」；在设计的语境下，这不够。
**门禁 A 的形式**应该是：每个语言维护一张**声明种类清单**（语言定义 ⇒ 清单），
前端每遇到一个声明就**打勾或记 drop**，门禁断言清单 100% 覆盖。

⇒ 这条门禁能同时抓住「Kotlin 的循环整个不存在」「TS 的类字段整个不存在」这类**原审计按构念计数抓不到**的问题。

### 3.3 「丢弃」这个词要分三类，处置完全不同

| 类别 | 处置 | 例子 |
|---|---|---|
| **没实现**（工程债） | 实现它；门禁清单补上 | Kotlin 的 `for` |
| **没能力**（IR 缺口） | 先加 IR 能力，再实现 | 联合类型、穷尽性、临界区 |
| **不可能**（运行时事实） | 保守建模 + 明确记录 | 并发交错顺序、`select` 就绪顺序 |

⇒ 原审计把它们混在一个「丢弃」桶里，所以「丢弃率 34.9%」这个数字
**高估了「IR 不够」的部分**，也**低估了「工程债」的部分**。
