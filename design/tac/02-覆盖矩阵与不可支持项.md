# 覆盖矩阵：TAC 对各语言全部特性的表达力（含「无法完整支持」及理由）

> **立场**（用户口径）：TAC 应当支持全部语言的全部特性。凡是确实无法支持的，必须给出理由。
> 本文的判定标准因此不是「能不能降级」，而是「**能不能完整表达**」。

## 0. 判定标准：什么叫「完整表达」

一个构念被判定为「TAC 完整支持」，当且仅当下面四条同时成立：

1. **可表达**：该构念的运行时语义可以由 TAC 的指令流 + CFG + 元数据完整刻画，**不产生「UNRESOLVED / UNKNOWN / 静默跳过」**。
2. **可判定**：分析引擎能基于 TAC 得出确定结论（而不是「不知道」）。
3. **不撒谎**：TAC 里不出现与源码语义相反的东西（审计里最贵的一类是**错答案**，不是缺信息）。
4. **可追责**：如果该构念在某个语言里确实无法静态刻画，它在 TAC 里有一条**显式的、机器可读的**记录（IR-B 的 `TacDrop`），并且精度随之下调。

**只有第 4 条不成立时才算「无法完整支持」**——而第 4 条不成立的构念分三类根因，见 §4。

> **重要**：IR v2 的 `SOURCE_DEGRADED` / `TacDrop` **不是「兜底通道」**，而是「**确实无法静态表达**的记账通道」。
> 一个语言构念如果能被完整表达，它就**不应该**产生 drop。

## 2. 需要新增的 IR 能力（本文新增提案，编号接续 `01`）

`01-TAC-IR-扩展设计.md` 已提出 IR-A..IR-H。本节补上「**完整支持**」所必需、但 IR-A..IR-H 尚未覆盖的部分。

### IR-I 分支区域（`TacBranchRegion`）—— 覆盖 B6 / C4

**为什么必须有**：审计认定「控制流建错」的一整类问题都出在分支上（ArkTS switch 按顺序执行 case、Java switch 多标签 arm 只有第一个标签被测、Scala `match` 的 case-class 模式被当成终止通配）。
**分支的正确性不只是「有几条 BRANCH」，还包括「哪些 case、每个 case 绑定了什么、有守卫吗、穷尽吗、default 在哪、fall-through 到哪」**——
这些是**结构**，不是指令流 ⇒ 指令流装不下 ⇒ 必须有区域结构。

```java
/** 一个分支区域：switch / match / when / if-else 链。 */
public record TacBranchRegion(
    String id,
    BranchKind kind,                 // SWITCH | MATCH | WHEN | IF_CHAIN
    TacOperand subject,              // 被判定的值；IF_CHAIN 为 null
    List<TacCase> cases,
    String defaultCaseId,            // default 的 case id；无则 null
    boolean fallThrough,             // case 体末尾是否落入下一个 case
    boolean exhaustive,              // 是否穷尽（编译器可判定时为 true）
    List<String> missingCases,       // 穷尽性检查缺哪些类型（可空）
    String scopeId)
    implements java.io.Serializable {}

public record TacCase(
    String id,
    List<TacGuard> guards,           // 该 case 的判定条件（可多个 ⇒ OR）
    List<TacBinding> bindings,       // 该 case 绑定的变量（模式绑定）
    String bodyLabel,                // case 体入口
    String nextLabel)                // 该 case 不匹配时跳到哪（下一个 case）
    implements java.io.Serializable {}

public record TacBinding(String name, TacType type, TacType sourceType, boolean nullable)
    implements java.io.Serializable {}
```

**与 `TacGuard` 的关系**：`TacGuard` 说「**这一条边**的条件是什么」；`TacBranchRegion` 说「**这个分支整体**长什么样」。
两者互补，缺一不可。

**Z3 友好性**：区域让引擎能一次性问出「这个 switch 的 case 集合是什么」「某个 case 的守卫集合是什么」，
从而对 `case` 值做**集合推理**（例如「x 落在这个 switch 的任一 case 里 ⇒ x ≠ default」）。

### IR-J 异常类型（`THROW` 的类型 + 异常层级）

**为什么必须有**：`TacInstruction` 现在**没有「抛出类型」字段**（类型在 `CATCH_HANDLER.ctorType`，但抛出点没有）。
⇒ catch 的匹配只能靠 CFG 侧比对，而抛出的具体类型在 TAC 里根本不存在。

**最小改动**：复用 `TacInstruction.ctorType`（`TacInstruction.java:231`，`NEW`/`NEWARRAY` 已在用），让 `THROW` 也用它。
**零新字段、零新枚举**。异常层级（哪些异常是 `RuntimeException` 的子类）由引擎侧的目录提供，
**不进 IR**（它是世界知识，不是程序事实）。

### IR-K 类型的三个新维度（类型实参 / 联合 / 类型变量）

**为什么必须有**：审计里「泛型实参无字段」「联合类型变成假类名 `"A|B"`」「类型变量只留上界」都在这一类。
**假类名是最坏的一种丢失**：它不是「未知」，而是**错的**（`"A|B"` 不是任何真实类型 ⇒ 任何按类型匹配的规则都永远不命中）。

```java
// TacType 追加三个可选字段（全部追加在末尾，不动 15 个既有 Kind）：
private final List<TacType> typeArguments;   // 泛型实参；null = 未参数化
private final TacType bound;                 // 类型变量的上界；null = 不是类型变量
private final List<TacType> unionMembers;    // 联合类型的成员；null = 不是联合
```

**为什么不用新增 `TacType.Kind`**：加 Kind 会波及所有 `switch (type.kind())` 的地方
（实测 `checkers/boundary/Range.java:135` 等 —— `return switch (t.kind()) {`，另有 4 份复制的
`isArithType`，共 6 处按类型分派），且**联合类型与泛型实参是「正交维度」而不是「新的种类」**——
一个 `List<string|null>` 同时有泛型实参和联合成员，加 Kind 表达不了这种组合。

**「假类名」的终结**：联合类型 ⇒ `unionMembers` 非空、`className` 不再拼字符串；
类型变量 ⇒ `bound` 非空、`className` 为 null（**不是** `"T"`）；泛型 ⇒ `typeArguments` 非空。

### IR-N 类型声明的完整化（类型参数 / 允许的子类型）

`IR-E` 已提出 `TacTypeDecl`。这里补两个字段：

```java
List<TacTypeParam> typeParameters;  // <T : Bound>，含变型（in/out）与约束
List<String> permittedSubtypes;     // sealed / permits：允许的子类型
```

**为什么必须有**：审计认定「sealed 类型 / permits 子句完全没处理」；
而「穷尽性检查」需要知道「这个 sealed 层次有哪些子类型」。

### IR-L 挂起 / 恢复（协程）

```java
// TacInstruction.Effect 追加一个枚举常量（追加在末尾）：
SUSPEND   // 这个调用可能挂起当前执行；恢复点在同一个函数的某个标签
```
**配套**：函数级新增 `List<TacResumePoint> resumePoints`（`{label, kind}`，kind ∈ {SUSPEND, EXCEPTION}）。

**为什么不能只靠 `Effect`**：`Effect` 只能标记「这里可能挂起」，不能表达「恢复后从哪继续、恢复时哪些局部量是活的」。
`suspend fun` 的完整建模需要**状态机展开**：每个挂起点一个状态，函数变成若干个状态函数。
**这是前端工作量，不是 IR 能力缺口** —— IR 只需能标出挂起点与状态边界。

### IR-M 临界区（同步）

```java
// 函数级：
List<TacCriticalSection> criticalSections;  // {label, monitorExpr, kind(SYNCHRONIZED|ATOMIC|TRANSACTION)}
```

**为什么必须有**：Java 的 `synchronized` 现在完全没有锁语义（锁对象只被求值）。
引擎里已有原子性 checker（`plumb-dfa/.../checkers/controlflow/ServletAtomicityDfaChecker.java`），
但**临界区的范围信息在 TAC 里不存在** ⇒ checker 无从判断「这两条写是不是在同一把锁下」。

### IR-P 全语言统一的 callee 命名规范（`calleeSig` / `calleeParamTypes`）

**为什么必须有**：这一条不是「新能力」，是**「已有能力必须统一使用」**：
- 审计认定「Python 方法调用在引擎的调用图解析器里解析不了」—— 根因是 `declared_arity` 减接收者而签名不减，
  **两个地方对「参数个数」的约定不一致**；
- Java 的 for-each 用的是合成短名 `"iterator/0"`、`"hasNext/0"`、`"next/0"`（**不是任何真实方法名**）⇒ 调用图解析不到；
- TS/ArkTS 的 `ownerOf` 有 `UNKNOWN_OWNER` 兜底 ⇒ owner 丢失。

⇒ **必须写死一份规范**（写在 `01` 的 §3 或独立的 wire 文档里）：

| 规范项 | 规则 |
|---|---|
| 形状 | `<ownerFqn>#<methodName>/<arity>` 或 `<methodName>/<arity>`（无 owner 时） |
| arity | **总是「显式实参个数」**，不含隐式接收者；接收者单独由 `args[0]` / `owner` 表达 |
| 接收者 | **一律显式作为 `args[0]`**（Java/Kotlin/Scala/C#/PHP/Python 统一） |
| 迭代协议 | `iterator/0`、`hasNext/0`、`next/0` **必须是真实存在的语言方法名**（如 `java.util.Iterator.hasNext/0`），不得用合成短名 |
| owner 未知 | **不允许**用 `UNKNOWN_OWNER`；改用**结构化 owner 缺失**（`ownerType=null` + `calleeSig` 只含方法名与 arity） |

**这一条是「跨函数污点能否跨过方法边界」的总开关** —— 审计认定 Python 在**每个方法边界**都断掉。

### IR-Q 强制转换与相等语义的引擎侧规则表

不是 IR 能力，是**引擎侧**（与 `IR-H` 同族）：PHP `"1abc"+1 == 2`、TS `"1abc"*1 == NaN`、
Java `==` vs `.equals`、Go 接口比较、Python `is` vs `==`。
IR 侧只需保证 `CAST` 与 `calleeSig` 能区分这些（现有 IR 已有 `castType` 与 `calleeSig`）。

## 3. 「无法完整支持」的清单及其理由

按 §0 的判定标准，下面这些**确实是无法完整支持的**。其余全部支持。

### 3.1 根因一：结果由**运行时**决定，源码文本不足以判定

| 构念 | 为什么无法静态表达 | 保守建模形状 | 对精度的影响 |
|---|---|---|---|
| **动态属性 / 反射 / `eval` / `getattr` / `globals()` 副作用** | 属性是否存在、值是什么，取决于运行时的对象状态与注册表，源码里没有这个事实 | `CALL` + `UNINTERPRETED`；结果按**未知**处理（既不当干净、也不当污点源） | 依赖该结果的规则**不出结论**（而不是出错结论） |
| **Go 的表达式求值顺序未定义处** | Go 规范明确某些表达式的求值顺序是未指定的（函数实参、`map` 下标与赋值） | 固定一种顺序，并在该函数上记一条 `TacDrop(impact=SEMANTICS)` | 依赖求值顺序的规则（典型是「先校验后使用」）在该函数上不成立 |
| **运行期才确定的类型（TS 的 `any`、Python 的鸭子类型）** | 类型在运行期才定 | `TacType.UNKNOWN` + `domain=Dynamic`；类型测试用 `INSTANCEOF` 的动态形式 | 类型门控类的规则在这些点上**不触发**（不误报，也漏报） |
| **C# `dynamic` / `object` 的运行期绑定** | 同上 | `CALL` + `UNINTERPRETED` | 同上 |

### 3.2 根因二：**并发/调度**决定的顺序

| 构念 | 为什么无法静态表达 | 保守建模形状 | 对精度的影响 |
|---|---|---|---|
| **线程交错的具体序列（data race 的实际发生顺序）** | 交错是调度器与硬件决定的，源码里没有这个事实 | 顺序路径 + `Effect.CONCURRENT` 标记 | 竞态类规则报「**可能**发生」，不报「发生了」 |
| **Go `select` 就绪哪个 channel** | 就绪由运行时决定 | 保守展开成「**所有** case 都可达」 | 分支可达性被过近似 ⇒ 多报 |
| **`synchronized`/`lock` 的争用顺序（谁先进入）** | 同上 | 临界区范围进 IR（`IR-M`）+ `Effect` 标记 | 死锁/顺序类规则**不报**（无法判定），原子性规则照报 |
| **协程的恢复顺序** | 同上 | 挂起点 + 恢复点（`IR-L`）；恢复后状态按「任意挂起点可能到达」合并 | 跨挂起点的数据流被过近似 |

### 3.3 根因三：**求解器侧能力**（不是 IR 的缺口，但影响「Z3 能证到多少」）

| 构念 | 为什么无法静态表达 | 保守建模形状 | 对精度的影响 |
|---|---|---|---|
| **IEEE-754 浮点的精确舍入** | 现有 bridge 把所有数建成无界 Int（`Z3Bridge.java:266-278`），浮点与实数统一成 Int 近似 | `TacValueDomain.Floating(53,11)` 声明形状；**bridge 侧要接 Z3 的 FP 理论才可能精确** | 浮点相关的边界推理**不可用**（当前就已经不可用） |
| **C# `decimal` 的 128 位定点舍入** | Z3 无十进制定点理论 | `FixedPoint(128, scale)`；按 Real 近似 | 同上 |
| **字符串的**内容**级性质**（是否包含某子串、长度以外的关系） | 现有 bridge 把字符串折成**长度**（`Z3Bridge.java:258-260`） | 现有简化维持；内容级性质不可判定 | 字符串内容类规则**不走 Z3**，走其它机制 |

### 3.4 根因四：**没有运行时对应物**

| 构念 | 为什么无法静态表达 | 保守建模形状 | 对精度的影响 |
|---|---|---|---|
| **类型级计算**（TS 的 conditional/mapped types、Scala 3 的路径依赖类型） | 类型级计算**不产生任何运行时值**；TAC 是运行时 IR | 运行时语义不受影响 ⇒ **对运行时不产生影响**；但**依赖类型推断的规则**用的是**解析后的类型**（TS 前端能拿到），故仍可判定 | 只影响「按类型推断的规则」，不影响运行时分析 |
| **编译期宏 / `inline` 展开**（Kotlin `inline`、Scala 3 `inline`、C# `where` 约束的展开） | 展开是**编译期行为**，不展开就看不到展开后的控制流 | 前端**必须做展开**才能完整支持（这是工作量，不是能力缺口）⇒ 列入 §5 路线图 | 展开前 ⇒ 内联体的控制流不可见 |

### 3.5 结论

**真正「无法完整支持」的只有 4 类根因、13 个具体条目**（4 + 4 + 3 + 2），且其中：

- **没有一条是「IR 表达不了」**——它们要么是**运行时事实**（源码里没有这个信息），
  要么是**求解器能力**（bridge 侧可补，不是 IR 侧），
  要么是**没有运行时对应物**（因此对 TAC 无影响）。
- 唯一「IR 侧要做事」的是 `inline` 展开，而它是**前端工作量**，IR 已经能表达展开后的形态。

⇒ **IR v2 足以支持全部语言的全部特性**（除 §3.4 的类型级计算，因为它没有运行时对应物）。
这正是 `01-TAC-IR-扩展设计.md` §0.2 形状选择的回报：**全部是加字段，没有一个是加变体**。

| `05` **模板字面量类型** `` `${A}-${B}` `` | 纯类型层计算：取值模式无处可放 | `IR-AU`（`TEMPLATE_LITERAL`） | **已解决** |
| `05` **`keyof` T** | 纯类型层计算：键名集合无处可放 | `IR-AU`（`KEYOF`） | **已解决** |
| `05` **`infer`** | 类型绑定子，绑定出的类型参数无处可放 | `IR-Y` 的字段扩展（`TacTypeDecl.typeParameters[].constraint`） | **已解决** |
| `05` **DNF 类型** | 类型层规范化过程无处可放 | `IR-AU` + `IR-T`（成员集合进联合成员列表） | **已解决** |
| `05` **`const` 类型参数** | 实参推导的字面量宽度无处可放 | `IR-AU`（`LITERAL`，实参记字面量类型） | **已解决** |
| `05` **`import type` / `export type`** | 类型图上的模块边无处可放 | `IR-AU`（`TacTypeDecl.typeOnlyImports`） | **已解决**（运行期仍是零指令） |

⇒ **净结论**：在「主命名空间 + 补充 IR」这套完整形状下，**真正无法完整支持的只剩 13 条根因级条目**，
且它们**没有一条是 IR 表达力问题** —— 全部是运行时事实、求解器能力、或无运行时对应物。

## 4. 「全部支持」怎么被证明（验收口径）

「全部支持」不是一句承诺，必须可验证。三个门禁：

### 门禁 A：**声明面完备性**（防 P0-1 复发）

> 对每个语言，**枚举该语言的全部声明种类**，逐个断言：要么 TAC 里有对应物，
> 要么有一条 `TacDrop` 记录。

实现方式：每个前端维护一张**声明种类清单**（语言定义 ⇒ 清单），
前端每遇到一个声明，必须在清单上打勾或记 drop。
**门禁脚本**读清单与实际产出，断言「清单 100% 被覆盖」。

### 门禁 B：**分支与异常的结构断言**（防「控制流建错」）

> 对每个 `BRANCH`/`CATCH_HANDLER`/`FINALLY_ENTER`，断言：
> ① 每个分支区域都能被 `TacBranchRegion` 描述；
> ② 每个 case 的守卫非空（除 default）；
> ③ `finally` 的每个出口都有边（IR-F 的 `finallyExits` 覆盖 try/catch/rethrow/return 四类）。

**门禁**在 CFG 构建后做结构校验；不满足 ⇒ 报**前端 bug**，不是「降级」。

### 门禁 C：**求解器可判定性**（把 Z3 从「检查器想到的守卫」扩到「CFG 推出的守卫」）

> 对每条路径，断言：路径上的守卫集合可被渲染成 solver DSL；
> 且渲染后的谓词数量 ≥ 1（否则说明这条路径的守卫全丢了）。

**门禁**用固定语料，统计「自动推出的守卫数」；这个数从 0 变成正数是 S2 阶段的验收线。

## 5. 与路线图的对应

| 阶段 | 覆盖矩阵里被打开的格子 |
|---|---|
| S1（IR-B + IR-A） | 打开「**记账通道**」：所有 drop 可见；但**不解决**任何表达力缺口 |
| S2（IR-C 守卫） | 打开 C2 / C3 / C4 的条件表达；门禁 C 成立 |
| S3（IR-F + wire `tryRegions`） | 打开 C5（异常/资源）；门禁 B 成立 |
| S4（IR-D 值域） | 打开 D1 / D4；溢出下溢的边界由 Z3 推 |
| S5（IR-E + IR-G + IR-I + IR-J + IR-K + IR-N） | 打开 A1–A5、B3、B6、C3、C4、C6、D2、D3、E5；门禁 A 成立 |
| S6（IR-L + IR-M + IR-H + IR-P） | 打开 C7、C8、E2；**跨函数污点跨过方法边界**（IR-P） |
| S7（前端逐语言铺开） | 每个语言按门禁 A 的清单逐项填满 |
| S8（`inline` 展开） | 打开 §3.4 的唯一一项 |

⇒ **没有任何一格是「打不开」的**。这与审计的现状（505 条丢弃、其中 279 条静默）形成对照：
审计里的「丢弃」绝大多数不是「TAC 表达不了」，而是「**前端没实现**」或「**IR 少了一个字段**」。

## 6. 给读者的三句话

1. **TAC 能表达全部语言的全部特性**——IR v2 补齐后，剩下的 **13 个例外**（根因一 4 + 根因二 4 + 根因三 3 + 根因四 2，见 §3.5）全部是「运行时事实」「求解器能力」或「无运行时对应物」，都不是 IR 的缺口。
2. **今天丢弃的 505 条里，没有一条是语言本身表达不了**——它们是「前端没写」「dispatch 缺 else」「IR 少字段」「wire 少字段」四类工程问题。
3. **因此优先级是工程量，不是架构**：`IR-P`（callee 规范）单项就能修好 Python 在每个方法边界断掉的跨函数污点；
   `IR-F` + wire `tryRegions` 能一次性修好 6 个 sidecar 语言的零异常流边。
